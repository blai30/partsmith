# Partsmith M2 plan: curves, threads and labels, sized for your printer

Written on 2026-11-07 against `main` at 633eeb9.

## 1. Purpose

M2 is the second of the four milestones that land v1.0 (technical design section 18). It brings the sketcher to Fusion and FreeCAD parity: conics, B-splines, every drawing and modify tool, sketch text and geometry projected from the model. It turns those outlines into sweeps, coils, lofts, ribs, thin walls, embossed labels, modeled FDM threads and tapped holes, in the GUI and in Python. Threads and tapped holes are sized from the user's own printer profile. With M2 a maker can build all four v1 test parts of technical design section 1: an enclosure with a fitted lid, a ribbed bracket, a spur gear and a threaded cap. They can also bring Fusion and Onshape parts in as STEP from inside the app and keep their references through upstream edits.

Technical design section 18 names four phases and four gates, but the diagram that held their contents is not in its text. In its place the section reads "*(Diagram in the original document: roadmap, 4 phases, 4 gates.)*". M2 to M4 are derived from the design's product sections and from the deferred lists of every spec (each "Later (not in M1)" or "Explicitly later" section and the open issues that defer work). The work M1 left open comes from [m1-gap-list.md](m1-gap-list.md). Four readers listed the deferred items with their sources and sizes. Three proposals were scored. This plan starts from the best one with parts of the other two (section 7.1). Configurations, face color painting and resin lattice infill stay in v1.1. Cloud, AI assist, plugins and the model library come after that (technical design section 18). Every open choice is settled by the owner's standing rule of 2026-11-05: the most open-source approach, the safest approach, the industry standard, then the planner's recommendation. Section 7.3 records each one as `Accepted (owner's rule of 2026-11-05)` with its options. Nothing in this plan waits for the owner before it starts. The human reviews and checks fall at the gate (section 4).

### 2.1 Why each item is in M2

In the order of the table:

1. The owner scheduled the exact trust-region step right after M1 (m1-gap-list.md, the paragraph on what stays with the owner). It removes the slides that fail property test 192 about once in 2,000 to 5,000 nightly runs. It lands before conics, B-splines and the modify tools add nonlinear rows to the same solver. Option (d) also changes the iteration path of cases that do not slide. The examples are re-blessed once, after the libm perturbation check, by an ADR that lists them (gate 5). A new acceptance test pins sketch.md section 3.11's minimum-norm promise on the replayable seeds (today only test 256 checks it).
2. Sweep paths along sketch curves, helix and thread edges and projected sketch geometry are named from what made them. In M1 every edge and vertex is named by its adjacent faces (naming.md open issue 4). The direct-generator rule changes the naming algorithm and goes to review at the gate. It is built as additions and aliases only. No M1 reference changes (section 7.3 item 3).
3. Sweep paths, ribs, webs and thin walls take open sketch chains. The profile API changes once, before four features depend on it. The region union moves from partsmith-features into partsmith-sketch with no change in behavior.
4. Recompute has a `CancelToken` and a `NotRun` status. The engine always passes a fresh token. The kernel has no progress hook (checked in partsmith-recompute, partsmith-engine and partsmith-occt-sys at 633eeb9). Nothing that is running can be stopped. The web restarts its worker and loses the undo history. Modeled threads, sweeps and embossed text run far longer than M1's features. Technical design section 14 makes previews cancellable. Cancel lands before those features: OCCT progress indicators and the engine's token checked against a flag the host holds outside the session, and the `not_run` status in the protocol. A protocol command cannot reach a running call. The web worker is blocked in `ps_call` and handles no message. The core has no second thread (it is built without shared memory, `crates/partsmith-wasm/build.rs`). On the desktop the running call holds the `Session` mutex (desktop.md open issue 9). The desktop gets Stop and a new host command beside desktop.md 1.1's eight, with its capability and app-manifest entry. The command sets the flag without taking the mutex. The web gets a SharedArrayBuffer word that the page sets and partsmith-occt-sys reads through an Emscripten JS import, with no fourth C ABI export (ADR 0010).
5. A command adds an asset to an open document without reopening it. The undo history then survives Choose folder. `asset_mismatch` names the asset. Asset names are read in the core. Font assets and STEP import from the UI need the command. The core read removes the UI's scan of `.ptsm` text (`ui/src/files/assets.ts` and `ui/src/app/actions/document-assets.ts` read `referencedAssetNames` at 633eeb9). That scan is the one exception to the rule that the UI never parses `.ptsm`.
6. `FEATURE_DESCRIPTIONS`, `FIELD_HELP`, `START_VALUES` and the body-creating target rule move from UI tables into `FeatureManifest` and `FieldHint` before eight feature types arrive. New features then add no UI-only tables, and built-in features use only the seam a plugin will use. It changes the protocol schema and goes to review at the gate.
7. M1 sessions offer only `generic-fdm` and `generic-resin`, though the engine already takes `put_printer_profile` (checked in partsmith-protocol). Threads, tapped holes and their clearances read `printer.fit.*`. M2's parts fit only when the profile is the user's own printer. The web and desktop apps keep a profile library in the webview's IndexedDB, since the desktop webview reaches no path but picked files and assets (desktop.md 1.1). The CLI and Python put a profile. A document that names a custom profile carries a copy (format version 3). That settles ADR 0047 decision 2 (section 7.3 item 21). `EvaluationContext` gains a reason. `printer.nozzle` on a resin profile gets a specific message instead of "Unknown value".
8. The `cargo fuzz` targets run in a new job of their own in `nightly.yml`, with no skip rule, on a nightly toolchain pinned by date in delivery.md section 2.2's tool table. They start before M2 adds entity types, feature params and commands to both schemas. M2 also starts reading font and STEP files from other people's documents. The font reader and a `read_step` target through partsmith-occt-sys join the loader and the decoder. The `.scad` target follows its interpreter in M4.
9. The scripted-edit metric is the share of downstream references that still resolve to the correct element. Its v1 target is above 99 percent. Its oracle is written by hand: in the metric's spec, the test author writes with each model the expected element name of every downstream reference after each scripted edit, or "lost". The metric counts matches against those names. The stored baselines only track drift between runs. It runs over the examples, the four success parts and a corpus. The corpus starts at 100 project-written models. They are rebuilt on every merge against volume, area, bounding box and face count. Every M2 naming rule is measured as it lands. M3 and M4 grow the corpus to the 500 models and the held-out set of the launch.
10. The kernel facade has only extrude and revolve sweeps, fillet, chamfer, shell, booleans, transforms, split, section, primitives and STEP (partsmith-occt-sys at 633eeb9). The spikes measure an exact helix and a modeled thread on a cap, wrap emboss on a cylinder and a cone, a loft with rails, up-to-face and tapered prisms, the rib construction, and edge projection, section by the sketch plane and silhouette (OCCT's hidden-line code, named in risk 8 as growing the core). Each is measured for validity, time, native and WebAssembly parity and the linked web core's size while specs are cheap to change. The WebAssembly spike opened phase 0 the same way. No product code merges from a spike.
11. Technical design section 19 schedules a Pyodide prototype in phase 1. This plan reads phase 1 as M2 (section 7.2). A time-boxed spike measures cold load, memory, and a script that builds a box through the web core and reads its volume. It brings Pyodide's MPL-2.0 license to review. M4 then knows whether web scripting ships in v1.0 or v1.1.
12. Components change records, references and recompute. M2 writes eight new feature types. An ADR fixes how a record and a reference name their component scope before then. Those records stay valid when components arrive in M4, with no content-rewriting migration.
13. Owner work with no agent code runs in parallel with wave 1. The list is the one m1-gap-list.md keeps in its paragraph "What stays with the owner after wave G", read with delivery.md section 3.6's release checklist: branch protection on `main` that requires the CI checks, among them the six checks of the three jobs that M1's wave H moved into `ci.yml` (`OCCT (windows-2025)`, `OCCT (macos-15)`, `Rust tests (windows-2025)`, `Rust tests (macos-15)`, `End-to-end tests (firefox)` and `End-to-end tests (webkit)`, delivery.md 2.14 and 8), with the `v*` tag ruleset; the curl checks of the deployment; installing and launching each bundle of the release dry run (desktop.md section 6); the Visual C++ notice comparison; offline desktop builds from the archives; the web performance run on the reference laptop; the Chrome and Edge dialog check of ui.md open issue 39; the other checks by hand at the gate (the Firefox and Safari consoles of delivery.md open issue 19, the tab order of ui.md open issue 43 in Safari 17 and the macOS app, and Geist on Windows of ui.md open issue 33) and the visual baselines of ui.md 6.6; the trademark search; and the first tag. The first release dry run passed on 2026-11-07 (release.yml run 42342882329 on 633eeb9: all three bundles built, 22 min 17 s). Its bundles can be downloaded until 2026-11-14. A tag on a later commit needs a dry run of its own (the checklist's fourth step). The first tag must exist before M2's tag.
14. Ellipse, elliptical arc, parabola, hyperbola, rho conic and B-splines by control or fit points (with a periodic option) land in the solver, profiles, region matching, the kernel's profile curves and the drawing UI. M1's sketch has only point, line, circle and arc entities. The kernel's profile curves are line, arc and circle (partsmith-sketch `Geometry` and partsmith-occt-sys `PlanarCurve` at 633eeb9). Text glyphs, projected circles seen at an angle, loft profiles and the gear's involute need them. The UI draws text, spline and conic entities from display polylines that the core sends in `sketch_solved`, by an ADR that amends spec README decision D15 ("the protocol sends no tessellated sketch curves"). A spline would otherwise need a second de Boor in TypeScript beside section 7.3 item 10's. Text would otherwise need the font parser that ui.md section 1 keeps out of the UI.
15. Smooth (G2), B-spline knot and weight, arc length, angle of a line to an axis, block, symmetric curves, midpoint of an arc, Snell's law, and point-circle, circle-circle and line-line distances complete technical design section 7's constraint table while the solver is open. They also make splines fully constrainable. The explicit tangent-at-endpoint mode and fix with stored coordinates wait.
16. The owner kept the 18-pixel glyphs and labels for M1 and said they are revisited after M1 (ADR 0049 status). M2 adds about a dozen constraint glyphs. The 24-pixel targets are decided by a new ADR that amends ADR 0049 decision 3, before the overlay is laid out again (section 7.3 item 22).
17. Extrude gains up to a face, body or vertex, a start from an offset or a face, through all in both directions, and a taper angle. Revolve gains two sides, symmetric and up to a face. Fusion users pick these extents daily (user value 5). The extents keep bosses following upstream changes. The rib reuses the up-to-body extent (section 7.3 item 19). One spec round and one kernel path (up-to shapes) serve both features. Thin-wall revolve, other directions, body faces and mixed sketches wait.
18. A profile sweeps along a path of lines, arcs, splines or model edge chains, with guide rail, twist, scale and orientation modes and the new, join, cut and intersect operations. The coil builds on the sweep. Threads do not, unless wave 1's spike picks option (b) of section 7.3 item 15. The sweep starts in wave 2 with its orientation modes because the coil needs it. Its guide rail, twist and scale modes follow in wave 4, after the checkpoint, since none of gate 1's four parts uses them.
19. A helix or coil is set by pitch, turns, height and taper, with a profile from a sketch or a preset, around an axis given by M1's axis references (origin axes, straight edges, round faces). It is the path every thread is built on. It is made exact on the parameter plane of a cylinder or cone (section 7.3 item 15).
20. Threads are modeled by default, or cosmetic, external or internal. Their profiles are FDM-tuned: clearance from the profile's fit classes and truncated crests (technical design section 11). The threaded cap is a success-criteria part (technical design section 1). Modeled threads are the riskiest OCCT construction in v1. They come after the wave 1 spike and cancellation.
21. Tapped and threaded hole types get metric and unified size tables, and clearance holes get close, normal and loose fits (section 7.3 item 16). "M3 clearance" becomes a pick, not a lookup. The holes reuse the thread builder and its tables. Almost every bracket and enclosure has screw holes. Holes on curved faces and per-hole settings wait.
22. An Import command in the UI and `partsmith import` in the CLI bring in STEP over the engine's existing `import_step` and wave 1's asset command. `import_step` stores the file as an asset and adds one body and one import feature (checked in partsmith-protocol). STEP is the route for Fusion and Onshape models. In M1 only Python can import it. Meshes, `.scad`, `.FCStd`, DXF and SVG join the command as they land.
23. A command over the engine's existing `export_python` (checked in partsmith-protocol) lets a GUI user reach the success criterion that every GUI-built model exports to Python that rebuilds the identical shape. The gate checks it on the four parts.
24. The tools are 3-point and rounded rectangles, 2-point, 3-point and tangent circles, center and tangent arcs, the tangent-arc toggle, centerline and midpoint lines, regular polygons and the four slot types. They have user value 5 and are the first thing a Fusion user misses. They are built as core recipes over M1's entities and constraints (section 7.3 item 4). M1 keeps two copies of its recipes: `ui/src/sketch/recipes.ts` (line, two rectangles, circle, 3-point arc, point) and `python/partsmith/sketch.py` (`Rectangle`, `Polygon`). Both move onto the core in this item, spec first. The move deletes `recipes.ts` with `recipes.test.ts`, rewires Python's `Rectangle` and `Polygon`, and takes new entity and constraint ids from the session's generator instead of the UI's `IdSource`. That makes it feature work, not a cleanup pass (AGENTS.md Process).
25. Trim, extend, split, 2D fillet and chamfer, offset with a live distance, mirror, rectangular, circular and path patterns, and move, copy, rotate and scale are computed in partsmith-sketch. They are applied as edits with successions. References follow them (section 7.3 item 5). The enclosure lid's lip is an offset, and the gear's tooth ring is a circular sketch pattern. Modify tools make delete-and-redraw routine. The redrawn hole that M1 fills with only a `region_split` notice (features/extrude.md test 31, the example `extrude/region-by-outer-boundary` with the stored key `e-1,e-2,e-3,e-4;~e-6`) gets a succession rule in a new ADR that amends ADR 0022. That test and that example change by spec first (gate 5).
26. A sketch can project edges, faces and bodies, intersect a body with the sketch plane, project a silhouette, include geometry from another sketch, and break the link. Each link goes through naming (section 7.3 items 7 to 9). Technical design section 2 names projected geometry in v1 scope. Sketching on a face against its edges is everyday modeling. The lid lip and the emboss build on it. Sketches gain body reads in their dependencies.
27. TrueType text, straight or along a path, is usable as profiles. It has user value 5 and is the input to printed labels. Text uses the built-in font or a user font stored as a content-hashed asset (section 7.3 item 13). It needs this milestone's B-spline profile curves. A user font on the desktop needs `ttf` and `otf` in `ASSET_EXTENSIONS` (`desktop/src-tauri/src/files.rs`, `step` only in M1) and a font file kind for the pick dialog, by an amendment of ADR 0037. Labels on flat faces work by extruding text, and curved faces use emboss.
28. A rib or web thickens an open sketch profile up to the body, on wave 1's open profiles and the up-to-body extent (section 7.3 item 19). The ribbed bracket among the success-criteria parts needs it.
29. Thin-wall extrude makes an open or closed profile into a wall of a given thickness, inside, outside or both sides. It uses the same open-profile thickening as the rib. Thin-wall extrude is in the parity matrix. Thin-wall revolve is not. It waits for M3.
30. A loft runs between profiles with rails, a centerline, point ends and tangent or curvature end conditions, on this milestone's spline and conic profiles. It is built with OCCT's own loft and multi-section sweep (section 7.3 item 18) once wave 1's spike has settled rails, the hard case. None of gate 1's four parts uses a loft. All of loft heads the cut line (section 6 item 11).
31. Emboss raises or recesses text and profiles onto faces. It wraps exactly onto cylinders and cones (knobs, bottles, the threaded cap's side) and projects with a warning elsewhere (section 7.3 item 17). The design calls emboss critical for printed labels. It needs this milestone's text and projection. It reuses the threads' parameter-plane mapping. Emboss presets with stroke checks come with M3's print-aware presets.
32. Sweep, coil, thread, tapped holes, rib, thin wall, extents, loft and emboss get commands, inspectors and the new path, rail and section selection kinds. They are generated from each feature's params schema and manifest hints (item 6). Each feature's UI ships with the feature.
33. One API, two front ends: `Ellipse`, `Spline`, `Text`, `Slot`, `Polygon`, `Rectangle(rounded=)` and the other shapes, the modify operations with offset and grid, projection, the `+`, `-` and `&` part operators, hole and thread tables (`Hole.counterbore(M3)`), and a constructor for every new feature. Each has twins in the examples and the GUI to Python to `.ptsm` round trip (ADR 0048).

## 3. Waves

The waves run in order. Within a wave, items in different crates run in parallel. Each track writes its own examples, twins and corpus scenarios as it goes.

- Direct-generator names for edges and vertices (item 2), as additions and aliases
- Open-profile consumers and the region-union move (item 3)
- Cancellation (item 4): the hosts' flag, the desktop's cancel command and Stop, the web's SharedArrayBuffer word, and `not_run`
- Assets through the protocol (item 5)
- Feature help and start values in the manifests (item 6)
- Custom printer profiles in every host, with the reason channel for printer values (item 7)
- Fuzz targets for the loader, the decoder and `read_step` (item 8)
- The naming metric harness, corpus runner and baselines (item 9), with each model's expected names after each scripted edit written by the test author

- The Pyodide spike and its ADR (item 11)
- The components document-model ADR (item 12)
- The owner's tasks carried from M1 (item 13), in parallel

Why now: everything later reads these contracts. The solver step lands before new entities load the solver. Edge names land before paths and projections, and the open-profile API before its four consumers. Cancellation comes before slow features, the asset command before fonts and STEP import, manifest hints before eight feature types, and version 3 before any new record. Changing any of them after M2's features exist would mean redoing each feature. The spikes settle the riskiest kernel methods while specs are cheap to change. The guardrails measure every naming and schema change from the first one. The profile track is independent of the rest. It makes the thread chain's fit classes the user's own. The reviews these contracts need fall at the gate (AGENTS.md). Wave 1 writes them once, with their options.

- Sketch track: Python entities and constraints for the new types (item 33)
- Feature track: the kernel profile curves for item 14's conics and B-splines (`PlanarCurve` in partsmith-occt-sys), first
- Feature track: extrude extents, start options, taper and revolve options (item 17)
- Feature track: the sweep (item 18) along lines, arcs and model edge chains with its orientation modes, and its path selection kind
- Feature track: helix and coil (item 19), threads (item 20), and tapped holes with ISO and UNC tables and fit presets (item 21)

## 6. Risks

1. Modeled threads in OCCT: booleans of helical faces are slow. They can fail or leave seam faces that later booleans reject. That puts the threaded cap and its preview budget at risk. Mitigation: wave 1's spike compares the exact parameter-plane helix with ThruSections against a pipe-shell sweep on a corpus of thread sizes, before the spec. Cancellation lands first. Thread rows get budgets from measurement (ADR 0057). A cosmetic thread is the fix the failure message offers.
2. Emboss on curved faces is the second-hardest kernel piece: text mapped into a face's parameter plane, then thickened along its normals. Mitigation: exact wrap only on cylinders and cones, projection with a warning that names the distortion elsewhere, and the wave 1 spike.
3. Naming: the direct-generator rule (item 2) touches every edge. Sweeps, coils, threads, lofts, text, trims and projections add many generated names. Renaming would break M1 documents. Order-dependent `#n` names on helical faces can drift. Mitigation: that rule as additions and aliases only, and the naming metric from wave 1. At least 30 new reference stability scenarios, every M1 example and the 66 scenarios unchanged as a gate check, and review of each rule at the gate.
4. Projected geometry makes sketches read bodies. That can create cycles. It also changes the recompute graph. Mitigation: a sketch projects only the body states before it in the timeline (its writer chain). A cycle is an error with a fix. Projected results enter cache keys only through the body's provider key.
5. Pure-Rust curve geometry: partsmith-sketch has no kernel. Spline and conic intersections, trims, offsets and the planar arrangement are new numeric code with tangent and overlap cases. Offsets of non-circular curves can only be approximations. Mitigation: every tolerance is stated in sketch.md before code. Property tests run on random curve sets. Offsets are checked against their stated tolerance. Glyph regions stay out of the arrangement.
6. Solver load and results: B-splines with many control points and conics add nonlinear parameters. The 4 ms drag median, the 16 ms frame and 1e-9 parity may not all hold. Option (d) also changes iteration paths. Some example results may shift. Mitigation: option (d) lands first. The examples are re-blessed once after the libm perturbation check, with an ADR. Property tests grow with each entity. The drag rows are measured in wave 2.
7. Native and WebAssembly parity: B-spline interpolation, ThruSections and pipe-shell approximations iterate to tolerances. FMA or libm differences can push a result across one. Mitigation: exact constructions are preferred. ADR 0042's 1e-9 comparison and the perturbation check run on every new example.
8. Web core size: 18.8 MiB on 2026-10-23 against the 25 MiB per-file limit. New OCCT code paths (form features, offsets, hidden lines for silhouettes), the font parser, the built-in font and a larger sketch crate add to it. Mitigation: every wave 1 spike measures the linked core's size. `check:dist` runs on every kernel PR. delivery.md section 3.5's plan starts with an ADR if it fails.
9. Web cancellation must reach a worker blocked inside one synchronous call, where no message arrives and a recompute is one `ps_call`. It has to do that with no new `unsafe` outside partsmith-occt-sys, no fourth C ABI export and no core global state. The route is a SharedArrayBuffer word that partsmith-occt-sys reads through an Emscripten JS import. It needs no shared memory in the core. If that route fails review, a web cancel restarts the worker as in M1 and loses the undo history, by an ADR settled under the owner's rule. The desktop still cancels through its host command (gate 11). Only some OCCT algorithms poll progress. The spec lists which calls can be interrupted.
10. Review timing: AGENTS.md puts the reviews of format version 3, the protocol additions, the naming rules and the new dependencies at the gate. A rejection there means rework. Mitigation: wave 1 writes every ADR with its options. The owner's rule settles each choice. No track waits. The owner may review the wave 1 set early.
11. Scope: M2 holds seven XL items. If the checkpoint after wave 2 shows an overrun of more than 25 percent, work is cut in this order: all of loft, then sweep's rail, twist and scale modes (none of gate 1's four parts uses either), then parabola, hyperbola and rho conics, then Snell's law, block and knot and weight constraints, then text along a path, then revolve options. Each cut moves to M3 by an ADR, never by weakening a test. The ADR adds its item to the exceptions of gates 2 and 3. Threads, tapped holes, splines, projection, text and emboss stay: the four success parts need them.
12. Performance: threads, text and patterned teeth multiply faces. More faces slow booleans (about 200 ms already on the 194-hole plate), tessellation and print analysis. `bench50` does not cover them. The owner recorded kept-face fingerprint reuse as later work on 2026-11-05. Mitigation: budget rows for every new operation. If a row or `bench50` fails, that reuse is the first remedy and moves into M2 by an ADR settled under the owner's rule (gate 19).
13. Fonts and untrusted files: user fonts and STEP files travel in shared documents. Parsing them is attack surface. The font reader and `read_step` fuzz targets cover them (gate 15). A user font's license is the user's responsibility. The built-in font is OFL 1.1.
14. The success criteria stay partly open after M2. A 50-feature rebuild under 1 s needs M4's speed work (the budget is 1.8 s). The Fusion-time comparison is recorded, not claimed. The gate must not report either as met.
15. The physical prints and the Fusion user's timed sessions need the owner's printers, the owner's time and a Fusion user. M2 asks for one FDM and one resin printer, as technical design section 16 does.
16. Balance of M3 and M4: as routed, each holds more than an M1-sized milestone, M4 most. The plan re-sizes both at the M2 gate from M2's measured pace, against the sizes of sections 2, 5.1 and 5.2. That re-size also decides whether long-tail parity moves to v1.1 (technical design section 19's mitigation), under the owner's rule, in an ADR on gate 19's review list.
17. Docs that overstate M1: architecture.md says the kernel facade covers sweep, loft and draft. It also lists ellipse, elliptical arc and B-spline entities. At 633eeb9 the facade has only extrude and revolve sweeps and no draft. Sketch geometry is point, line, circle and arc. Kernel profile curves are line, arc and circle. Agents planning from the doc alone would assume work that does not exist. Wave 1's records correct it.
18. Web STEP import and user fonts need the document's folder (ui.md open issue 37) until `.ptsz` bundles arrive in M4. The built-in font keeps default text free of it. Item 5's asset command keeps the undo history when the folder is chosen.
19. The Pyodide spike may show that web scripting has to wait for v1.1 (technical design section 19 allows it). Pyodide's MPL-2.0 license needs the owner's review. The spike merges no product code. Either answer changes only M4's plan.

## 7. Choices

### 7.1 Judge's record

This is a record, not an owner-rule choice. Three proposals were scored out of 5 on five axes. Higher is better on every axis.

| Proposal | User value | Dependency order | Risk | Gate coherence | Fit with the design and M3, M4 | Total |
| --- | --- | --- | --- | --- | --- | --- |
| Everyday printable parts | 5 | 3 | 2 | 4 | 3 | 17 |
| Curves, paths and threads | 4 | 5 | 4 | 5 | 4 | 22 |
| Sketcher parity and the loop to your printer | 4 | 4 | 3 | 4 | 4 | 19 |

- Everyday printable parts had the most user value. It also had about 45 items in every crate, with three slicer formats and detection on three operating systems. Its text was built on B-spline profile curves with no spline entities. Its threads were built on a helical sweep with no sweep feature. Its projection was limited to lines and arcs. It left the gear to M3.
- Curves, paths and threads put contracts before consumers and kernel spikes before specs. Its gate was the four success-criteria parts. It had the naming metric from wave 1. Its threads read only generic fit classes. It scheduled kept-face fingerprint reuse. The owner had recorded that as later work on 2026-11-05. Its default font, Geist, ships only as the UI's variable WOFF2 (`ui/public/fonts`), a format ttf-parser does not read.
- Sketcher parity and the loop to your printer had the clearest route through M3 and M4 and a section 7 coverage gate. It moved the riskiest kernel work (threads) to M3 and left only three success parts. Its CC0 corpus option breaks ADR 0028's single license.

This plan starts from Curves, paths and threads. From the first proposal it takes custom printer profiles in every host, the reason channel, extrude extents, the replayable solver seeds, six newcomer errors, Liberation Sans and the text profile rule, cancel ceilings, and a Fusion user (not the owner) at the timed check. From the third it takes section 7 coverage, the 100-model corpus, projected geometry with a stored fallback, additive protocol changes, a Pyodide spike that never merges, STEP import in the UI and the milestone split.

These facts were checked against the code at 633eeb9 before the plan relied on them:

- 20 built-in feature types
- sketch entities point, line, circle and arc
- kernel profile curves line, arc and circle
- no sweep, loft or draft in the kernel facade
- Measure takes exactly one target
- Export already takes bodies, a tolerance and per-body STL
- `ImportStep`, `ExportPython`, `PutPrinterProfile` and `SetTessellation` exist
- recipes are duplicated in `ui/src/sketch/recipes.ts` and `python/partsmith/sketch.py`
- 3MF leaves modifier bodies out with `modifier_omitted`
- the engine ships only the overhang overlay
- the engine never sets recompute's `CancelToken`

### 7.2 Planner's recommendations

Two planning choices rest on the planner's recommendation alone. The M2 gate re-sizes M3 and M4 (section 6 item 16).

1. Milestone split for v1.0. M2 is this plan. M3, "From model to printer", holds slicer handoff with per-slicer metadata, export-as and slots, multi-plate and watch mode; saved orientation and auto-orient; print-aware presets with quick selections; new checks with background analysis; resin tools; split with connectors and one-click suggestions; profile import and the calibration print; two-target measure and mass; on-canvas handles; datum geometry and the fillet, chamfer, shell, draft, pattern, split, scale, move and primitive options; and the canvas image, DXF and SVG. M3's gate prints the four parts through Send to slicer and starts the monthly print cadence. M4, "v1.0", holds components, joints and assembly checks, the code workflow and `.scad` import, mesh bodies and the other imports, surfaces, direct edits and derive, `.ptsz` and the git tools, the disk cache and speed work, release hardening and onboarding. Its gate is all four v1 success criteria. Options considered: print-aware features first (blocked: threads need a helix, and presets need the sketch tools every part starts from) and assemblies first (few users reach them first). Why this order: dependencies (splines, edge names, open profiles, projection and cancellation feed every later feature) and the success criteria (the four parts become buildable in M2).
2. Reading of the phases. Technical design section 18's four phases are read as M1 to M4. Section 19's "prototype in phase 1" then places the Pyodide spike in M2.

### 7.3 Choices under the owner's rule

1. One format version for M2. Accepted (owner's rule of 2026-11-05).
   - Options: (a) one bump to format version 3 for every M2 record shape (conic, spline, text and projected sketch entities, embedded printer profiles, new feature records), declared in wave 1 with a migration from 2 that changes only the version, frozen at the gate; (b) a bump per track; (c) optional fields with no bump
   - Picked: (a)
   - Safest: an M1 build refuses a version 3 file with `NewerFormatVersion` before it can drop a spline entity or an embedded profile on save (file-format.md section 3.9).
   - Industry standard: versioned schemas with forward migrations, the path ADR 0025 took for version 2. It also needs one review instead of several.
2. Protocol additions. Accepted (owner's rule of 2026-11-05).
   - Options: (a) new optional fields, types and commands with `PROTOCOL_VERSION` staying 1, as ADR 0024 did; (b) a version bump
   - Picked: (a)
   - Safest: M1 hosts keep working.
   - Industry standard: additive schema evolution. The schema change still goes to review at the gate.
3. Direct-generator edge names (item 2) and M1 documents. Accepted (owner's rule of 2026-11-05).
   - Options: (a) rename every edge after its direct generator, with a migration that rewrites stored references; (b) give direct-generator names only to edges and vertices that M1 leaves unnamed or names in a weaker form, add aliases where both forms exist, and never rename an element M1 names; (c) per-feature edge names with no general rule
   - Picked: (b)
   - Safest: every M1 reference resolves unchanged. No migration rewrites content. It reuses the alias mechanism that merged faces already use.
4. Drawing tools. Accepted (owner's rule of 2026-11-05).
   - Options: (a) TypeScript recipes, the way M1 builds its rectangles in `ui/src/sketch/recipes.ts`; (b) recipes in partsmith-sketch that emit M1-style entities and constraints as edits, reached by the UI through the protocol and by Python directly; (c) new entity types such as slot, polygon and rounded rectangle
   - Picked: (b)
   - Industry standard: Fusion and FreeCAD store these shapes as plain curves with constraints, with no record type of their own.
   - Safest: the solver, profiles, naming and region matching see only entities they handle. The UI keeps to the protocol. Option (b) ends M1's two copies (the UI's recipes and Python's `Rectangle` and `Polygon`). They move onto the core with the drawing tools (item 24) in wave 3, spec first. sketch.md 1.2 is updated to match. The move deletes `recipes.test.ts` and changes where new ids come from. A cleanup pass may not do that.
5. Modify tools. Accepted (owner's rule of 2026-11-05).
   - Options: (a) trims, offsets and fillets computed in the UI; (b) core operations in partsmith-sketch behind protocol commands that return edits, where trimmed or split pieces get new ids and successions (ADR 0022)
   - Picked: (b)
   - Safest: it keeps the UI to the protocol. Successions let regions and faces follow a trim. One implementation serves the UI and Python.
6. A redrawn hole (item 25). Accepted (owner's rule of 2026-11-05).
   - Options: (a) when new entities replace a hole's loop where it was, the hole's region follows them as a succession, built with a notice and Keep this match (ADR 0022, ADR 0024); (b) M1's behavior, where the redrawn disc fills the hole and the extrude reports it only in a notice
   - Picked: (a), in a new ADR that amends ADR 0022, with the modify tools' successions. features/extrude.md test 31 and the example `extrude/region-by-outer-boundary` are changed by spec first. The owner signed off M1's behavior with ADR 0022 on 2026-11-04 (features.md open issue 10, which names a succession for hole loops as the later fix). The new ADR goes to review at the gate (section 4 item 19).
   - Safest: the user's intent is kept and stated, as for M1's replaced lines. It keeps to technical design section 1's goal that upstream edits do not silently break downstream features.
7. Storing projected geometry. Accepted (owner's rule of 2026-11-05).
   - Options: (a) store only the source reference and project on every build; (b) store the reference (query and fingerprint, ADR 0021) plus the coordinates the projection edit saw and project live on every build; when the source is lost, project it as it was just before the feature that removed it, moved with the body since, read from the body's writer chain in the same run, and use the stored coordinates only when that fails too, each reported as a loss with its ghost; (c) store coordinates and refresh them in the document
   - Picked: (b)
   - Safest: a sketch whose source is lost still opens and solves, in the order ADR 0023 gives a face sketch: the live source, then the source as it was just before the feature that removed it (`face_placement_before_removal`), then the stored fallback. The loss is reported, never hidden. Only the projection edit and Break link write the document, never recompute. Saves stay byte-identical, unlike with (c).
   - Industry standard: Fusion's projected curves and FreeCAD's external geometry stay linked to their source. Break link is an edit that writes plain entities.
8. Which body state a sketch projects. Accepted (owner's rule of 2026-11-05).
   - Options: (a) the body as it is just before the sketch in the timeline, from its writer chain; (b) the body's latest state
   - Picked: (a)
   - Safest: no cycles. The result depends only on what comes before the sketch, as with M1's face sketches.
   - Industry standard: Fusion and FreeCAD project the model at the sketch's place in the history.
9. Model edges as snap and dimension targets (item 26). Accepted (owner's rule of 2026-11-05).
   - Options: (a) snapping or dimensioning to a model edge makes a linked projected entity that the constraint uses; (b) the snap copies the position with no link
   - Picked: (a)
   - Safest: the dimension follows upstream edits and reports a loss like any other reference.
   - Industry standard: Fusion projects the model geometry that a sketch dimension or constraint picks.
10. Curve math in partsmith-sketch. Accepted (owner's rule of 2026-11-05).

    - Picked: (a)
    - Why: no new dependency, the textbook algorithm, and the same libm rules as the rest of the native solver for native and WebAssembly parity (ADR 0004, ADR 0015). The kernel side uses OCCT's `Geom_BSplineCurve`.
11. Exact curves and offsets. Accepted (owner's rule of 2026-11-05).

    - Picked: (a)

    - Picked: (a), confirmed or replaced by wave 1's spike on a corpus of thread sizes, with the result in kernel.md and an ADR

    - Picked: (a), confirmed by wave 1's spike for rails and end conditions, the hard cases

    - Picked: (b), unless wave 1's spike shows cases that (a) builds and (b) cannot
    - Safest: one construction path that the extents already test, with extrude's naming rules for its side faces. It is also less code (engineering principle 5).
20. Cancellation. Accepted (owner's rule of 2026-11-05).

    - Picked: (a), with (b) as the web fallback by an ADR settled under the owner's rule (section 4 item 11)
    - Industry standard: OCCT's own interruption API. SharedArrayBuffer with Atomics is the standard way to signal a busy worker. The deployment's cross-origin isolation headers allow it.
    - Safest: the undo history is kept, `unsafe` stays in occt-sys and ADR 0010's three exports (no fourth export), the core needs no shared memory, and the core holds no global state. A cancel command in the protocol could not reach a running call: the worker handles no message during `ps_call`, and the desktop's call holds the `Session` mutex (desktop.md open issue 9).

    - Picked: (b), (c) and (d) together. Built-in profiles stay referenced by id. Any other profile is embedded, in print.md's written form, in the document that names it. The web and desktop apps keep the library in the webview's IndexedDB, since the desktop webview reaches no path but picked files and assets (desktop.md 1.1). The document's copy changes only through an edit (picking the profile again), never by recompute.
    - Safest: a shared document rebuilds with the same `printer.*` values everywhere. That removes print.md open issue 6's silent fallback.
    - Industry standard: slicers keep user presets in a config folder and write printer settings into their 3MF projects.

## 8. How the work runs

M2 runs the way M1's waves did. Each item goes through the same steps. A wave lands on `main` once all of its items have gone through them:

1. Spec. The behavior is written first in `docs/spec/<area>.md`, or in `docs/spec/features/<type>.md` for a feature type, with its acceptance tests, tolerances and messages. The spec author checks every claim about the code against the repository. A critic reviews the text. Each choice the spec meets gets an ADR with its options, settled by the owner's rule. Changes to the file format, the protocol schema, the naming algorithm, licenses or dependencies are marked for human review at the gate (AGENTS.md Process). The spec merges before any code.
2. Tests. A test author turns the spec into failing tests without seeing an implementation: acceptance tests in the crate's `tests/` directory, unit tests, examples with Python twins and expected results, corpus scenarios and E-tests. Implementers do not weaken them.
3. Code. An implementer works the item until its tests pass, in one crate where it can. Tracks that each own their crates run in parallel, as wave 2's three tracks do. A crate or folder that several tracks edit takes one track's pull request at a time.
4. Review. A reviewer with a fresh context checks the change against the spec, the ADRs and the invariants. The reviewer runs the examples and the corpora and looks at screenshots of UI changes.
5. Fixes. A fixer verifies each finding, fixes the real ones with a regression test and records why the others do not hold.
6. Cleanup. Each wave ends with a cleanup pass over its changes: the code smells that AGENTS.md's Process section lists are refactored with no change in behavior. Tests, example results and generated schemas stay identical, and benchmarks do not get slower. Wave 5's milestone cleanup pass covers all of M2.
7. Merge. A prose pass checks the wave's docs against the writing guide. The wave's branch gets a CI run. Verify-main then checks the result as it will land on `main`. `main` moves only after both pass. CI runs again on `main`, the platforms and nightly workflows run on the new head, and the owner gets a report. Note (2026-11-07, owner's rule of 2026-11-05 and the owner's direction to merge after each feature): wave 1's code lands one track at a time. Each track lands on `main` once its gate and verify-main pass. The track's gate checks its docs against the writing guide. The branch CI run is left out. CI on `main` runs the other platforms. Its deploy job needs every other job. A failure there never reaches production. A red CI run on `main` is fixed before the next track lands.

M2 keeps M1's workflows and adds two checks to them in wave 1. `ci.yml` runs on every push to `main` and every pull request: fmt, clippy with `-D warnings`, the workspace tests, the schema drift check, the examples, pytest, `pnpm` lint, typecheck and test, the notices and license checks, e2e with the `@engines` subset in Firefox and WebKit, the Windows and macOS rows, and the deployment. `platforms.yml` runs weekly or on dispatch and times `bench50` on `macos-15`. `nightly.yml` runs the sketch property tests every day. In wave 1, M2 adds the fuzz targets to `nightly.yml` as a new job of their own with no skip rule, on a nightly toolchain pinned by date in delivery.md section 2.2's tool table. Wave 1 also adds the corpus runner with the naming metric to the checks of every merge.

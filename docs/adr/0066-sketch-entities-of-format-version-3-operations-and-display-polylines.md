# 0066: Sketch entities of format version 3, sketch operations in the core and display polylines

Status: Accepted (owner's rule of 2026-11-05): the contracts that the M2 plan's items 14, 24 to 27 and 32 build on, with the plan's choices 1, 2, 4, 5 and 7 to 14 as the plan settled them, and the choices below. It builds nothing in wave 1. It changes the file format: the sketch entity records, the `link` member and the point roles of format version 3 ([ADR 0061](0061-format-version-3-for-the-records-of-m2.md)). It changes the protocol schema: the entity kinds and roles that reach it through `SketchParams` and `SketchSolution`, three display buffers of `SketchDisplay`, commands 39 to 41, the error code `sketch_operation_failed` and five selection kinds. It amends spec README decision D15. It adds a dependency and a license: ttf-parser 0.25.1 (MIT OR Apache-2.0) and the Liberation Sans Regular font (SIL Open Font License 1.1). All of them go to human review at the M2 gate (AGENTS.md Process, m2-plan.md gate 19). The naming rules of projected geometry and of faces made from text are not decided here: items 26 and 27 bring them to naming.md, for the same review. `PROTOCOL_VERSION` stays 1 (ADR 0024's additive rule).

## Context

- **M1's entities.** `Geometry` in `crates/partsmith-sketch/src/entity.rs` has four variants: `Point`, `Line`, `Circle` and `Arc`, tagged `type` with `deny_unknown_fields`. `PointRole` in `src/point_ref.rs` has `Point`, `Start`, `End` and `Center`, and the `PointRef` pattern of the schema allows only `start`, `end` and `center`. The kernel's profile curves are line, arc and circle (`PlanarCurve` in partsmith-occt-sys). sketch.md section 1.2 lists the conics, the B-splines, text and projected geometry as later work.
- **The plan's settled choices.** Choice 1 puts every M2 record into format version 3. Choice 2 makes the protocol additions additive. Choice 4 builds the drawing tools as recipes in partsmith-sketch that emit M1-style entities and constraints. Choice 5 builds the modify tools as operations in partsmith-sketch behind commands that return edits. Choices 7 to 9 store projected geometry as a reference plus the coordinates the projection edit saw, project the body state just before the sketch, and make a snap to a model edge a linked entity. Choices 10 and 11 evaluate curves in house and keep them exact in OCCT. Choices 12 to 14 read fonts with ttf-parser, build Liberation Sans into the core, store user fonts as assets and use a text entity whole.
- **Recipes live in two copies.** `ui/src/sketch/recipes.ts` holds `lineRecipe`, `rectangleTwoPointRecipe`, `rectangleCenterRecipe`, `circleRecipe`, `arcThreePointRecipe` and `pointRecipe`, with ids from the UI's `IdSource`. `python/partsmith/sketch.py` holds `Rectangle` and `Polygon`. Item 24 moves both onto the core.
- **The UI draws curves from entities.** Decision D15 reads "the protocol sends no tessellated sketch curves, and the UI draws curves from the entities". ui.md section 3.16.2 has the UI tessellate circles and arcs at 0.25 CSS pixels. `SketchDisplay` in `crates/partsmith-protocol/src/solution.rs` carries three region fill buffers. ui.md section 1 says the UI never evaluates geometry. It reads no font. A spline drawn by the UI would need a second de Boor in TypeScript.
- **Selection kinds.** `SelectionKind` in partsmith-model has eight values (model.md section 2.12). Sweep paths, ribs, thin walls, loft rails and sections, and text profiles have none.
- **Components.** [ADR 0069](0069-component-scopes-by-containment-and-occurrence-paths.md) requires every new reference to name its target by id or element reference, never by position, and to sit beside a `body` field when it names a face, edge or vertex.

## Decision

1. **Entity records** (sketch.md sections 2.12 and 3.20). Format version 3 adds nine entity types after `arc`: `ellipse` (`center`, `major`, `minor_radius`), `elliptical_arc` (the same, then `start_angle`, `end_angle`), `parabola` (`vertex`, `focus`, `start_parameter`, `end_parameter`), `hyperbola` (`center`, `major`, `minor_radius`, `start_parameter`, `end_parameter`), `conic` (`start`, `control`, `end`, `rho`), `bspline` (`degree`, `poles` as point entity ids, `weights`, `knots`, `periodic`), `fit_spline` (`points` as point entity ids, `periodic`), `fixed_spline` (`degree`, `poles` as coordinates, `weights`, `knots`, `periodic`) and `text` (`text`, `font`, `size`, `path`, `horizontal_alignment`, `vertical_alignment`). Every stored field is user data. A fit spline's control points and knots, a conic's B-spline form, glyph outlines, display polylines and the live geometry of a link are derived and never stored.
2. **Point roles.** `vertex` and `focus` (a parabola's) and `control` (a conic's) follow `center` in `PointRole`. The `PointRef` pattern gains them.
3. **Linked entities.** An entity of an ordinary kind gains the optional member `link`, after its geometry and before `construction`. Its kinds are `edge`, `vertex`, `section` and `silhouette`, each with `body` and a naming `Reference`, and `sketch`, with `feature` and `entity`. The geometry fields hold the coordinates the projection edit saw. The build replaces them with the live projection of the body state just before the sketch, and never writes it. The engine's sketch solves and drags use the live geometry of the latest recompute in the same way. A drag commit and every tool's edit keep the stored fields and the `link` as stored. A linked entity is fixed in the solver. Only the projection command and Break link write a link or its coordinates.
4. **Text.** A text entity stores its string, its font (an asset name or a built-in name), its size as a length expression (the font's em size), the id of the curve it runs along, and two alignments. It stores no glyph index. A feature uses it whole, by its id. Its glyph regions never enter the sketch's arrangement.
5. **Recipes and operations in the core** (sketch.md section 2.13). `apply_recipe` and `apply_operation` return a `SketchChange`: the changed params and the ids the change added. New ids come from the caller's generator. Item 24 defines the recipes, item 25 the operations and item 26 Break link.
6. **Protocol commands** (protocol.md section 2.5). Command 39, `sketch_recipe`, command 40, `sketch_modify`, and command 41, `sketch_project`, each return `{change: SketchChange}` and record nothing. The host stores the change with one `update_feature` edit. The error code `sketch_operation_failed` carries the sketch crate's message for input a tool cannot use.
7. **Display polylines** (sketch.md section 3.20.9, protocol.md section 2.6). `SketchDisplay` gains `curve_positions` (`f32`, 2 per vertex), `curve_starts` (`u32`, 1 per polyline) and `curve_ids` (`u32`, 1 per polyline, an index into the solution's `entities`). They hold a polyline for every entity whose kind is not point, line, circle or arc, text included. A closed polyline repeats its first vertex at its end. Every vertex lies on the curve. The curve stays within 0.01 mm of each segment, and its tangent turns at most 5 degrees along it.
8. **D15 amended.** The UI draws points, lines, circles and arcs from the entities, as before. It draws every other kind from the display polylines. Nothing stores a polyline or refers to a vertex of one.
9. **Selection kinds** (model.md section 2.12). `SelectionKind` gains `sketch_chain`, `sketch_text`, `path`, `rail` and `section`. The spec of the first feature that uses each fills in its value and the UI's rule.
10. **Font dependencies.** ttf-parser 0.25.1 joins partsmith-sketch with `default-features = false` and the feature `std` in item 27. Its only non-dev dependency, `core_maths`, is optional and stays off. The built-in font is the regular face of Liberation Sans from a 2.x release of the Liberation Fonts, embedded unmodified in partsmith-sketch, with its SIL Open Font License 1.1 text in the notices. Its name fixes its bytes. Item 27 records the release and the file's SHA-256. Item 27 adds the feature `opentype-layout` if its kerning rule reads the GPOS table, and records that in this ADR for the same review.
11. **What lands when.** Item 14 (wave 2) builds the curve kinds, their roles, profiles, chains, display polylines and the `curve_*` buffers. Item 24 (wave 3) builds the recipes and command 39, item 25 (wave 3) the operations and command 40, item 26 (wave 3) the links and command 41, and item 27 (wave 3) the text and its dependencies. Each item's spec step fills in the behavior these sections leave to it, before its code.

## Alternatives considered

The plan settled choices 1, 2, 4, 5 and 7 to 14. This record does not reopen them. The choices below are each Accepted (owner's rule of 2026-11-05): the most open-source approach, then the safest, then the industry standard, then this work's recommendation. Every option is equally open, plain JSON in a format under Apache-2.0, unless a choice says otherwise.

1. *How an ellipse is stored.* (i) Its center, the vector of its major semi-axis and its minor radius; (ii) its center, two radii and the angle of the major axis, as FreeCAD stores it; (iii) its center and two points. The rule takes (i), the safest. Each stored number is one solver parameter, as a line's points are. No angle enters the rows, and no angle wraps. It has 5 degrees of freedom like (ii). OCCT builds the exact ellipse from the same data. Elliptical arcs, hyperbolas and parabolas follow the same form, with a parabola stored by its vertex and focus.
2. *How a B-spline's control points are stored.* (i) As point entities of the sketch, named by id in order, as Fusion's control point spline holds sketch points; (ii) as coordinates in the record, addressed by their position for constraints, as FreeCAD's internal geometry does; (iii) as coordinates no constraint can address. The rule takes (i), the safest. A constraint on a control point names a point entity. Inserting a knot adds a point and shifts nothing that a constraint names, where under (ii) every constraint after it would silently name another pole. The same holds for fit points. A spline that the solver must not move needs (iii), since a projected spline's control point count can change in a build that writes nothing. That is the `fixed_spline`, as Fusion's fixed spline is the result of projection, intersection and import.
3. *The degree of a fit spline.* (i) Cubic, not stored; (ii) a stored degree. The rule takes (i), the industry standard: Fusion's and FreeCAD's fit point splines are cubic. A degree can follow later as an optional key that keeps this meaning when absent.
4. *Rho, weights and knots.* (i) Stored constants of the solve; (ii) solver parameters. The rule takes (i), the safest. No constraint of M2's wave 2 sets them. As parameters they would leave every such curve under-constrained, and the degrees of freedom the UI shows would mean nothing. Item 15's spec decides whether its weight and knot constraints make them parameters.
5. *How a projected entity is stored.* (i) An ordinary entity with a `link` member; (ii) an entity type `projected` that wraps its geometry. The rule takes (i), the safest. Constraints, profiles, chains, messages and naming see only the kinds they already handle. Break link removes one member. It is also the most open-source form and the industry standard: FreeCAD's external geometry and Fusion's projected curves are ordinary curves that carry a reference to their source.
6. *What a section or silhouette curve names.* (i) The face, or the edge or face, that makes the curve, as a naming reference; (ii) the body with the position of the curve in the kernel's result. The rule takes (i). Option (ii) is an index-based reference, which the invariants forbid.
7. *What an included entity names.* (i) The other sketch's feature id and entity id, with the stored geometry describing the source for repairs and ghosts; (ii) the same ids with a fingerprint text of their own. The rule takes (i), the recommendation. Entity ids are permanent and never reused (model.md section 3.1). A fingerprint would have no choice to confirm. The stored geometry already says what the source was. Less is more (engineering principle 5).
8. *How a text is placed.* (i) Along a curve entity of the sketch, a construction line for straight text; (ii) at a stored position with a stored angle; (iii) at a point entity with a stored angle. The rule takes (i), the safest. Straight text and text along a path are one record. Horizontal, angle and distance constraints on the line place and turn the text. No new point role and no angle parameter are needed. Fusion's text along a path takes a curve the same way.
9. *What a text's size measures.* (i) The font's em size; (ii) the height of its capitals; (iii) OpenSCAD's size rule. The rule takes (i), the industry standard: a font's point size and CSS's `font-size` are the em size. It is exact for every font from one header value. Capitals of Liberation Sans are about 0.69 times the size. M4's `.scad` import converts OpenSCAD's rule to it.
10. *Whether a text's size is an expression.* (i) A length expression evaluated like a driving dimension; (ii) a number set by a new dimension. The rule takes (i), the recommendation: a label follows a parameter as every dimension does, with no new constraint type.
11. *Where the font reader lives.* (i) In partsmith-sketch, which owns text entities, their outlines and their display polylines; (ii) in a new crate; (iii) in partsmith-features. The rule takes (i), the recommendation. The crate is pure Rust and builds on every target. The engine and the features already call it. A new crate would add a boundary for one function. The features have no display role.
12. *How the font is bundled.* (i) The font file as released, unmodified; (ii) a subset of its glyphs. The rule takes (i), the safest. The SIL Open Font License 1.1 lets a font be bundled and embedded in software. It forbids a modified version from using a Reserved Font Name. An unmodified file keeps its name and its bytes, which the built-in name fixes. The file adds about 0.4 MiB to the web core, which risk 8 tracks.
13. *How display polylines travel.* (i) As `f32` buffers in `SketchDisplay`, like the region fills; (ii) as JSON arrays in each solved entity. The rule takes (i), the safest for the 16 ms frame budget. A 40-glyph text has thousands of vertices on every drag frame. As JSON numbers they would weigh several times their 8 bytes each, and they would reach the sessions that have display off.
14. *Which kinds get polylines.* (i) Every kind but point, line, circle and arc; (ii) text and splines only. The rule takes (i), the recommendation. The UI keeps one path for the curves M1 did not have, with no conic formulas in TypeScript. The M1 kinds keep the UI's own tessellation, which follows the zoom.
15. *How fine a polyline is.* (i) Fixed bounds in sketch units: 0.01 mm from the curve and 5 degrees of turn per segment; (ii) a tolerance the host sends with the zoom. The rule takes (i), the safest. The core does not know the zoom, and the same sketch gives the same polylines in every session. 0.01 mm is half a pixel in a 20 mm wide view on a 1000-pixel screen. The turn bound keeps small glyphs round when zoomed in.
16. *What the recipe and modify commands do.* (i) Return the changed params, which the host stores with an `update_feature` edit; (ii) apply the edit themselves with a label. The rule takes (i), the safest. Previews, transactions, undo labels and the mutation queue stay on the host's one path, as `solve_sketch` with a candidate does. A tool can chain several steps on a candidate before anything is stored.
17. *The new point roles' names.* (i) `vertex`, `focus` and `control`; (ii) `center` for a parabola's vertex, as FreeCAD's position names do. The rule takes (i), the recommendation: names are words that say what they are (AGENTS.md code style).
18. *The selection kinds' names.* (i) `sketch_chain`, `sketch_text`, `path`, `rail` and `section`, fixed now with the features that fill them in named; (ii) each kind named by the feature that first needs it. The rule takes (i), the safest. The protocol schema gains them once, in the wave 1 review. Item 32 names `path`, `rail` and `section` in the plan.

## Consequences

- Specs: sketch.md sections 1.2, 1.3, 2.4, 2.12, 2.13, 3.20, 3.21 and 4.1, tests 303 to 335 and 339 to 341 and open issues 25 and 26; protocol.md sections 1, 2.5 (commands 39 to 41), 2.6, 2.9 and 4, tests 114 to 121 and 123 and open issue 10; file-format.md section 3.9's version 3 row; model.md section 2.12 and tests 113 and 114; engine.md sections 1, 3.22 (the nouns of the five selection kinds), 3.27 and 4 (`SketchOperationFailed`) and tests 226 to 230 and 234 to 236; ui.md sections 2.7, 2.12, 3.7 (the placeholders of the five selection kinds) and 3.16.2 and test U-290; python-api.md section 1; the spec README's decision D15 and its index row for sketch.md.
- No code changes in wave 1, and no example result, generated schema or acceptance test of M1 changes. Each item's code changes `docs/format/ptsm.schema.json` and `docs/format/protocol.schema.json` when it lands. sketch.md test 15 and protocol.md tests 34 and 71 then take the names that item adds, in that item's spec step.
- A version 3 document with these records cannot open in an M1 build, which refuses it with `NewerFormatVersion` (file-format.md section 3.9). A version 2 document holds none of them.
- The web core grows by the font file and ttf-parser in wave 3. `check:dist` and delivery.md section 3.5 record the size. The font reader gets its fuzz target with item 8 in wave 3.
- `pnpm -C ui notices` lists ttf-parser and the font's license when item 27 adds them. cargo-deny already allows MIT and Apache-2.0. The OFL text is a data file's license, which the notices generator must read from the font's folder.
- Naming: a face made from a projected entity is named after the entity id like any other. The names of faces made from text must not index glyphs or characters (m2-plan.md gate 4). Items 26 and 27 bring both rules to naming.md for review at the gate.
- This changes the file format, the protocol schema, a dependency and a license. It goes to human review at the M2 gate with format version 3.

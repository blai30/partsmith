# 0065: Feature help, start values and new-body fields in the manifests

Status: Accepted (owner's rule of 2026-11-05): the M2 plan's item 6 and the choices below. It changes the protocol schema: `FeatureManifest` gains the member `description`, `FieldHint` gains the members `help`, `start` and `creates_body`, and the types `StartValue` and `BodyCreation` are new. It also changes the data every built-in manifest returns, among them the `essential` flag of `reverse` in the extrude, revolve and hole manifests. The schema change goes to human review at the M2 gate (AGENTS.md Process, m2-plan.md gate 19). No file format, naming, license or dependency change. `PROTOCOL_VERSION` stays 1 (ADR 0024's additive rule). This ADR carries out the companion change of ui.md open issue 15 that moves the UI's tables into the manifests. It extends [ADR 0011](0011-feature-contract-extensions.md)'s decision that the manifest types are pure data in `partsmith-model`: `StartValue` and `BodyCreation` join them there, and a manifest now needs a `description`. ADR 0011 stands. `FEATURE_API_VERSION` stays 1 (choice 8).

## Context

- **The UI holds feature data of its own.** At a3f4573 four things about the built-in features live in UI code. `FEATURE_DESCRIPTIONS` in `ui/src/commands/descriptions.ts` gives 19 feature commands their description, keyed `feature.<type>`. `FIELD_HELP` and `fieldHelp` in `ui/src/inspector/help.ts` give the hover help of fields of 13 types, keyed by type and path. `START_VALUES`, `HEAD_DIAMETER` and `startValue` in `ui/src/inspector/start-values.ts` give the start values of 6 types, among them a hole's head at twice its Diameter. `bodyCreatingTarget` in `ui/src/inspector/model.ts` decides which field receives the body a command creates. It infers that from the hint path `target`, the options of the `op` hint and the schema's `required`.
- **The open issue.** ui.md open issue 15 lists two of its companion changes for review: the move of these four into `FeatureManifest` and `FieldHint` for plugins, the CLI and Python, and an essential `reverse` in the extrude, revolve and hole manifests. The inspector overrides that flag today (ui.md section 2.12, the inline Reverse).
- **The seam.** Technical design section 15 has built-in features register through the same trait and manifest a plugin will use, with no private shortcuts. A plugin feature gets no description, no help and no start value today. A plugin whose optional `target` body field is not meant for a new body would get one.
- **New features arrive.** M2 adds eight feature types, with inspectors generated from each feature's params schema and manifest hints (m2-plan.md items 6 and 32). Each would add rows to the UI's tables.
- **The CLI and Python read no manifest.** Neither `crates/partsmith-cli` nor `python/partsmith` sends `feature_catalog` at a3f4573. Their users type every value.

## Decision

1. **A description per feature type** (model.md section 2.12). `FeatureManifest` gains `description: String`, required, after `label`: what the feature does, in the words of the interface, one sentence of at most 120 characters that ends with a period. Hosts show it with the feature's command.
2. **Help per field.** `FieldHint` gains `help: Option<String>`, omitted when none: the hover help of a field whose label alone does not say what it does.
3. **Start values per field.** `FieldHint` gains `start: Option<StartValue>`, omitted when none. `StartValue` is tagged `kind`: `expr` (an expression that means the same in every document unit, for a hint with a unit), `choice` (one of the hint's options, for an enumeration or tag field) and `multiple` (a factor times the value of another expression field, for a hint with a unit). A hole's head diameter is `{"kind": "multiple", "field": "diameter", "factor": 2.0}`.
4. **Fields that receive a new body.** `FieldHint` gains `creates_body: Option<BodyCreation>`, omitted when none. `while_new`: the field receives the body a host's command creates while the feature's `op` is `new`, and hosts show it only then. `at_start`: a new feature's field starts set to a body the command creates. Mirror and the two patterns mark their `target` `while_new`. Split body marks its `target` `at_start`.
5. **Checked at registration** (features.md section 3.3). The registry refuses a manifest whose start value or `creates_body` does not fit its hint, with `ManifestMismatch` and a problem text that says why. It does not check the texts.
6. **The built-in values** (features/<type>.md, each Manifest section). Each feature spec lists its description and the help, start value and `creates_body` of each field, with the texts and values the UI's tables held. `import` gets a description too. The extrude, revolve and hole manifests mark `reverse` essential.
7. **The engine passes them on** (engine.md). `feature_catalog` carries each manifest as the registry returns it.
8. **The UI reads only the manifest** (ui.md sections 2.10 and 2.12). `descriptions.ts`, `help.ts` and `start-values.ts` are removed. A command's description, a field's help, its start value and the body-creating field come from the catalog. The inline Reverse moves a field whose hint is essential and changes no flag. A plugin feature gets the same treatment from its manifest.
9. **The CLI and Python** change nothing. Their users type every value. A description or help text in their output is later work (python-api.md and cli.md are unchanged).

## Alternatives considered

The plan settled where the values go: into `FeatureManifest` and `FieldHint` (m2-plan.md item 6 and section 2.1). The spec met eight choices that the plan leaves open. The owner's rule settles each: the most open-source approach, the safest, the industry standard and the recommendation of this work. Every option is open source, and the first criterion picks none of them.

1. *The form of a start value.* Options: (i) a tagged `StartValue` with `expr`, `choice` and `multiple`; (ii) one text member that a host reads by the hint's kind, beside a second member for a derived value; (iii) a text template that names other fields in braces. The rule takes (i), the safest. The registry checks each form against its hint, and the generated TypeScript type is a tagged union a host cannot misread. (ii) needs two members for one value. (iii) adds a small language that hosts would parse. Tagged unions are the industry standard of this protocol too (spec README decision D1).
2. *The hole's head diameter.* Options: (i) `multiple`, a factor times another field's value; (ii) a fixed start value of `6.4 mm`; (iii) a rule in the UI for the hole alone. The rule takes (i), the safest. The head keeps following the Diameter the user typed or the document reused (ui.md U-103). With (ii) a hole of 8 mm would start with a 6.4 mm head that fails. (iii) is a UI-only rule a plugin cannot use.
3. *Which field receives a new body.* Options: (i) `creates_body` on the field's hint, `while_new` or `at_start`; (ii) the M1 inference from the path `target`, the `op` options and `required`; (iii) one member at the manifest root that names the field and when. The rule takes (i), the safest. The rule is explicit and checked at registration. Any field path works. A plugin's optional `target` that is no new body stays an ordinary body field. (iii) states the same thing away from the hint it is about.
4. *A required description.* Options: (i) required; (ii) optional and omitted when empty. The rule takes (i), the safest. Every feature command shows what it does in its tooltip and in the palette (ui.md section 2.10, test U-111). Fusion and FreeCAD give every command a tooltip, the industry standard.
5. *What registration checks.* Options: (i) the structure of start values and `creates_body`, not the texts; (ii) nothing, with hosts falling back on their own rules; (iii) the texts too, by length and final period. The rule takes (i). A start value that does not fit its field fails at startup, as a unit or an option that does not fit already does (features.md section 3.3), the safest. The style of the built-in texts is checked by their tests (features.md tests 47 and 49), the recommendation of this work: a host can show any text, and a plugin should not fail to load over its wording.
6. *A start value that depends on the document units.* Options: (i) refused at registration; (ii) accepted. The rule takes (i), the safest. In ui.md section 2.12 every start value means the same in every document unit. A length start carries its unit. `2` as a length start would start a field at 2 mm in one document and 2 in in another.
7. *The `reverse` flag.* Options: (i) mark `reverse` essential in the extrude, revolve and hole manifests and drop the inspector's override; (ii) keep the override. The rule takes (i), the safest. The UI then changes no flag a manifest sets. That is the seam of technical design section 15. The inspector shows the same fields as in M1 (ui.md U-31).
8. *The version of the manifest contract.* Options: (i) `FEATURE_API_VERSION` stays 1; (ii) it becomes 2. The rule takes (i), the safest. A bump protects nothing yet. No plugin can load before the plugin API ships (features.md section 1, Later). No plugin declares a range that a bump would keep from loading. Plugins declare a compatible range once the plugin API ships (features.md section 2.2, technical design section 15). The version counts from there.

## Consequences

- partsmith-model gains `FeatureManifest::description`, `FieldHint::help`, `start` and `creates_body`, `StartValue` and `BodyCreation` (model.md tests 106 to 112).
- `FEATURE_API_VERSION` stays 1 (choice 8). Neither struct has a `Default`. Every Rust constructor of `FeatureManifest` and `FieldHint` names the new members. Among them are the `manifest` and `hint` helpers of `crates/partsmith-features/src/builtin/common.rs` and the test features of the crate tests. [ADR 0018](0018-body-updates-carry-measurements.md) recorded the same kind of change for `BodyUpdate::measured` (features.md open issue 6).
- partsmith-features checks the new members at registration and returns them from every built-in manifest (features.md tests 46 to 63, and the manifest tables of features/<type>.md).
- partsmith-protocol carries them in `feature_catalog` (protocol.md tests 110 to 113). partsmith-engine passes them on (engine.md test 225). `docs/format/protocol.schema.json` and `ui/src/generated/protocol.ts` are regenerated and logged in ADR 0016 when they are checked in.
- The UI loses `descriptions.ts`, `help.ts` and `start-values.ts` with `FEATURE_DESCRIPTIONS`, `FIELD_HELP`, `START_VALUES` and `HEAD_DIAMETER`, and the inference of `bodyCreatingTarget`, in favor of `bodyCreatingField`. Its test catalog carries the new members (ui.md U-285 to U-289 and E-174). U-29 and U-111 read the manifest instead of the tables. U-31, U-103 and E-84 keep their results.
- The UI keeps tables that this item does not move: `COMMAND_KEYWORDS` (search words, with other apps' names), `FEATURE_SHORTCUTS`, `TOOLBARS`, `FEATURE_ICONS` (it maps the manifest's icon name to the UI's icon set), `FEATURE_REQUIREMENTS` (when a command is available) and `WITHOUT_COMMAND` (the types with no command: `import`). The inline Reverse of ui.md section 2.12 stays too. It keys on the top-level paths `reverse` and `extent` and hides the toggle for the extent kinds `symmetric` and `full` (`REVERSE_IGNORED`). A plugin feature's command has the fallback icon, no search words and no shortcut, is always enabled and is reached from the palette. Moving search words and availability into the manifests is later work, with the plugin API (technical design section 15).
- The feature specs of waves 2 to 4 list their descriptions, help, start values and new-body fields in their manifests. Their inspectors need no UI rows (m2-plan.md item 32).
- The CLI, Python and the file format change nothing.
- This changes the protocol schema. It goes to human review at the M2 gate.

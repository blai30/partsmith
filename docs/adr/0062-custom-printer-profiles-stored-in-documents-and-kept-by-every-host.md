# 0062: Custom printer profiles, stored in the documents that name them and kept by every host

Status: Accepted (owner's rule of 2026-11-05): the M2 plan's choice 21, which settles [ADR 0047](0047-printer-profiles-listed-whole-and-no-custom-profiles-in-m1-hosts.md) decision 2 with its options (b), (c) and (d) together, and the choices below. It changes the file format (a key of format version 3, [ADR 0061](0061-format-version-3-for-the-records-of-m2.md)) and the protocol schema (a command, a request field, a result field, a `Document` member and a member of the `set_printer` edit). Both go to human review at the M2 gate (AGENTS.md Process, m2-plan.md gate 19). No license or capability change. Choice 13 adds `schemars` as a normal dependency of partsmith-engine ([ADR 0020](0020-dependency-log.md), update of 2026-11-08). That edge also needs human review at the M2 gate. The library's place is [ADR 0037](0037-save-checks-the-file-and-hosts-reach-the-assets-folder.md)'s amendment of 2026-11-07.

## Context

- **M1 hosts offer two printers.** A session starts with the built-in profiles `generic-fdm` and `generic-resin`. The engine already takes `put_printer_profile` (protocol.md command 4, `crates/partsmith-protocol`), but no M1 host sends it (ADR 0047 decision 2). A document stores only its `printer` id (`Document::printer` in `crates/partsmith-model/src/document.rs`).
- **A shared document loses its printer.** A document that names a profile the session lacks rebuilds with `generic-fdm` and the warning `unknown_printer_profile`, whose M1 text says "Install it or pick another printer." (engine.md section 3.4). No M1 host can install a profile. The `printer.fit.*` values that size clearances silently change (print.md open issue 6).
- **M2's parts need the user's printer.** Threads, tapped holes and their clearances read `printer.fit.*` (m2-plan.md item 7). A part fits only when those values are the user's own printer's.
- **The plan settled the shape.** The M2 plan's choice 21 picked ADR 0047's options (b), (c) and (d) together. Built-in profiles stay referenced by id. Any other profile is stored, in print.md's written form, in the document that names it. The web and desktop apps keep a library in the webview's IndexedDB and offer to add a stored profile they lack. The CLI reads a profile file and Python takes a profile argument. The document's copy changes only through an edit, never by recompute. Gate 12 checks the result in fresh web, desktop, CLI and Python sessions.
- **No reason for an unavailable value.** `EvaluationContext::resolve` returns `Option<Quantity>` (expressions.md section 2, `crates/partsmith-model/src/expr/evaluate.rs`). `printer.nozzle` on a resin profile reads "Unknown value 'printer.nozzle'. Check the spelling; printer values look like printer.fit.slip." (print.md open issue 1).
- **Crate boundaries.** partsmith-model does not depend on partsmith-print (architecture.md). The CLI no longer depends on partsmith-print either ([ADR 0019](0019-hosts-read-profile-and-load-positions-from-the-engine.md)). Python sends protocol frames through `partsmith-py`.

## Decision

1. **The stored profile** (file-format.md section 3.2, model.md section 2). `Document` gains `printer_profile`, after `printer`: a JSON object in print.md's written form, present only when `printer` names a profile that is not built in. The model keeps it as a `serde_json::Map` and checks only that its `id` is the string `printer` names (`PrinterProfileWithoutPrinter`, `PrinterProfileIdMismatch`). The engine reads it with print.md's new `PrinterProfile::from_written`, which takes no default, and writes its members in the written form's order (engine.md section 3.2). A stored profile that fails that check, or that has a built-in id, refuses to open with `parse_error` at `/printer_profile`.
2. **Resolution** (engine.md section 3.7). A document's profile is the one it stores, else the session profile with its id, else the built-in profile with its id, else the default FDM profile with the warning `unknown_printer_profile`. That warning reads `Printer profile "{id}" is not among your printers. Printer values and checks use the default FDM profile until you add that printer or pick another one.` Every host offers both actions.
3. **The copy changes only by an edit** (engine.md section 3.3). The `set_printer` edit gains an optional `profile`. The engine completes an edit without one from the session profile its `printer` names. A built-in printer stores no profile. Undo and redo replay the recorded pair. Recompute, `put_printer_profile` and `remove_printer_profile` never touch a stored profile. `new_document` stores the session profile its printer names.
4. **Protocol** (protocol.md section 2.5). `put_printer_profile` takes exactly one of `profile` (the input form) and `text` (the input form as JSON text) and returns `{profile}` in the written form. Command 36, `remove_printer_profile {id}`, removes a session profile. `Document.printer_profile` and the edit's `profile` are `$defs/PrinterProfile`. `PROTOCOL_VERSION` stays 1 (protocol.md section 2.9). The engine API gains `put_printer_profile_text` and `remove_printer_profile`. `ProfileIdReserved` and `InvalidProfile` gain the index of the edit they refuse (engine.md section 4).
5. **The web and desktop apps** (ui.md sections 2.15 and 3.17). The IndexedDB database `partsmith` goes to version 3 with a `printers` store of written forms keyed by id. Startup puts every library profile into the core. Add printer and Edit printer open one dialog whose Save puts the profile, keeps it in the library and picks it. A document that stores a profile the library lacks gets the offer "Add '{name}' to my printers". One whose library copy differs gets "Use my '{name}'". The Problems row of `unknown_printer_profile` gets "Choose printer" and "Add printer '{id}'". The desktop adds no host command (desktop.md section 1.1).
6. **The CLI** (cli.md sections 2 and 3.3). `rebuild` and `export` take `--printer-file <PATH>`, not with `--printer`. The CLI reads the file as text, puts it with `put_printer_profile_text` and applies `set_printer` with its id in memory. Nothing is saved. A document that stores its profile rebuilds with it and needs no option.
7. **Python** (python-api.md section 3.13). Every `printer` argument and `Document.printer` take an id or a mapping in the input form. A mapping is sent as `text`. `Document.printer_profile` returns the stored profile as a new dict or `None`.
8. **The reason channel** (expressions.md sections 2 and 3.12, print.md section 3.5). `EvaluationContext` gains the provided method `reason(&self, name: &str) -> Option<String>`, which returns `None` by default. A name whose value is `None` and whose reason is `Some` gives `ExprErrorKind::UnavailableValue { name, reason }`, with the reason as its message. `PrinterValues` gives `printer.nozzle` on a resin profile the reason `printer.nozzle has no value with '{name}', a resin printer with no nozzle. Pick an FDM printer, or write a length instead.`

## Options considered

The plan settled the routes. The spec met eleven choices the plan leaves open, and the track's code round met four more (12 to 15). The owner's rule settles each: the most open-source approach, the safest, the industry standard and the recommendation of this work. Every option keeps profiles in plain JSON with no account. The first criterion picks none of them.

1. *Where the copy sits.* Options: (i) a `printer_profile` key beside the `printer` id at the root; (ii) `printer` as either an id or a profile object; (iii) a root list of every profile the document has used. The rule takes (i), the safest. The protocol's `printer` stays a string for every client. The id and the copy can be checked against each other. A version 2 reader of `printer` sees what it always saw. Slicers do the same in their 3MF projects: PrusaSlicer writes the printer preset's name and its full settings side by side in `Metadata/Slic3r_PE.config`. Option (iii) keeps profiles no feature reads.
2. *Who writes the copy.* Options: (i) the engine completes a `set_printer` edit from the session profile it names, and an edit may also carry its own `profile`; (ii) every host sends the whole profile in the edit; (iii) recompute writes the copy of the profile in effect. The plan rules out (iii). The rule takes (i), the safest. One rule in the engine replaces one in each host. Undo restores the exact copy that was replaced, whatever the session holds by then.
3. *Which wins when the copy and a session profile share an id.* Options: (i) the copy; (ii) the session profile; (iii) the newer of the two. The rule takes (i), the safest and the plan's aim: a shared document rebuilds with the same values everywhere. Under (ii) a user's own edit of a profile would silently change every document that names it. (iii) needs a time that no profile has. The UI's "Use my '{name}'" makes the other choice an edit the user sees and can undo.
4. *A stored profile the engine refuses.* Options: (i) refuse to open, with `parse_error` and a message that says what to fix; (ii) open with the default FDM profile and a warning; (iii) open and resolve by id as a version 2 document does. The rule takes (i), the safest. (ii) and (iii) bring back the silent change of `printer.fit.*` that this ADR removes. A stored copy of a built-in profile is refused the same way. Only a hand edit can write one, and the copy and the built-in could differ.
5. *Defaults in a stored profile.* Options: (i) every field of the written form required (`from_written`); (ii) the input form, with omitted fields from the technology's generic profile. The rule takes (i), the safest. Under (ii) a later change of a generic profile would change documents that store a profile. A rule of print.md section 3.1 that refuses a profile an earlier build accepted needs a new format version (file-format.md section 3.9).
6. *What the model knows of a profile.* Options: (i) a JSON object the model keeps, with the id check in the model and the profile check in the engine; (ii) `PrinterProfile` moved into partsmith-model; (iii) partsmith-model depends on partsmith-print. The rule takes (i), the recommendation. It keeps the crate boundaries of architecture.md. `ptsm_schema` takes the profile's schema as an argument, and the engine passes print's (file-format.md section 3.10).
7. *How the CLI and Python send a profile.* Options: (i) a `text` field on `put_printer_profile` that the engine reads; (ii) each host parses the input form itself. The rule takes (i), the safest. A host that reads a file or a mapping gets the print crate's message for text it cannot read (`invalid_profile`), not a `malformed_request` for the whole frame. The CLI needs no dependency on partsmith-print.
8. *The CLI's option.* Options: (i) `--printer-file <PATH>`, not with `--printer`; (ii) `--printer` taking either an id or a path; (iii) a profile folder the CLI reads on every run. The rule takes (i), the industry standard: slicers' command lines load a settings file with an option of its own (PrusaSlicer's `--load <file>`). (ii) is ambiguous for a file named like an id. (iii) makes a build depend on the machine, which a document that stores its profile no longer needs.
9. *Python's argument.* Options: (i) every `printer` argument takes an id or a mapping; (ii) a method `Document.add_printer(profile)`; (iii) a `PrinterProfile` class. The rule takes (i), the recommendation (AGENTS.md principle 5, fewer options). `json.load` of a profile file and `Document.printer_profile` of another document both pass as they are.
10. *Removing a profile.* Options: (i) command 36, `remove_printer_profile`; (ii) no removal: a session keeps a deleted profile until it restarts. The rule takes (i), the safest. Under (ii) a printer the user deleted from the library would still resolve in the open documents that name it and store none.
11. *The reason channel.* Options: (i) a provided `reason` method beside `resolve`; (ii) `resolve` returns a `Result` with a reason; (iii) the evaluator special-cases `printer.nozzle`. The rule takes (i), the safest. Every existing context compiles and behaves as before. (ii) changes every implementation. (iii) puts print knowledge in partsmith-model.
12. *How the app reaches the library* (2026-11-08, the code round; ui.md section 2.9). Options: (i) a `printerLibrary` member of `App` and of `CreateAppOptions`, beside `recent` and `recovery`; (ii) a library that `library.ts` opens when it is imported; (iii) a member of the store's state. The rule takes (i), the safest and the pattern the app already uses for its other stores. Tests pass a memory library, as they pass a memory recovery store. (ii) is global mutable state, and (iii) puts a database handle into the state that renders.

13. *How the engine gets the profile's schema* (2026-11-08, the code round; engine.md section 2, file-format.md section 3.10). Options: (i) `schemars` as a dependency of partsmith-engine, which calls `schema_for!` on print's `PrinterProfile`; (ii) a new partsmith-print function that returns that schema; (iii) the `PrinterProfile` entry cut out of the protocol schema. The rule takes (i), the industry standard: the engine builds the schema the way the other crates build theirs. `schemars` 1.2.2 (MIT) is already a workspace dependency and in every build through partsmith-print. No crate joins the build. (ii) adds an API the spec does not have, and (iii) ties the file format's schema to the protocol's. This adds a dependency edge, so it needs human review at the M2 gate.
14. *Which profile "Edit '{name}'…" edits* (2026-11-08, the code round; ui.md section 3.17). The UI holds no copy of the library, and a session profile comes from the library or from a Save whose library write failed. Options: (i) the listed profile the document's printer names, unless it is built in; (ii) a profile the UI reads from the library each time the menu opens. The rule takes (i), the safest: the menu opens at once and never waits on IndexedDB. The built-in profiles are the two generic ones of print.md section 2.2.
15. *What choosing the document's own printer in the menu does* (2026-11-08, the code round; ui.md section 3.17). Options: (i) nothing, as in M1, unless the document stores a copy that differs from the listed profile, which the choice then stores in its place; (ii) always commit `set_printer`. The rule takes (i), the safest: a choice that changes nothing adds no undo entry, and the listed profile replaces a differing copy only when the user picks it. The item "{name} (this document)" leaves the document as it is. The printer dialog's Save always commits, so the document stores what was saved.

The M2 warning names only actions every host offers, as m2-plan.md gate 12 asks and docs/guidelines/errors.md does for every message.

## Consequences

- A document that names a custom profile carries it. It rebuilds with the same `printer.*` values, findings and geometry in every fresh web, desktop, CLI and Python session (gate 12). A version 2 document that names an unknown profile still warns (newcomer error corpus NC13, by handoff).
- An M1 build refuses a document that stores a profile, with `NewerFormatVersion` (ADR 0061). It never drops the copy when it saves.
- partsmith-model gains `Document::printer_profile`, two `StructureError` variants, two `EditError` variants and the `profile` of `Edit::SetPrinter` (model.md tests 98 to 105 and 115). partsmith-model's expression evaluator gains `EvaluationContext::reason` and `UnavailableValue` (expressions.md tests 99 to 103). partsmith-print gains `from_written` and `ProfileError::MissingField` (print.md tests 128 to 138). Print test 27 now expects `UnavailableValue` for `printer.nozzle` on a resin profile.
- partsmith-engine gains `put_printer_profile_text`, `remove_printer_profile`, the open check of a stored profile and the completion of `set_printer` (engine.md tests 171 to 194). `EngineError::ProfileIdReserved` and `InvalidProfile` gain an `index` field.
- partsmith-protocol gains command 36, the `text` field and the `{profile}` result (protocol.md tests 89 to 95; test 34 lists the new command). `docs/format/protocol.schema.json`, `docs/format/ptsm.schema.json` and `ui/src/generated/protocol.ts` are regenerated and logged in ADR 0016 when they are checked in.
- The CLI gains `--printer-file` (cli.md tests 72 to 84). Python gains the mapping forms and `Document.printer_profile` (python-api.md tests 125 to 131, 138 and 139). The UI gains the printer dialog, the library and the offers (ui.md U-252 to U-265, U-291 to U-296, E-168 to E-170). The desktop host changes nothing (desktop.md test 74).
- ADR 0047 decision 2 is settled. Its decision 1 stands. print.md open issues 1 and 6 are resolved.
- `ProfileError::Json` still carries serde's text, which the CLI and Python now show to users (print.md open issue 11).
- Profile import from slicers and the calibration print stay in M3 (m2-plan.md section 7.1, the milestone split).
- This changes the file format and the protocol schema. Both go to human review at the M2 gate.

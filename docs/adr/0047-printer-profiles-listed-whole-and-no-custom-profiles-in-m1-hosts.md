# 0047: The protocol schema lists printer profiles in their written form, and custom printer profiles are Later in the CLI and Python

Status: Proposed, needs human review: decision 1 changes the protocol schema (gap list item PRINT-3, a planned entry in ADR 0016's log), and decision 2 settles the public API of the CLI and Python for custom printer profiles (gap list item PRINT-2) by adding none. No file format, license, dependency or capability change.

## Context

- **Listed profiles described in the input form** (PRINT-3). `PrinterProfile` reads through `ProfileInput` (`#[serde(try_from = "ProfileInput")]`, print.md section 3.1), and schemars follows serde: with `try_from`, the schema of `PrinterProfile` in the deserialize contract is `ProfileInput`'s. The protocol schema is one document generated in that contract (protocol.md section 2.9), so `$defs/PrinterProfile`, which only the `list_printer_profiles` result carries, required only `id`, `name` and `technology` and gave `fit` as a `FitInput` with every class optional, although the engine lists every profile with every field (print.md test 1, the result example of protocol.md section 2.5). The generated TypeScript made `bed`, `layer_height`, `max_overhang_angle`, `max_bridge_length` and `fit` optional and nullable, and the UI fell back where it read them: `printerDetail` in `ui/src/print/printer.ts` left out a bed that a listed profile always has, and `bedOutline` in `ui/src/print/bed.ts` drew nothing for one. Requests already carry the input form as `ProfileInput` (`put_printer_profile`).
- **Checked on 2026-10-28** with schemars 1.2.2, the locked version: on a struct that keeps `#[serde(try_from = ...)]`, `#[schemars(!try_from)]` gives the struct's own schema in both contracts, with the same `required` list (every field but the `Option` that `skip_serializing_if` leaves out) and a `FitClasses` definition, while serde still reads the struct through the input type. `#[schemars(!try_from, deny_unknown_fields)]` adds `"additionalProperties": false` to that schema in both contracts, and `#[serde(deny_unknown_fields)]` on `FitClasses` to its definition, without changing what serde reads through the input type.
- **No route for custom profiles** (PRINT-2). The engine has `put_printer_profile`, and a session keeps the profiles it is given (print.md section 1.2: profiles live in the session, and persisting them is the hosts' job, later). No M1 host sends it: the UI lists custom printer profiles as Later (ui.md section 1.2), the CLI opens a headless session per run whose `--printer` takes an installed id, and Python has no call for it. A document names its printer by id only (`printer`, file-format.md section 3.2; print.md open issue 6), so the document format carries no custom profile that a host could install from, and a route would have to bring the profile along on every run.

## Decision

1. **Results list profiles in the written form; requests keep the input form.** `PrinterProfile` keeps `#[serde(try_from = "ProfileInput")]` and gains `#[schemars(!try_from, deny_unknown_fields)]`, so its JSON Schema is its written form in both contracts: `id`, `name`, `technology`, `bed`, `layer_height`, `max_overhang_angle`, `max_bridge_length` and `fit` required, `nozzle_diameter` optional, and `fit` the `FitClasses` definition with its four classes required, both closed to unknown members like `Bed`, as serde reads them (print.md section 3.1 rule 1); `FitClasses`, which nothing deserializes on its own, gains `#[serde(deny_unknown_fields)]` for that. `$defs/PrinterProfile` was closed before, as `ProfileInput`'s schema, and stays closed. `ProfileInput` and `FitInput` keep the input form and stay closed, and `Bed`, which both forms share, stays closed too. The protocol schema and the UI's generated types are regenerated, and the UI's fallbacks for the fields a listed profile always has go (`printerDetail` keeps leaving out an absent nozzle, the one optional field). The engine is unchanged, no message changes, and `PROTOCOL_VERSION` stays 1 (protocol.md section 2.9). Spec: print.md sections 2.2 and 3.1 and test 124, which replaces two unit tests of `src/profile.rs`; protocol.md section 2.5 commands 3 and 4, section 2.9 and test 86; ui.md section 3.17 (`printerDetail`); the planned entry in ADR 0016's log. `crates/partsmith-protocol/AGENTS.md` names `PrinterProfile` beside `FixRef` among the result types that reject unknown fields.
2. **Custom printer profiles are Later in the CLI and Python** (cli.md section 1 and the `--printer` row of section 2, python-api.md section 1, print.md section 1.2), as the gap list recommends when the document format does not already carry custom profiles. Their sessions have the built-in profiles only, so in M1 `--printer`, `Document(printer=...)`, `Document.printer` and `check(printer=...)` name `generic-fdm` or `generic-resin`, and any other id keeps its existing `unknown_printer_profile` behavior. protocol.md section 2.5 command 4 says that no M1 host sends `put_printer_profile`. The Later entries name no option, flag or method, so whichever route the owner picks is specified then. No code changes.

## Options the owner can still pick

For decision 1:

- (a) **The written form for results** (chosen): two attributes and the regenerated files, and the schema says what the engine writes, closed as serde reads it.
- (b) **Keep the input form** in the schema: no schema change, and every host keeps a fallback for fields the engine always writes.
- (c) **A schema of the written form on the protocol side**, as a mirror struct in `partsmith-protocol` or a `schema_with` function on the `profiles` field: leaves the schema of `PrinterProfile` as serde reads it, at the cost of a second description of the written form under another name, kept in step with print.md by hand or by a test.
- (d) **One schema per direction**, requests generated in the deserialize contract and results in the serialize contract: every type that both directions share would be described twice, and many generated TypeScript names would change, far more than this item needs.
- (e) **The written form open to unknown members**, like the protocol's own result types (`#[schemars(!try_from)]` alone, `FitClasses` unchanged): the schema would accept a listed profile with a member that every Rust decoder rejects (`decode_response_frame` reads profiles through `ProfileInput`, print.md section 3.1 rule 1), and would loosen `$defs/PrinterProfile`, which was closed. The generated TypeScript is the same either way, since the generator closes every object (`additionalProperties: false`).

For decision 2:

- (a) **Later** (chosen): no public API and no code.
- (b) **A CLI `--printer-file <PATH>` on `rebuild` and `export`, and a Python profile argument or `Document.add_printer`**: each reads print.md's input form and sends `put_printer_profile` before the document recomputes; the CLI exits 1 with the engine's message for `invalid_profile` and `profile_id_reserved`, and Python raises `EngineError` with those codes. Size M (gap list): new options and methods, their errors and tests in two hosts, and the CLI would read `ProfileInput` through `partsmith-protocol`, since it no longer depends on `partsmith-print` (ADR 0019). The profile still has to come along on every run, since the document stores only its id.
- (c) **Profiles stored in the document** (print.md open issue 6): a file-format change, after which a route in each host is small and a shared document keeps its printer; it needs a decision of its own.
- (d) **Profiles persisted by the hosts** (print.md section 1.2): a profile folder that the hosts read at startup, a host feature with its own storage and capability questions.

## Consequences

- Decision 1 changes `docs/format/protocol.schema.json` and `ui/src/generated/protocol.ts`, reviewed at the next gate with ADR 0016's entry. Reverting it is removing the two attributes, regenerating both files and restoring the UI's fallbacks.
- Every profile the engine lists validated against the old schema and validates against the new one, since the engine always wrote every field. A listed profile that leaves out `bed`, `layer_height`, `max_overhang_angle`, `max_bridge_length`, `fit` or a fit class, which the engine never sends, validated before and fails now; one with an unknown member failed before and still fails. Code that read the fields as optional still compiles against the stricter type. Only code that builds a listed profile without one of those fields stops compiling, which in the repository is the two `bed: null` cases of a UI test of `printerDetail`, a profile the engine never lists; that test keeps its `nozzle_diameter: null` case.
- Decision 2 adds no code. A user whose printer is neither generic profile gets the checks of `generic-fdm` or `generic-resin`, which the CLI and Python reports name. Picking (b), (c) or (d) later adds a route without changing any M1 behavior.
- The `unknown_printer_profile` warning still says "Install it or pick another printer." (engine.md section 3.4), and no M1 host can install a profile, so only picking another printer is open to a user. Rewording it is left to the item that picks a route (options (b) to (d)), since the words are pinned in the engine, its tests and protocol.md's example (print.md open issue 6).

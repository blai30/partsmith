# 0056: Range messages state the bound the check applies

Status: Accepted (owner, 2026-11-05): the truthful alternative of features.md open issue 15, `must be at least 0.000001 mm, but it is 0.0000001 mm`, built by wave G's messages track. The choices below that the decision leaves open are Accepted (owner's rule of 2026-11-05). No schema, protocol, public API or dependency changes: `Bound` and `FeatureError` keep their variants and fields.

## Context

- **A bound the value meets.** The positive length rule (features.md section 3.4) rejects a length below `LINEAR_TOLERANCE` (1e-6 mm). The kernel builds nothing smaller. The hole's head checks and the torus's tube reject a length within the tolerance of another value in the same way. Their errors kept the bound as written, `GreaterThan(0)` or `LessThan(b)`. Section 3.12 wrote the value with the digits that tell it apart from that bound: `Distance must be greater than 0 mm, but it is 0.0000001 mm.` The value shown meets the bound the message states, against the error guidelines' rule that a message is true in every case the code reaches.
- **The decision.** On 2026-11-05 the owner chose to state the bound the check applies (`AtLeast(LINEAR_TOLERANCE)`), at the cost of showing the tolerance.
- **Units and rounding.** The tolerance is 0.0000000393700787 in, which the usual 6 decimals write as `0 in`. A bound derived from a tangent carries rounding in its last bits: a 90 deg countersink that ends 1e-6 mm above a 5 mm hole's bottom has the largest head diameter 15.999997999999998 mm. Read back, 15.999998 is just over it. A fix that sets such a bound would fail the check it came from.

## Decision

1. **Which values get the bound the check applies** (features.md section 3.4). Each check compares the value with the bound it applies. A value that also fails the bound as written (0 or less, or not beyond the other value) keeps that bound and its name: `Distance must be greater than 0 mm, but it is 0 mm.`, `Counterbore depth must be less than the hole depth (5 mm), but it is 6 mm.` A value that meets the bound as written but not the check gets the bound the check applies, `AtLeast` or `AtMost`, with no name: `Distance must be at least 0.000001 mm, but it is 0.0000001 mm. Use 0.000001 mm or more.` The checks: the positive length rule (`AtLeast(LINEAR_TOLERANCE)`), the hole's diameter (`AtLeast(2 LINEAR_TOLERANCE)`), head diameter (`AtLeast(D + 2 LINEAR_TOLERANCE)`), counterbore depth (`AtMost(L - LINEAR_TOLERANCE)`) and countersink (`AtMost(D + 2 (L - LINEAR_TOLERANCE) tan(angle / 2))`), and the torus's tube (`AtMost(major - LINEAR_TOLERANCE)`).
2. **How values and bounds are written** (features.md section 3.12). The value and the bound are each written with the fewest decimals, at least the usual 6 and up to 15 significant digits, that put the written number within a hundredth of the distance between them. When the written number of a bound, read back, would lie on the side of its limit that the bound refuses (below a `GreaterThan` or `AtLeast` limit, above a `LessThan` or `AtMost` limit), its last decimal moves one step toward the values the bound accepts. A `GreaterThan` or `LessThan` bound equal to its limit to 15 significant digits keeps its number. Every value the message's advice names then passes the check, up to values with more than 15 significant digits. The suggestion and its `SetField` fix use the same text (section 4.4). The fix passes the check too. The countersink above reads `Head diameter must be at most 15.999997 mm, but it is 15.9999999 mm.`
3. **The revolve's angle** (features/revolve.md section 3.3 step 4, test 26). An angle within the angular tolerance of 0 (1e-9 rad) states that tolerance as its bound, `GreaterThan(1e-9)`: `Angle must be greater than 0.000000058 deg, but it is 0.00000001 deg.` The tolerance is 0.0000000572958 deg. Decision 2 writes it above that.
4. **Two sides below the tolerance** (features.md section 4.1, features/extrude.md test 46). `BothSidesZero` reads `Both sides of the extrusion add up to less than 0.000001 mm. Give at least one side a distance.` The tolerance is written in document units as decision 2 writes an `AtLeast` bound next to a total of 0 (`0.00000004 in` in an inch document).

## Options considered

The decision of the owner settles the wording. **The choices the owner's rule settles.** Each is Accepted (owner's rule of 2026-11-05).

1. *Which values get the new bound.* The options: (i) every value the check rejects, 0 and negative values included; (ii) only values that meet the bound as written. The rule takes (ii), the recommendation. The issue the owner decided is about values within the tolerance. Under (i), the common message for 0 would show the tolerance. A counterbore deeper than its hole would lose the name `the hole depth`.
2. *How a bound with more digits than 6 decimals is written.* The options: (i) the usual 6 decimals, rounded to nearest; (ii) always 15 significant digits; (iii) the decimals that tell it apart from the value, moved toward the values it accepts when the text read back would fail. The rule takes (iii), the safest. Under (i) the tolerance reads `0 in` and a fix can fail its own check. Under (ii) every bound in inches shows digits of rounding, `39370.0787401575 in` for the modeling limit. The first build moved only `AtLeast` and `AtMost` bounds and wrote a strict bound to the nearest: the revolve's angle read `greater than 0.000000057 deg`. An angle of 0.0000000571 deg followed that advice and still failed. The options for strict bounds: move them the same way, or leave them to the nearest and record it. The rule takes moving them, the safest: the advice of every range message then works. A strict bound named after another value, such as `the ring radius (0.3937 in)` for 10 mm, then shows that value up to one step of its last decimal toward the accepted side, within the usual 6 decimals. A strict bound whose written number equals its limit to 15 significant digits keeps it. Only values with more digits lie between the two. Moving it would turn the countersink's 16 mm, computed as 15.999999999999998 mm, into `15.999999 mm`. An `AtLeast` or `AtMost` bound still moves in that case. Its fix sets the value to the written number.
3. *The revolve's angle within the angular tolerance.* The options: (i) keep `GreaterThan(0)`, a message the value meets; (ii) state the bound the check applies, `GreaterThan(1e-9)`; (iii) state it as `AtLeast(1e-9)`, with a fix. The rule takes (ii), the safest: the message is true and the check is unchanged. Under (iii) the fix would set an angle so small that the kernel sweeps nothing.
4. *`BothSidesZero` for two sides above 0 that add up to less than the tolerance.* The options: (i) keep `Both sides of the extrusion are 0.`, which is not true there; (ii) a wording true in both cases that states the tolerance; (iii) a field with the sides' total, a public API change of `FeatureError`. The rule takes (ii), the safest without an API change.
5. *`ConeRadiiZero`.* `Cone bottom and top radius cannot both be 0.` states a rule. A radius below the tolerance is built as an apex, a radius of 0 (features/cone.md section 3.2). The options: change it as `BothSidesZero`, or keep it. The rule takes keeping it: the message is true of the cone as built. The common case keeps its plain words.

## Consequences

- The per-feature tests "below the tolerance" pin the new texts: features/box.md test 11, cylinder.md 8 and 9, cone.md 12, sphere.md 7, torus.md 7 and 8, extrude.md 45 and 46, fillet.md 17, chamfer.md 14, shell.md 13, revolve.md 26 and hole.md 25 to 31, with features.md test 9 of section 6.5.
- The hole's head checks and the torus's tube compare the value with the bound they state. They can differ from the old checks in the last bit of a value at the bound itself.
- A host shows `Use 0.000001 mm` and the other bounds of this kind as one-click fixes, as for every `AtLeast` and `AtMost` bound.

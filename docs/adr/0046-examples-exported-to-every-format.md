# 0046: The examples runner exports every example that builds to STL, 3MF, OBJ and STEP and checks each report against the file written

Status: Accepted. No capability, schema, license or dependency changes: runner test 5 runs the built `partsmith` binary with `tempfile` and `serde_json`, which the CLI's tests already use, and stores no expected results.

## Context

- **No example was ever exported** (gap list EX-6). Technical design section 16 asks the feature example suite to cover "each import and export path", and its round-trip tests ask a STEP export and import to keep the volume within 1e-6 relative. `partsmith export` is tested on four engine fixtures (cli.md tests 34 to 49: `box.ptsm`, `two-bodies.ptsm`, `circle.ptsm` and `fillet.ptsm`), the engine's export on the box and the two bodies (engine.md tests 85 to 95 and 160), and the STEP round trip on the box alone (cli.md test 41, engine.md test 89), whose faces are planar with corners at whole millimeters. The corpus holds 256 examples, 232 of which build, with every feature type and the curved faces of cylinders, cones, spheres, tori, revolves, fillets and patterns.
- **Two forms were named.** The gap list asked delivery.md to say what an export example is, either (a) a runner test that runs `partsmith export --json` for `stl`, `3mf`, `obj` and `step` and compares its report, or (b) a STEP export, import and volume check for every example that builds, and to pick the one with the least code that covers each export path.
- **Measured on 2026-10-28** in the development container (4 cores, debug CLI binary, OCCT 7.9.3). The `examples::` module took 24 s. Exporting all 256 examples to the four formats took 41 s: the 232 that build exported to each format with exit 0 and a report naming one file of the format's media type with its size; the other 24 exited with 1, 7 with `features_failed` and 17 with `nothing_to_export`. Only `extrude/union-touching-itself` warned (`non_manifold_edges`, in each mesh format), which its expected `mesh_validity` finding also reports. A temporary test imported each of the 232 STEP files with `Session::import_step` and measured it: the worst volume difference from the sum of the expected bodies' volumes was 9.0e-13 relative, the worst area difference 3.1e-13, every face count was unchanged, and the imports and measures took 20 s in one thread, 3 s of them for the benchmark model.

## Decision

1. **Every example that builds is exported to each format** (option (a)), by runner test 5, `examples_export_to_every_format` in `crates/partsmith-cli/tests/examples.rs` (delivery.md section 2.8, "Export examples"). An example builds when its expected results have no feature with status `error` and a body without `"empty": true` whose record in the `.ptsm` has neither `"visible": false` nor a `role` other than `part`, the bodies `partsmith export` takes by default in every format (engine.md 3.13 item 1). For each such example and each of `stl`, `3mf`, `obj` and `step`, `partsmith export --json <example> -o <output>` into a temporary directory must exit with 0, write a file at `<output>`, and print a report that, without its `warnings`, matches `{"files": [...]}` with the one file asked for (`<output>` as passed, `model/<format>` and the size of the file written) by the examples' comparison rules. Failures are worded as a rebuild's are, with `partsmith export to <format>` in place of `partsmith rebuild` (delivery.md section 4); delivery.md tests 68 to 70 check the parts.
2. **Warnings are not compared.** They describe the mesh at the document's `standard` tolerance, the mesh the print checks analyze, whose problems the expected `mesh_validity` findings already hold; io.md's tests hold their words.
3. **The check stores and blesses nothing.** No expected results change, and a new example that builds is exported with no step of its own. It reads the expected results while a bless run may be rewriting them, so a bless run is followed by a run without `PARTSMITH_BLESS` (delivery.md section 2.8).
4. **`py` stays with the twins**, whose round trip (python-api.md section 3.9, first form) calls the engine's `export_python`, which `partsmith export --format py` calls too.
5. **The STEP files are not imported back** (options (b) and (c) are not taken); delivery.md open issue 18 keeps (c) with the measurement above.

## Options considered

- (a) **Every format's report** (chosen): covers the four formats over the whole corpus with no stored results, in one test function and a few helpers beside runner test 4's, and finds an export that fails, panics or reports a file other than the one it wrote, on any geometry the corpus holds. It does not read what a file holds.
- (b) **The STEP round trip for every example that builds**: about as much code, plus an engine session per worker. It covers one format of four, though it is the only one of these checks that reads what a file holds, and the only one technical design section 16 gives a tolerance for.
- (c) **Both**: (a) with the STEP file it writes imported and measured, about 20 more lines and a few seconds on 4 cores. It adds the round trip over curved faces, which no test has, and can be added later; delivery.md section 8 asks the owner about it (open issue 18).
- (d) **Stored export reports**, each format's byte count as an expected result: a new file per example or a new member in each of the 256 expected files, all blessed again, for numbers that change with the zip crate and the tessellation and say no more than (a) about whether an export works.
- (e) **A few examples per format**: less time, but the corpus is there for its spread of geometry.
- For the warnings: (w1) not compared (chosen); (w2) none allowed, which fails `extrude/union-touching-itself`, whose two parts touch along an edge on purpose; (w3) each warning's code among the codes of the example's `mesh_validity` findings, a check that export and print agree, which ties io's codes to print's for meshes that runner test 4 already covers.

## Consequences

- delivery.md sections 2.1, 2.8, 3.7, 4 and 8, tests 64 and 68 to 70 and open issues 4 and 18; cli.md section 3.4 item 8. The code is in `crates/partsmith-cli/tests/examples.rs`; production code changes only if an export defect shows.
- The runner rebuilds each example that builds four more times. Exporting the corpus alone took 41 s on 4 cores, so the module, at 24 s before, is expected to take about a minute, within section 5's 3 minutes; delivery.md open issue 4 says when it moves to its own job.
- The platforms workflow runs `examples::` on Windows and macOS (delivery.md section 2.14), so the exports run there too (delivery.md test 64), which only CI can check.

# 0069: Component scopes: a record belongs to the scope that holds it, and a reference leaves its scope only through an occurrence path

Status: Accepted (owner's rule of 2026-11-05): the M2 plan's choice 26, option (a), and the choices below. It builds nothing in M2: no code, no schema change, no protocol change, no dependency and no license. It sets rules that every record and reference of format version 3 keeps ([ADR 0061](0061-format-version-3-for-the-records-of-m2.md)). It keeps the key `occurrence` and three document keys free for M4. file-format.md section 3 states the rules, by handoff from this step. The ADR goes to human review at the M2 gate as the components ADR, with format version 3 (AGENTS.md Process, m2-plan.md gates 18 and 19). M4's specs fill in the records it names.

## Context

- **Components in the design.** Technical design section 9: a component groups bodies, sketches and features with its own origin. It is local to the file or linked from another `.ptsm` file. A linked file stays live. A linked component can be overridden per instance with parameters. Joints place components, and joint values are parameters. Section 6 adds that parts reference each other by relative path and id. The M2 plan puts the code of components in M4 (section 5.2) and this ADR in wave 1 (item 12, choice 26).
- **One scope today.** A `Document` holds `parameters`, `bodies` and `features`. It rejects unknown keys, and so do `Parameter` and `Body` (`deny_unknown_fields` in `crates/partsmith-model/src/document.rs`, file-format.md section 3.2). Ids are unique in the document across every kind, the ids declared inside feature params included (model.md section 3.1). `IdKind` has five kinds with the prefixes `p-`, `b-`, `f-`, `e-` and `c-` (`crates/partsmith-model/src/id.rs`).
- **M1 references name their targets in the same document.** None carries a document, a file or a scope.
  - A body is named by its id (`body`, `tools`), a sketch or a datum plane by its feature id, a sketch entity or point by its id or `PointRef`, and a region by its `RegionKey`.
  - A face, edge or vertex is named by a `Reference` (`q`, `fp`, `nb`, `merged`). A `Reference` is closed to unknown fields. It always sits beside a `body` field in the same object (spec README decision D2, naming.md section 2.4).
  - A parameter is named by its name in an expression, and a printer value by a dotted name under `printer` (expressions.md section 3.5). A parameter name holds no dot (model.md section 3.3).
  - An asset is named by the hash of its content (file-format.md section 3.11), and a printer profile by its id.
- **Element names start with a feature id**, such as `f-ext1/lateral/e-1` (naming.md section 3.1). The grammar's `instance` group, `@<feature>:<n>`, names the copies a pattern or mirror feature makes inside the document. It names no component.
- **Frames.** Stored coordinates are in sketch coordinates, in body coordinates, or in world coordinates. Body coordinates move with the element's motion: a face sketch's fallback with `fallback_frame: body` (sketch.md section 2.2) and an edge or face axis's `direction` (features.md section 2.5). Records in world coordinates include a face sketch's fallback with `fallback_frame: world`, a primitive's `plane` and `position`, the origin planes and axes, and `move_body`'s `translation`. Fingerprint centroids and directions are in world coordinates of the body state (naming.md section 2.3).
- **Cache keys carry no document identity.** A feature's key is a BLAKE3 hash of its canonical params, its evaluated values, its upstream keys and the versions of partsmith-features and OCCT (recompute.md section 1). No path, handle or document name enters it.
- **M2 writes many new records and references.** Format version 3 gains conic, spline, text and projected sketch entities, the stored printer profile (`printer_profile`, [ADR 0062](0062-custom-printer-profiles-stored-in-documents-and-kept-by-every-host.md)) and the records of eight feature types. Their sweep paths, helix axes, thread and emboss faces, up-to-face and up-to-body extents, loft sections, rib targets, projected edges and font assets are all references to a body, a feature, an element or an asset.
- **Nothing is reserved yet.** At a3f4573 no key named `occurrence`, `components`, `occurrences` or `joints` appears in `docs/format/ptsm.schema.json`, in `docs/format/protocol.schema.json` or in the document types of the crates.

## Decision

**Scopes.** A scope is one set of `parameters`, `bodies` and `features`, with the records nested in them (sketch entities and constraints), one origin and one timeline. A `.ptsm` document's top-level arrays are its root scope. Format versions 1 to 3 hold the root scope alone. M4's components add scopes. A local component holds the same three arrays inside the document, with the same record shapes. A linked component's scope is the root scope of another `.ptsm` file. An occurrence is the record that places a component in a scope (technical design section 9 calls it an instance).

1. **A record belongs to the scope whose array holds it.** No record names its scope. A record that moves between a local component and the root moves unchanged. A local component extracted into a file of its own keeps every record unchanged.
2. **An unqualified reference resolves in its own scope.** Every reference that format versions 1 to 3 hold is unqualified. It resolves in the scope of the record that holds it, in M4 as now. The same records then build the same way in the root, in a local component and in a linked file.
3. **A reference into another scope carries an occurrence path.** In M4, a reference to a body, feature, sketch entity or element of another scope adds the field `occurrence` to the object that holds its target's id field. Its value is an array of occurrence ids. The first entry is an occurrence in the holding record's scope. Each later entry is an occurrence in the component that the entry before it places. The ids and element names beside the path keep their unqualified form. They resolve in the scope the path ends in. An element reference stays `q`, `fp`, `nb` and `merged`, with `occurrence` beside its `body` field. No stored id, element name `q` or expression holds a scope. An expression names only the parameters of its own scope and `printer.*` values. A record that sets a parameter of another scope, such as M4's per-occurrence override, names that parameter by its id in the occurrence record. As an illustration of M4's form, a face of a lid placed by the occurrence `o-lid` reads `{"kind": "face", "body": "b-1", "occurrence": ["o-lid"], "face": {"q": "f-ext1/end-cap", "fp": "plane|n=0,0,1|c=0,0,30|a=400|adj=4,4"}}`. A plain id string, such as an entry of `tools`, is always unqualified. Where M4 lets such a field reach another scope, it gives the field an object form with `occurrence`. That object is a new value of the field, written only from M4's format version on.
4. **References cross scopes downward only.** A reference names its own scope or a scope that an occurrence in it places, at any depth. It never names a parent scope or a sibling. A component's records are then complete in themselves. A local component and a linked file build the same in every occurrence. Occurrences cannot form a cycle. A feature writes only bodies of its own scope. A reference into an occurrence reads its target and never changes it. The `body` a feature writes, and the references to that body's elements beside it (naming.md section 2.4), never take `occurrence`.
5. **Ids are unique within a scope.** From M4 on, model.md section 3.1's rule reads "within a scope". A linked file's ids are unique in that file. Its records are reached from outside only through an occurrence path. Format versions 1 to 3 hold one scope. For them the rule is unchanged.
6. **Coordinates are in the scope's own frame.** Every stored coordinate, direction, placement and fingerprint is in sketch coordinates, in body coordinates, in a frame of a referenced element, or in world coordinates. World coordinates are the coordinates of the scope's own origin: the document's origin in format versions 1 to 3, the component's origin in M4. An occurrence's placement maps its component's frame into the frame of the scope that holds the occurrence. A qualified reference stores its fingerprint in the frame of the scope its path ends in. Moving an occurrence changes no stored record.
7. **File properties are not scoped.** `format`, `format_version`, `units`, `printer`, `printer_profile` and `rollback` belong to the file. `units` gives every bare number in the file's expressions its unit (expressions.md section 3.10). A linked file keeps its own units. The `printer.*` values of every scope a build holds, linked files included, come from the printer of the document the session builds (choice 6). A linked file's own `printer` and `printer_profile` apply when that file is opened as a document of its own. M4's components spec decides what a linked file's `rollback` does.
8. **Some names are not scoped.** An asset name is the hash of its content and means the same bytes in every scope. The built-in font's name fixes its bytes (m2-plan.md choice 13). A printer profile id names a profile of the session or the document's stored profile (ADR 0062).
9. **Reserved names.** Until M4 adds them, no key of a document is named `occurrence`, at any depth, and no document root holds `components`, `occurrences` or `joints`. No property of the protocol schema is named `occurrence` either. M4 adds these keys with a format version of its own. The step that migrates a document into that version changes only the version number, whichever version comes before it. ADR 0061 decision 5 already requires a new version for a new key of `Document`.

**What M2's records and references do now.** Every M2 spec that adds a record, a reference, an edit, a protocol type or an expression name keeps these rules. The critic of each spec checks them.

1. A new record goes into the root scope's arrays (`parameters`, `bodies`, `features`) or nests inside a feature record. A new document-level key holds a property of the file, never records that other records reference. `printer_profile` is the one such key of version 3 so far.
2. A new reference names its target by id, `PointRef`, region key, element reference, parameter name, asset name or built-in name. It never names a target by its position in a list or by its display name. It holds no document, file, scope or occurrence.
3. A new face, edge or vertex reference sits beside a `body` field in the same object, in documents and in protocol messages (spec README decision D2). That object is where M4 puts `occurrence` when the reference reads a body of another scope (decision 4).
4. A new coordinate, direction, placement or fingerprint is in sketch coordinates, in body coordinates (moved by the element's motion, as a fallback with `fallback_frame: body` and an axis `direction` are, sketch.md section 2.2 and features.md section 2.5), in a frame that an element the record references defines (such as a referenced face's parameter plane), or in the document's world coordinates. M2 writes no coordinate in the frame of another document, file or occurrence.
5. No new key is named `occurrence`: not in a record, a param, a value, an edit or a protocol type. No new document-level key is named `components`, `occurrences` or `joints`.
6. No new record stores a file path, a document name, a URL or a session handle. A file reaches a document only as an asset.
7. A new feature's build reads only its params and what its `Dependencies` declare: features, bodies, expressions and assets, with their results in the same run. `printer.*` values reach it through its expressions. No cache key takes the document's path, handle or name.
8. A new expression name is a parameter name of the document or a dotted name under `printer`. M2 adds no other dotted-name namespace. A dotted name outside `printer` stays an unknown value (`UnknownValue`, expressions.md section 4). M4 gives no dotted name a scope (decision 3).
9. A new naming rule builds element names from the document's feature ids and generators (naming.md section 3.1). No rule writes a file, document or occurrence name into an element name. The `@<feature>:<n>` group keeps naming the copies of pattern and mirror features.

**What M4 fills in.** model.md and file-format.md: the `components`, `occurrences` and `joints` records, a linked component's relative path, the per-scope id rule, edits and transactions inside a local component, and the migration step into M4's format version. naming.md: how an occurrence's elements are listed, how a qualified reference resolves or is lost, with its candidates, and how a feature that reads an occurrence's geometry (a projection of its edges, a derived body, a boolean tool) names what it makes from it. That rule keeps one naming map from holding two elements of one name when two occurrences of one component, or two scopes that hold the same feature id (decision 5), meet in it. recompute.md: each component's timeline built as a unit from its own records, its occurrences' results, each occurrence's placement and parameter overrides, and the session's printer values. Its cache keys name no document. Two occurrences with the same overrides then share results. expressions.md: an override names a component's parameter by its id, never by its name. protocol.md, engine.md, ui.md and python-api.md: `occurrence` beside `body` in picks, element descriptors and uses, and the commands for components and joints.

## Alternatives considered

The plan settled the timing (choice 26). Its options: (a) an ADR in wave 1 that fixes how a record and a reference name their component scope, with no code; (b) components built in M2; (c) everything decided in M4. It picked (a), the safest: M2's new records are written component-ready, and M4 needs no content-rewriting migration. This record does not reopen it.

The choices below are each Accepted (owner's rule of 2026-11-05): the most open-source approach, then the safest, then the industry standard, then this work's recommendation. Every option is equally open: plain JSON in a format under Apache-2.0. The safest decides most of them.

1. *How a record names its scope.* (i) By containment: a record is in the scope whose array holds it, and a local component holds the same three arrays as a document; (ii) a `component` field on every record, with every record in the document's flat arrays and absence meaning the root; (iii) the component's id as a prefix of every record id. The rule takes (i), the safest. A local component has the shape of a document's root scope. Extracting it into a linked file, or bringing a linked file in as a local component, moves records unchanged. Under (ii), an extraction removes a field from every record. Every reference needs a check against its target's field. Under (iii), every id changes when its record moves, and with it every element name that starts with a feature id. Containment is also how open formats that nest definitions work: a KiCad hierarchical sheet is a schematic file of its own, placed by a sheet symbol.
2. *How a reference names a target in another scope.* (i) An `occurrence` path beside the target's id field; (ii) a path inside the id string, such as `o-lid/b-1`; (iii) an occurrence prefix inside the element name `q`. The rule takes (i), the safest. It adds one optional field and changes no existing value. Under (ii), the type of every id field changes shape. Under (iii), the naming grammar changes. The resolver then parses scopes out of names. A path of placed instances is the industry standard: Fusion's occurrence paths, STEP's next assembly usage occurrences and KiCad's sheet paths name a placed part that way. The field takes Fusion's word for a placed component. naming.md already calls the copies of a pattern instances (`@<feature>:<n>`, `ElementName::with_instance`).
3. *Which way a reference may cross.* (i) Downward only, into the occurrences a scope places; (ii) any way, with references into parent and sibling components (in-context design). The rule takes (i), the safest. A component builds the same wherever it is placed. Occurrences cannot form a cycle. Under (ii), a component's result depends on where it is placed. Its file no longer builds on its own. A later version can add another path form for upward references without rewriting any record.
4. *Where ids are unique.* (i) Within a scope; (ii) within a file, across all its scopes. The rule takes (i), the safest. Under (ii), bringing a linked file in as a local component needs new ids. Bringing two files written by `SequentialIds` into one file as local components needs new ids too: both start at `f-000000000001`. New feature ids change every element name and every stored reference built on them. That is the content rewrite this ADR exists to avoid. Under (i), M4's edits and commands name a local component's scope as well as an id. That is a new field, not a changed one.
5. *The frame of stored coordinates.* (i) The scope's own frame, with each occurrence's placement mapping it outward; (ii) the root's frame for every record. The rule takes (i), the safest. Moving an occurrence or a joint changes no stored record. A linked file needs no rewrite when it is placed. Under (ii), every placement change rewrites the coordinates and fingerprints of the component's records. It is also the industry standard: STEP assemblies keep each part's geometry in its own frame, with a transform for each placement.
6. *The printer of a linked file.* (i) The printer of the document the session builds gives `printer.*` values to every scope of that build; (ii) each file's own printer applies to its own scope. The rule takes (i), the safest for the print. A part fits on the printer it is printed with. One build prints on one printer. Under (ii), a linked threaded cap keeps the clearances of the printer its own file names. That printer may not be the user's. The linked file's stored profile stays in it, untouched.
7. *Reserving names now.* (i) Keep `occurrence` free at any depth and the root keys `components`, `occurrences` and `joints` free, with a schema test; (ii) reserve nothing and rename in M4 if needed. The rule takes (i), the safest. M2 adds eight feature types and many value types. One of them could take one of these names for something else. Under (ii), M4 would then need a migration that rewrites that key.

## Consequences

- M2 builds nothing for components. Format version 3's records and the protocol additions keep the nine rules above. Each M2 spec's critic checks them.
- file-format.md section 3 gains the scope rules and two schema tests of the reserved names, by handoff from this step. protocol.md gains the same test for the protocol schema. model.md, naming.md and recompute.md name this ADR where they defer components. architecture.md's document model names the scope rule.
- M4 adds `components`, `occurrences`, `joints` and `occurrence` with a format version of its own. The step that migrates a document into that version changes only the version number. Every M1 and M2 document opens in M4 with the same meaning: one root scope and no occurrences.
- M4's edits, transactions, `list_uses`, fixes and picks need a scope or an occurrence path for records outside the root. Each is a new optional field. M1 and M2 hosts send none and keep addressing the root scope.
- Two files written by `SequentialIds` can become local components of one file with no change of id.
- Downward-only references rule out in-context design across components in v1. A box with its fitted lid stays a multi-body part (technical design section 9): both bodies sit in one scope and reference each other freely.
- A linked file prints with the printer of the document that places it, not with its own.
- The decision changes the meaning of no M1 file and no code. It goes to human review at the M2 gate with format version 3.

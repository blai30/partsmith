# W2-2D-1: Thread and clearance-hole tables, designations and editions

Status: Accepted (owner's rule of 2026-11-05): the M2 plan's open choices "Size range and data form of the thread tables", "How a thread size is typed in params, the manifest and the inspector" and "Versioning of table values", decided as the wave 2 decisions of 2026-11-19 accept them ([m2-wave2-decisions.md](../design/m2-wave2-decisions.md) section 2 item 7 and section 3). Needs human review at the M2 gate (m2-plan.md gate 19) for three things: the provenance of the ISO and ASME values kept in the repository under Apache-2.0 (choice 16), the meaning a stored designation gets in format version 3 with its edition rule, and the note to [ADR 0051](0051-corpus-coverage-checks.md) on example coverage. It specifies [features/thread.md](../spec/features/thread.md) sections 2 to 4, 8 and 9 and delivery.md section 2.8's series rule. The `FieldHint` member that names a table and the protocol route of the rows are track 3A's (stage 3), under the protocol review. No dependency changes.

## Context

- **Choice 16.** m2-plan.md section 7.3 item 16 picked ISO 261 and ISO 262 coarse and fine threads with ISO 965-1's classes 6H and 6g, ASME B1.1's UNC and UNF with classes 2A and 2B, and ISO 273's clearance holes (fine, medium and coarse as close, normal and loose), "kept in the repository under Apache-2.0 with each source named in the spec". It named no size range and no data form.
- **Who reads the tables.** The thread (item 20) and the tapped and clearance holes (item 21, "a pick, not a lookup") read the same rows. The UI and Python need the rows to offer them. Gate 3 asks for examples of tapped hole sizes, gate 6 for "a tapped hole after a size change".
- **The coverage checks.** Runner test 7 of delivery.md section 2.8 asks for an example of every option value of every manifest, with no exceptions (ADR 0051). Features.md section 3.3 makes a hint's `options` list exactly the schema enum's values.
- **The file format.** Version 3's records reach production from wave 2's code on (file-format.md section 3.9 rule 3), and every value a version 3 build has written keeps its meaning until the gate (rule 2). Whatever a stored size means is fixed from the first build that stores one.

## Decision

1. **Sizes.** ISO 262's selected sizes M1 to M64 with ISO 261's coarse pitch and ISO 262's fine pitches (74 sizes); UNC from #1 to 1-1/2 and UNF from #0 to 1-1/2 (47 sizes); ISO 273's clearance holes for the same 34 diameters (features/thread.md section 3).
2. **Data form.** The rows are constant data in `partsmith_features::threads`. The derived dimensions (H, D1, D2) and the classes' deviations are computed from the standards' formulas, not stored: ISO 68-1 and ISO 724 for the basic dimensions, ISO 965-1's fundamental deviations and ASME B1.1's allowance for the classes ([ADR W2-2D-3](W2-2D-3-the-modeled-thread-profile.md)). Tests check every derived value against values the standards print, and a pinned file holds every row (features/thread.md tests 4 to 6 and 20).
3. **Typing.** A record stores a standard (an enum, `iso_metric` or `unified`) and a size as a text, its designation. The core checks the text against its table. A text that writes one size another way gets a fix that sets the designation, and a text that names no size gets none (features/thread.md sections 4.2 and 9, alternative 7). The sizes are not enum values in either schema.
4. **Spelling.** `M8x1.25` (every metric size names its pitch), `1/4-20 UNC`, `#10-24 UNC`, `1-1/2-6 UNC`, and `M3` for a clearance hole (features/thread.md section 4.1). The class is not part of the designation: each standard has one class per kind in M2.
5. **Editions.** The rows and formulas are the M2 edition. It is fixed from the first merge of code that builds a stored size (file-format.md section 3.9 rule 2), and frozen for good when the gate reviews format version 3. Every row is checked against the standards' current texts before that merge (features/thread.md open issue 2). A new row may come in any later release. A corrected row or formula is a new edition, before the gate as after it. A record selects it with an optional key whose absence means the M2 edition (features/thread.md section 3.5).
6. **Coverage.** Runner test 7 also asks, for every hint that names a thread table, for an example of each series of that table: ISO metric coarse, ISO metric fine, UNC and UNF (delivery.md section 2.8, tests 167 and 168). The rows themselves are held by features/thread.md's tests. This is a note to ADR 0051: its rule "every option value has an example" covers a table's series, not its 121 sizes. Gate 3's "tapped hole sizes" is read the same way, an example of each series (an m2-plan.md note). Track 3A's tests build a modeled thread, external and internal, of the first and the last size of each series (features/thread.md, the tests from 21).
7. **Hosts.** Features/thread.md section 8 states what a host needs from the tables. Track 3A writes the member and the route.

## Alternatives considered

Each choice states its options, the pick and the owner's rule's reasons in order: the most open-source approach, the safest, the industry standard, then this work's recommendation. Every option keeps the data in the repository under Apache-2.0. The first criterion picks none of them.

1. *Size range.* (i) ISO 262's selected sizes M1 to M64, UNC #1 to 1-1/2 and UNF #0 to 1-1/2; (ii) only a printable range (for example M2 to M30, #4 to 1/2); (iii) all of ISO 261 (every pitch, M1 to M300). The rule takes (i), the safest. ISO 262 selects from ISO 261 the sizes for bolts, screws, studs and nuts, and every row of (i) mates a standard fastener. (ii) refuses some of those sizes (M1.6 in small electronics, M36 and up on large prints). A user who needs one models the thread by hand, without the class's limit, the clearance or the truncation. (i) stops at M64 and at 1-1/2 in, the end of ISO 262:1998's selection and of the UNF series. Larger fastener sizes (UNC up to 4 in) can come as new rows. (iii) adds several times the rows, most of them sizes no standard fastener has. Each row is a value that features/thread.md open issue 2 checks against the standards' texts before it is fixed, and any of them can still come as a new row in a later release without changing a stored record (features/thread.md section 3.5). The industry tools' tables are wider than (i): FreeCAD's metric list also has ISO 261 sizes outside ISO 262's selection, such as M1.1, M2.2, M4.5, M9 and M11. Every size of (i) is among them. Safety decides before the industry standard.
2. *Data form of the deviations.* (i) The standards' formulas with cross-check tests; (ii) the standards' printed tables, row by row. The rule takes (i), the safest: one formula per class replaces about 70 hand-entered numbers, and tests check it against printed values. The wave 2 decisions of 2026-11-19 (section 2 item 5) fix it.
3. *Typing a size.* (i) A closed Rust enum of every size; (ii) a standard enum and a size text checked against the core's table, with a fix for a near match; (iii) a series enum and major diameter and pitch expressions checked against the table; (iv) a hint whose options depend on another field. The rule takes (ii), the safest. (i) writes every size into `ptsm.schema.json` and `protocol.schema.json`, needs format version 4 for any later size, and needs an example per size under runner test 7. (iii) stores numbers that can disagree with every row. (iv) is a new protocol hint kind for a list that never changes within a session. Fusion's thread data names a size by its designation text (`ThreadInfo.threadDesignation` in its API), the industry standard.
4. *Spelling.* (a) `M8x1.25` with every pitch named; (b) `M8` for coarse sizes and `M8x1` for fine ones. The rule takes (a), the safest: one form per size, and a record always says its pitch. A typed `M8` gets the fix to `M8x1.25`. (b) is how a drawing writes coarse threads, and the lookup accepts it as a near match.
5. *Editions.* (i) Fixed from the first stored size and frozen at the gate, corrections as a later edition selected by an optional key; (ii) tables named by edition from M2 on, every record storing its edition; (iii) values that may change with a release. Safety separates (iii) from the others: it would rebuild a saved document with other geometry. (i) and (ii) are as safe as each other. Under both, a stored record keeps its geometry in every release, (i) by the rule that a missing key means the M2 edition, as choice 13's font rule keeps a font's glyphs. Neither is a practice of other CAD tools that this work can cite. The industry standard does not separate them. The rule takes (i), this work's recommendation and the simpler: no record carries a key until a correction exists.
6. *Coverage of sizes.* (i) An example per size; (ii) an example per series, by a note to ADR 0051; (iii) a listed exception in delivery.md. Safety separates (iii): it leaves the series untested. What (i) adds over (ii) is a build of every size. Every size's geometry comes from the same code with other numbers. features/thread.md test 17 holds every row to the kernel's limits, and track 3A's tests build the first and the last size of each series, the smallest and the largest pitch and diameter. With those, safety does not separate (i) from (ii). No industry standard covers example suites. The rule takes (ii), the planner's recommendation: sizes are not options, the tests of features/thread.md hold the rows, and an example per series shows each series builds. (i) adds 121 examples that runner tests 4 and 5 rebuild and export to four formats on every run.
7. *Which texts get a fix.* (a) A text that writes exactly one row another way: other case or spaces, `×` or a decimal comma, trailing zeros, a coarse size without its pitch, a unified size without its `#` or its series (features/thread.md section 4.2); (b) also the row nearest a text that names no row, by major diameter and then by pitch (`M9` to `M8x1.25` or `M10x1.5`, `M8x1.5` to `M8x1.25`); (c) no fix, only the message. The wave 2 decisions of 2026-11-19 accept "a fix that offers the nearest match" (section 3). This ADR reads it as (a): the nearest match is the row the text names. Safety rules out (b). It offers a size of another diameter or pitch, and a user who applies it models a thread that does not mate the part the text named, with nothing in the model to show it. (a) and (c) are as safe as each other. Fusion and FreeCAD pick a size from lists and have no typed size to fix. No industry standard separates (a) from (c). The rule takes (a), the planner's recommendation as the decisions accept it. (c) makes a user retype `M8` as `M8x1.25`.

## Consequences

- features/thread.md sections 2 to 4, 8 and 9 and tests 1 to 12 and 20 specify the tables, the lookups and their messages. Track 3A adds the `FeatureError` variants of section 9 to features.md section 4.1, the thread record and the hole's size key to file-format.md section 3.9's version 3 row, and the `FieldHint` member and the route to model.md and protocol.md.
- delivery.md section 2.8's runner test 7 gains the series rule, held by tests 167 and 168. ADR 0051 gets a note (the stage close writes it from this ADR's hand-off).
- The tables' values become part of what a stored size means from the first merge of code that stores one. features/thread.md open issue 2 checks every row against the standards' current texts before that merge, and gate 19 reviews them with format version 3.
- Python writes designations as strings and keeps no copy of the tables (track 4B).

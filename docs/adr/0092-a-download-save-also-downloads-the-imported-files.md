# 0092: A download Save also downloads the imported files

Status: Accepted (owner's rule of 2026-11-05): ui.md open issue 45, which ADR 0064 left to the first caller of a picked file, and plan choice "A download Save of a document holding picked assets", option (i). It binds wave 3's font assets too. No file format, protocol, naming, license, dependency or desktop change. It changes the UI's Save and Save as on a browser without the File System Access API (Firefox and Safari, ui.md 1.1).

## Context

- **What a download Save does in M1** (ui.md 3.19, read at 0f578c1). Without the File System Access API, `chooseSaveTarget` gives a download target, and Save as writes the document with `files.write`, which clicks an `<a download>` of an object URL. The page reads no folder there, and the core held no asset. Step 3 of the write says a download target never reaches the asset step.
- **What changes in M2.** [ADR 0091](0091-step-import-in-the-ui-and-the-cli-through-import-step.md) imports a picked STEP file on every browser, through a file input where the API is missing. `save_document` then returns the file, and the page cannot write it next to the downloaded document. The next open of that document reports `asset_missing`.
- **What browsers do with several downloads** (their documentation and settings, not measured here, ui.md open issue 47). A download lands in the browser's download folder, under the name the page gives, or that name with a number when a file of that name is there (Firefox and Chromium add ` (1)` before the extension). No browser lets a page choose a subfolder. Chromium asks once per site before a page starts a second download without a new click ("Download multiple files", its "Automatic downloads" setting). The download target is used only where the API is missing, which in ui.md 1.1's browsers means Firefox and Safari. A Chromium browser without the API would take it too, with Chromium's prompt (E-178 runs Chromium with the API deleted). Firefox saves each download to its folder without a prompt unless the user turned on "Always ask you where to save files". Safari asks once per site before the first download ("Do you want to allow downloads on ...?") unless the user changed the site's Downloads setting.
- **What the page sees.** Nothing tells the page that a browser blocked or dropped a download: the click on `<a download>` throws nothing either way. A save whose download was blocked still goes on to `markSaved`, and the document is then reported saved.
- **The order of writes.** file-format.md 3.11 and [ADR 0036](0036-hosts-write-assets-first-and-check-them-against-the-engine.md): a host that writes into a folder writes the assets before the document. A document in that folder then never names a file that is not there. A download writes into no folder: the user moves the files by hand, and that order protects nothing there.

## Decision

1. **The steps** (ui.md 3.19, writing the document, step 3). For a download target, when `save_document` returned assets, the page downloads the document first, as in M1. Then it downloads each asset, in the result's order (sorted by name), through `files.write({ kind: 'download', name }, kind, bytes)`, under its asset name (`<64 hex>.step`, `.ttf` or `.otf`). The file kind is `step` for a `.step` asset and `font` for the others, which gives the media type of `FILE_TYPES` (`model/step`, `font/sfnt`). Then it sends `markSaved`. A download that throws stops the save with the Save message of its reason, as a failed document write does: nothing after it is downloaded and no `markSaved` is sent.
2. **Why the document comes first.** A prompt or a setting that applies to a page's later downloads and not to its first, such as Chromium's "Automatic downloads" (Context), blocks the second download and the ones after it, and the page does not see it. With the document first, such a block loses only assets, copies of files the user picked, which "Choose file..." adds again (decision 4). With the assets first, it would lose the document while the page marks it saved, and the browser would then let the tab close without asking. A prompt before the first download, as Safari's, blocks the document in either order, as it blocks M1's one download. Firefox without "Always ask you where to save files" saves every file in either order. The gate's human check records what each browser does (decision 5).
3. **The message.** After the last download, the persistent info notification `download_asset` (one asset) or `download_assets` replaces `download_hint` for that save: "{file} and its imported file are in your downloads folder. Move the file named {asset} into a folder named assets next to {file}, or Partsmith cannot find it when you open {file} again." With more than one asset: "{file} and its {count} imported files are in your downloads folder. Move the files whose names end in .step, .ttf or .otf into a folder named assets next to {file}, or Partsmith cannot find them when you open {file} again." It shows after every download Save with assets, not only the first of a session, since the user moves files by hand each time.
4. **The way back.** An opened document whose assets the page cannot read (no folder in Firefox and Safari) shows `assets_unsupported`, which now names the action: each import's `asset_missing` message offers "Choose file..." ([ADR 0091](0091-step-import-in-the-ui-and-the-cli-through-import-step.md) decision 5). Picking the downloaded file, or the file first imported, adds it by its name, and the import builds.
5. **The test.** E-178, tagged `@engines`, runs in Firefox and WebKit (and Chromium with the API turned off, as the download E-tests do). It imports `S`, saves, and checks that the page downloaded exactly two files, `Untitled.ptsm` then `S`, with the document's text and the bytes of `S`, and that `download_asset` shows. Playwright accepts every download, and the browsers' own prompts are a human check at the gate (m2-plan.md gate 20's preview review in Chrome, Firefox and Safari). The reviewer records what each browser asked and whether a file was missing from the downloads folder while the notification said it was there (ui.md open issue 47).

## Alternatives considered

- (i) **Download each asset too** (chosen), the document first.
- (ii) **Refuse the save with a warning.** The work is not saved at all on Firefox and Safari.
- (iii) **Offer Import only with the File System Access API or on the desktop.** Firefox and Safari users lose the command that m2-plan.md item 22 gives every host. Gate 17's `@engines` subset includes import.
- (iv) **Warn at import time and keep M1's save.** The document downloads without its file, and the warning comes before the user has anything to move.
- (v) **A zip of the document and its assets.** That is the `.ptsz` bundle of M4 (m2-plan.md section 5.2), a format of its own that every host must open. Not in M2.

The rule takes (i). (i) to (iv) are the project's own code, and (v) would need an archive library or a writer of our own. Open source does not tell them apart. (i) is the safest: nothing is lost on Firefox and Safari, and gate 17's `@engines` import test can pass there. (ii) loses the work, (iii) loses the command and (iv) loses the file. The industry standard where no folder can be written is (i): web slicers and editors that export a model with its textures download each file. The plan recommends (i), with the message that says where the files go.

For the order: **the assets first**, as file-format.md 3.11 orders a folder write, or **the document first** (chosen). Both are the project's own code. The document first is the safer, for the reason of decision 2: where a block hits only later downloads it costs an asset the user can add again, never the document, and where it hits the first download or none, the order changes nothing. No standard covers the order of several downloads. The plan named no order.

## Consequences

- A download Save of a document with imports puts more than one file in the downloads folder, and the user moves the asset files by hand. A renamed duplicate (`<hash> (1).step`) does not match its name: "Choose file..." still adds it, since the core checks bytes, not file names.
- A download Save writes the document before its assets, the reverse of a folder write. file-format.md 3.11's order still binds every write into a folder, and its sentence on downloads says what a download Save writes since M2.
- Wave 3's fonts follow the same steps with no change to this ADR.
- M4's `.ptsz` bundles end the hand move. This ADR is then superseded for documents saved as bundles.
- The browsers' prompts are not measured in CI. ui.md open issue 47 records what the gate's human check finds.

# 0055: A re-attach by pick asks the engine for the plane

Status: Accepted (owner, 2026-11-05): option (a), the query command `attach_plane`, as wave F's reattach track built it. It changes the protocol schema: a new command, `attach_plane`, and its result (ADR 0016's entry of 2026-11-04, accepted with it). The rule it builds is the owner's decision of 2026-11-04 on ADR 0023: a host's re-attach by pick follows engine.md section 3.22's rule. This ADR does not reopen that decision. The owner also accepted the two open choices as built: (ii) for unknown motions and (i) for what "not offered" means for a pick. A new base of a datum plane follows the same rule (Accepted (owner, 2026-11-05): option (a) of engine.md open issue 23). Wave G builds it through this command (the amendment of 2026-11-05 below), with the choices the owner's rule settles there, each Accepted (owner's rule of 2026-11-05).

## Context

- **The rule.** The faces built from a sketch inherit its motion: the motion of its stored face just before it when its fallback is in body coordinates, the identity for a fallback in world coordinates or an origin plane, and the datum's motion for a datum plane (features/sketch.md section 3.3). Later features store fallbacks and axis directions in the body coordinates of those faces. A stored plane that changes the sketch's motion moves those later features with no message. engine.md section 3.22 stores `Attach`, `TurnDrawingBack` and drag commits in the coordinates that keep the motion. It does not offer an `Attach` that no coordinates keep it for (ADR 0023, amendment 1).
- **The pick did not follow it.** The UI's re-attach by pick (ui.md section 3.16.1) kept a sketch without motion in world coordinates. For every other sketch it stored a picked face in body coordinates, as a new sketch does. It stored an origin or datum plane as picked. A sketch on a face that a Move body moved, re-attached to a face that moved otherwise or to an origin plane, then got another motion. The features built on its faces moved (engine.md open issue 16, ui.md open issue 25).
- **The owner's decision.** On 2026-11-04 the owner decided that a re-attach by pick follows section 3.22's rule: a re-attach that no stored frame keeps the sketch's motion for is not offered. The other option, re-basing the fallbacks and directions of later features in the same batch, was declined.
- **What the UI can see.** Descriptors are at the display state. A lost face has none. The UI cannot read the motion of the sketch's stored face just before the sketch. A datum's motion is computed from its frames (features/datum_plane.md section 3.2 step 4). No message carries it. The UI can tell only that a sketch on an origin plane or with a world fallback has no motion (its motion is the identity). That leaves out every face sketch saved since format version 2 and every sketch on a datum plane. The rule needs the engine.

## Decision

1. The protocol gains command 35, `attach_plane {doc, feature, plane}`, in the Sketch group. Its result is `{plane: Option<SketchPlane>}`, with `plane` absent for none. The command records nothing and emits nothing (protocol.md section 2.5, engine.md section 3.22). A new command does not bump `PROTOCOL_VERSION` (protocol.md section 2.9). Its result carries `SketchPlane`, a closed file-format type that no result carried before (protocol.md section 3.6, test 87).
2. The engine reads the latest recompute as `solve_sketch` does. A sketch that did not run there, because it comes after the focus feature or at or after the rollback marker, is read in a recompute without the stop point and the marker, made for the command only. The features before it that did not run would otherwise give it the wrong motion. It compares the motion the sketch's stored plane gives it with the motion the given plane would give it: unchanged for an origin or datum plane whose motion matches, and for a face in its own coordinates when those keep the motion, else in the other coordinates when they keep it, else none. Two motions match when each of their 12 components differs by at most 1e-9, for `Attach`, `TurnDrawingBack`, drag commits and `attach_plane` alike. A sketch whose datum has no plane (it failed or did not run) has an unknown motion and gets any plane unchanged. A picked datum plane whose datum has no plane has an unknown motion too. It gets no plane. A face stands where it stood just before the sketch, the fallback a host sent moved by the face's motion there. A sketch without motion stands where the host's descriptor showed the face instead: the fallback moved by the face's motion at the display state. The two differ only for a face that moves after the sketch.
3. The UI builds the plane as for a new sketch, then, in one task of its mutation queue, checks the pick, asks with `attachPlane` and commits the plane it returns, as one undo entry labeled "Attach '{label}'". A pick the engine gives no plane for commits nothing and shows the hint `attach_moved` in the sketch hint. The pick stays open (ui.md sections 3.16.1 and 4.3). The `attach_after` refusal stays in the UI and comes first. A datum plane that is suppressed or has an error is refused in the UI with `attach_datum_unbuilt` before the engine is asked. `attach_moved` would say something untrue about it. Both refusals read the document when the task runs, not when the pick is made. They see a suppress queued just before the pick.
4. Re-basing later features stays declined, as the owner decided.

## Options considered

- **(a) A query command, `attach_plane` (chosen by the owner on 2026-11-05; built in wave F).** One command and one result, no new error code. The UI keeps building the edit and its undo label. The rule stays in one place in the engine with `Attach`.
- **(b) An applying command, `attach_sketch {doc, feature, plane}`.** The engine stores the plane itself as one undo entry and fails with a new error code when no plane keeps the motion. That saves one round trip, but the undo label, the refusal message and the `attach_after` check move into the engine. The protocol gains an error code as well as a command.
- **(c) A field on `pick_reference`.** `Pick` gains an optional `sketch`. The descriptor of a flat face gains the plane that keeps that sketch's motion. Origin and datum planes are not picked through `pick_reference`. They would need a second addition (a flag on the sketch's solution, and a motion for each datum), two schema changes for one rule.
- **(d) `apply_edits` refuses the edit.** An `update_feature` that changes a sketch's motion fails with `edit_rejected`. No schema change, but the same edit from Python, the CLI or a file is refused too. The UI can show only the core's message, not the hint.
- **No change in the core.** The UI alone would have to refuse every pick of a sketch whose motion it cannot see (almost every re-attach of a sketch made since format version 2), or keep its old rule. The owner's decision replaced that rule.

## Open choices (accepted by the owner on 2026-11-05)

### 1. Unknown motions

The owner's decision names re-attaches that no stored frame keeps the sketch's motion for. It does not say what happens when a motion is unknown: a sketch on a datum plane whose datum has no plane in the latest recompute (suppressed, failed or not run), or a picked datum plane in that state. Once such a datum builds again, its motion becomes the motion of the sketches on it. The options:

- **(i) Take the plane in both cases.** This was the spec before the review of 2026-11-04. A sketch picked onto a datum that does not build can move later features once that datum builds again.
- **(ii) Refuse a picked datum plane with an unknown motion, and take any plane for a sketch whose own motion is unknown (chosen by the owner on 2026-11-05; built in wave F).** The engine gives no plane for such a datum. The UI refuses one that is suppressed or has an error with `attach_datum_unbuilt` before it asks. A sketch whose own datum does not build can still be moved off it. The motion that datum gave it before is unknown. Later features that stored placements on its faces read them with the new plane's motion.
- **(iii) Refuse both.** A sketch on a datum that does not build cannot be re-attached by pick until that datum builds again.

### 2. What "not offered" means for a pick

The owner's decision says a re-attach that no stored frame keeps the sketch's motion for is not offered. For `Attach` that means the action is not in the message's list. A pick has no list: any face in the view and any plane row can be clicked. The header's three origin plane buttons are the one place the UI offers planes. The options:

- **(i) Refuse when picked (chosen by the owner on 2026-11-05; built in wave F).** Every plane and face stays pickable, the three buttons included. A pick the engine gives no plane for stores nothing and shows `attach_moved`. A sketch on a moved face sees Top, Front and Right enabled. Each click shows the hint.
- **(ii) Dim the refused origin planes.** When plane picking opens for a re-attach, and again after each change while it stays open, the UI asks `attach_plane` for XY, XZ and YZ. It marks the buttons the engine refuses as unavailable, with `attach_moved` as their reason. Faces and plane rows are still refused when picked. That is three more queries per opening and per change. Each is a whole recompute for a sketch the marker holds back. No schema change.

## Consequences

- `docs/format/protocol.schema.json` and the UI's generated types gain the command and its result. `crates/partsmith-protocol` lists 35 commands. Python and the CLI have no re-attach by pick and do not send the command.
- Tests: engine.md 166 and 167, protocol.md 88 (with 34 and 87 updated), ui.md U-146, U-250, E-108 and E-165 with the fixture `reattach-moved.ptsm`. engine.md open issue 16 and ui.md open issue 25 are resolved.
- A sketch without motion re-attached to a face that a Move body after the sketch moved stands where the descriptor showed the face, as the UI's earlier rule placed it. The placement is now in body coordinates, and those keep its identity motion just before the sketch. The same pick gives the same plane with the marker before or after that Move body (engine.md test 166 (f)). The descriptor's `fallback` as built would put the sketch where the Move body's inverse takes that placement, 100 mm beside the face in test 166 (f).
- A re-attach of a sketch at or after the rollback marker, or after the focus feature, costs one more recompute: the whole recipe without them.
- `attach_moved` says that the sketch and the picked plane do not move together. It names no feature that moved either of them: the engine does not report one. Naming it needs a field in `attach_plane`'s result, another schema change, left for after M1.
- Two motions match within 1e-9 per component (engine.md section 3.22). A datum's motion is computed from its frames and can differ from its face's motion by rounding (0.09999999999999964 mm for 0.1 mm, engine.md test 166 (g)). An exact comparison would refuse such a datum with a hint that is not true. `Attach` and drag commits use the same comparison, also for a sketch on a datum plane.
- A new base of a datum plane can move later features the same way a re-attach could (an inspector pick, or `UseReferences` or `KeepMatch` on its `base`). The owner's decision of 2026-11-04 does not cover it. On 2026-11-05 the owner chose option (a) of engine.md open issue 23: such a new base is refused while later features build on the datum's sketches, as `attach_plane` refuses a re-attach. Wave G builds it (the amendment of 2026-11-05).
- The owner's choices of 2026-11-05 are the ones wave F built. The code and the tests above stay as they are.

## Amendment of 2026-11-05: a datum plane's new base

Status: Accepted (owner, 2026-11-05): option (a) of engine.md open issue 23. The choices below that the decision leaves open are Accepted (owner's rule of 2026-11-05).

A datum plane passes its motion on to the sketches on it (features/datum_plane.md section 3.2 step 4), and a datum plane on it passes the same motion on. The faces built from those sketches pass it on to the fallbacks and directions later features store on them. A new base that changed the datum's motion moved those later features with no message, as a re-attach of a sketch did before this ADR. The ways to give a datum plane a new base are a pick in its inspector field Base plane, and the repair actions `UseReferences` and `KeepMatch` at its `/base/face`. The owner chose (a) on 2026-11-05: such a new base is refused while later features build on the datum's sketches, as `attach_plane` refuses a re-attach.

**The rule** (engine.md section 3.22, *A datum plane's new base*). A new base of a datum plane `P` is refused when three things hold. Later features build on `P`'s sketches: a `Use` of `list_uses` names a sketch on `P`, or on a datum plane on `P` at any depth, with another feature as its user. The motion `P`'s old base gives it, `d`, is known. The old base is `P`'s base when the open transaction began, and outside a transaction its base now. The motion `P` would pass on with the new base, `n`, is unknown or does not match `d` within 1e-9 per component. Both are read in the state just before `P` in its run: the latest recompute, or a recompute without the stop point and the marker when `P` did not run there, as for a sketch. One engine helper gives both: the motion the registry builds for `P` with its record holding that base alone, in that state.

**The choices the owner's rule settles.** Each is Accepted (owner's rule of 2026-11-05).

1. *How the inspector asks the core.* The options: (i) `attach_plane` answers for a datum plane too, with the same request and result; (ii) a new query command for a datum's base, with a protocol type for it (the protocol schema does not describe the features' `PlaneRef` today); (iii) `apply_edits` refuses the edit with `edit_rejected`; (iv) the UI refuses every new base of a datum whose sketches later features use, without asking. The rule takes (i). It adds no command, type or error code, and the protocol schema changes in two descriptions only (ADR 0016's entry of 2026-11-05). The rule stays in one place with the sketch's. (ii) adds a command and a type for the same answer. (iii) would refuse Python and every other host too, and the inspector would learn of it only from a failed preview, which is this ADR's option (d) for a sketch. (iv) refuses new bases that keep the motion, such as Top to Front for a datum on an origin plane. For a datum plane the host builds `plane` as for a sketch, and the command does not read a face's `fallback` and `fallback_frame`: a datum plane stores neither. A request for a datum plane failed with `not_a_sketch` before. Every request answered before means the same, and `PROTOCOL_VERSION` stays 1.
2. *A datum whose old base gives no motion.* The options: (i) refuse every new base when `d` is unknown; (ii) keep every new base whenever `P` has no plane in its run, as this amendment first had it; (iii) keep every new base only when the old base gives no placement (a lost face, or a datum with no plane), and read `d` from the old base when `P` fails for another reason or a preview in the open transaction changed it. The rule takes (iii), the safest. Under (ii), a datum that failed for any reason, such as an offset that does not evaluate, took any base. Inside the inspector's transaction, (ii) also compared a pick with the preview of the pick before it. (i) would leave a datum whose base face was lost without a repair while later features build on its sketches, and (iii) keeps that repair, as open choice 1 (ii) above does for a sketch whose datum has no plane.
3. *A new base whose motion is unknown*: a datum plane that has no plane in the run or comes at or after `P`, or a face that gives `P` no placement. The options: refuse it, or keep it. The rule takes refusing it, as open choice 1 (ii) refuses a picked datum plane with no plane. Keeping it would store a base that gives `P` no placement. `d` would then be unknown, choice 2 would keep any base after it, and two edits would get past the rule.
4. *A cause's revert of the base* (engine.md section 3.21). The options: leave such a revert out while the base it restores is refused, or offer it as before. The rule takes leaving it out, the safest. A base change is allowed while nothing builds on the datum's sketches. Its revert can then change the motion back after features were built on them. A sketch's revert has no such gap. A re-attach is refused whenever it changes the motion, and the revert restores a motion the sketch had.
5. *`TurnDrawingBack` and `KeepRegions`.* Each fixes a sketch or a profile and also renames references later features store, a later datum's base face among them. `TurnDrawingBack` renames a face to another face the same feature made from the same sketch, and the datum's motion stays. `KeepRegions` renames a face to the name of the face it resolves to now. That name's motion can differ, as it can for a later sketch's face plane in body coordinates, which engine.md section 3.22 does not check either. The options: (i) do not offer `KeepRegions` when its rename would give a later datum a refused base; (ii) offer it as before and record the gap. The rule takes (ii). (i) closes the gap for a datum only, while the same rename of a later sketch's plane stays open, and it would build every later feature's edits for each offer of a profile's fix.
6. *A pick of the edited datum itself* (ui.md section 3.7). The options: (i) refuse it in the UI before asking the core, with its own hint; (ii) ask the core like any other pick. The rule takes (i), the safest. The core refuses it only while later features build on the datum's sketches, and its hint `datum_base_moved` would then name the datum as its own target. Otherwise the pick would land and the datum would sit on itself. The new hint `datum_base_self` says what happened.
7. *The Restore of an edit of a datum plane* (ui.md section 3.7). Restore reopens a canceled edit with its saved params, and its first preview would send the saved base without asking. Features built on the datum's sketches in between would then move. The options: (i) ask `attachPlane` for a saved base that differs from the record's before the first preview, and reopen with the record's base when the core refuses it; (ii) reopen as saved. The rule takes (i), the safest.

`apply_edits` still stores any base, from any host, as it stores any plane of a sketch, and undo and redo bring back a recipe as it was.

**The UI** (ui.md sections 2.6, 3.7 and 4.3). While a command edits a datum plane of the document, each pick its Base plane field takes asks `attachPlane` before it lands, from the view, a browser row or the Choose menu. A pick of the edited datum itself is refused without asking, with the new hint `datum_base_self` (choice 6). A pick the core gives no plane for is refused: the field keeps its value, no history step or preview is made, and a hint shows under the field for 3 s. The hint is the first that applies of `attach_after` (a picked datum plane that comes after the edited one), `attach_datum_unbuilt` (one that does not build) and the new `datum_base_moved`. OK waits for a pick on its way. The Restore of a canceled edit asks for a saved base that differs from the record's first (choice 7). A command that adds a new datum plane asks nothing. A repair candidate whose action the core leaves out is listed without one, as before.

**Tests.** engine.md 168 to 170 (169 (d) is a `Keep this match` that would change the motion: a datum on the top of a box joined after a Move body, which merged with the moved cube's top), ui.md U-251 and E-166 with the fixture `datum-base-lifted.ptsm`, and E-108's row for it. engine.md open issue 23 is resolved. protocol.md command 35 says what the command answers for a datum plane.

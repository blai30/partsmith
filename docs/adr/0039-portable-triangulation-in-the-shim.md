# 0039: Tessellation triangulates with the shim's copy of Delabella in double-double arithmetic, the same on every platform

Status: Proposed, needs human review: third-party code copied into the repository (MIT) and changed, its notices entry, and the shim's glue to OCCT's mesher, written against OCCT's installed headers.

## Context

- **The first platforms run.** Run 40315773128 of `platforms.yml` (scheduled, 2026-10-26, commit 2a202ac), job 121568157520 on `macos-15`, found seven examples outside the tolerance of delivery.md 2.8, in 96 lines, all under `/checks/` (delivery.md open issue 1 (d)): `bench/fifty-features`, whose body 0 had 3 open edges at z = 28 on face 50 (`1 error, 29 warnings` instead of `29 warnings`); `cone/pointed` and `cone/apex-below-tolerance`, 5 warnings instead of 4; `cone/frustum` and `cone/inverted`, their thin walls in another order with values up to 0.6 percent off; and `chamfer/pipe-tee` and `fillet/pipe-tee`, their mirror overhangs swapped (print.md 3.7 item 7 orders those now).
- **Delabella's precision is the compiler's.** Since 2026-10-13 (kernel.md open issue 8), tessellation has used OCCT's Delabella algorithm, which triangulates each face's nodes at once instead of inserting them one by one (Watson took 11 to 12 s on the engine's sphere and on `PLATE`). OCCT 7.9.3's `src/BRepMesh/delabella.cpp` computes its lifted coordinate (x² + y²), cross products and orientation tests in `long double` (its typedefs on lines 49 to 53): a 64-bit mantissa with GCC on x86_64, where the expected files were blessed; 53 bits with MSVC and on arm64 macOS, where `long double` is `double`; 113 bits in software with Emscripten. The points of a circle and the cells of a parametric grid are cocircular once mapped into the unit square, every triangulation of cocircular points is a Delaunay triangulation, and so rounding picks the diagonals, differently on each platform.
- **Measured.** Recompiling only OCCT's `delabella.cpp.o` with a 53-bit `long double` and fused multiply-adds (Clang, `-mfma -ffp-contract=on`) reproduced all 29 lines of the macOS log for `bench/fifty-features`. At 53 bits without fused operations, as MSVC builds it, 10 examples failed, `move_body/move-then-fillet` got 6 open edges, and `CDelaBella::Triangulate()` crashed (SIGSEGV) on `revolve/quarter`, `revolve/quarter-reverse`, `revolve/bare-angle` and `revolve/line-direction-sense`: the predicted Windows failures, since the Windows examples step has not run yet. A double-double variant passed the whole corpus against the Linux expected files. On 2026-10-27, kernel.md test 137's face (20 integer points on a circle) gave different triangles with OCCT's copy natively (64 bits) and under WebAssembly (113 bits): two of the 18, and their order.
- **What the evidence does not show.** The cone lines were not reproduced by the Delabella change alone, and no Delabella variant reproduced pipe-tee's swap, so node positions on macOS also differ from Linux's in the last bits: OCCT is built by Apple Clang, which fuses floating-point operations by default, and calls Apple's libm. A deterministic triangulator cannot remove a diagonal that input noise decides.

## Decision

1. **The shim triangulates with its own copy of Delabella, in double-double arithmetic** (kernel.md 3.7 item 2). `cpp/mesh_algorithm.cpp` defines an `IMeshTools_MeshAlgoFactory` that gives each face the algorithm OCCT 7.9.3's `BRepMesh_DelabellaMeshAlgoFactory` gives it, by surface type, with the shim's base algorithm (a `BRepMesh_CustomBaseMeshAlgo` over the copy) wherever OCCT's factory uses its own Delabella base algorithm; cylinders keep OCCT's Watson algorithm as there. `cpp/mesh.cpp` meshes through a `BRepMesh_Context` built with a named algorithm type, never `IMeshTools_MeshAlgoType_DEFAULT`, whose constructor reads `CSF_MeshAlgo` (kernel.md test 113), and replaces its face discretization with a `BRepMesh_FaceDiscret` over that factory. Both meshing call sites, `tessellate` and `element_display`, use that one helper.
2. **Double-double arithmetic** (`cpp/double_double.h`): a value is the unevaluated sum of two doubles, about 106 bits, computed with double addition, subtraction and multiplication alone (Knuth's two-sum, Dekker's product with Veltkamp's split), never a fused operation or a library call, so the same nodes give the same triangles on every platform. `static_assert`s check the algorithm at compile time; they cannot check the code the compiler emits, so `build.rs` passes `-ffp-contract=off` to every compiler but MSVC, whose default `/fp:precise` fuses nothing on x64 (kernel.md 3.12 item 5), and kernel.md test 137, which lists the exact triangles of a cocircular face, guards it at run time on every platform CI and the platforms workflow test.
3. **Every change to OCCT's copy** (from `src/BRepMesh/delabella.pxx` and `delabella.cpp` of OCCT 7.9.3, the tag `V7_9_3`), so a reviewer can `diff` the two:
   1. The files are `cpp/delabella/delabella.h` and `cpp/delabella/delabella.cpp`. The MIT notice stays word for word at the top of each, and a comment after it says the file is the shim's copy and points here.
   2. Everything is in namespace `partsmith::occt::delabella`: OCCT's `IDelaBella`, `CDelaBella` and the other names are in `libTKMesh.a` too, and second definitions in the global namespace would break the static link (LNK2005 on MSVC) or the one-definition rule.
   3. The five `long double` typedefs (`Unsigned28`, `Signed29`, `Signed31`, `Signed45`, `Signed62`) are `DoubleDouble`; `Signed14` and `Signed15` stay `double`, as in OCCT's copy.
   4. The four `assert`s call `require`, which throws `std::logic_error`. OCCT's release build defines `NDEBUG` and compiles them out, while `cc` defines no `NDEBUG`, so they would abort, which the shim never does (kernel.md 3.9 item 7). One of them stops the emergency search for a visible face at the start of the face array, which with the check compiled out walks on past it. The base algorithm turns the exception into a `Standard_Failure`, so OCCT's mesher gives that face no triangulation and `tessellate` fails with `Failed` (kernel.md 3.7 item 7).
   5. Removed: the deprecated `DelaBella()` function with its `printf` default error log, the C interface (`DelaBella_Create` to `GetFirstHullVertex(void*)`) and the header's `#ifdef __cplusplus` around the C++ interface, with the includes only they or nothing needed (`stdio.h`, `search.h`, `malloc.h` or `malloc/malloc.h`, `assert.h`); `cstdlib` (for `malloc` and `free`) and `stdexcept` are included instead. The error log stays, unset by default, and the base algorithm sets none.
   6. Comments that trailed code are on their own lines above it (tabs in them became spaces), the `clang-format off` markers that kept them aligned are gone, and the trailing comment of the header include, which named a `LOG()` macro that no longer exists, is dropped. Identifiers, formatting and every other line are OCCT's.
4. **The glue is the shim's own code.** OCCT's `BRepMesh_DelabellaBaseMeshAlgo.cxx` and `BRepMesh_DelabellaMeshAlgoFactory.cxx` are LGPL and are not copied: `cpp/mesh_algorithm.cpp` is written against OCCT's installed public headers (the base algorithm classes, node insertion, deflection control and the range splitters, header-only templates the shim instantiates as any OCCT header is used) and does what OCCT's base algorithm does, in the same order, so the copy sees the same coordinates: the face's nodes, then the four corners of their bounding box grown by a tenth of its diagonal as auxiliary nodes, all mapped into the unit square, and Delabella's triangles turned counterclockwise in its order.

## Options considered

- (a) **The shim's own factory over a copy of Delabella in double-double arithmetic** (chosen). No OCCT rebuild, no OCCT cache key change and no change to the source route of delivery.md 2.13 (ADR 0034): OCCT stays the unmodified tag. Costs: 1,058 lines of third-party code kept in the repository (`delabella.cpp` 955 and `delabella.h` 103, from OCCT's 1,009 and 107), the renamed notices entry, 173 lines of glue and 125 of arithmetic.
- (b) **Patch `delabella.cpp` in `scripts/build-occt.sh`.** Fewer lines, but OCCT becomes a modified OCCT, whose patch ADR 0034's source route then publishes with the archive (delivery.md 2.13), and every OCCT cache key changes: one cold build each of Linux native (56 min), WebAssembly (88 min), Windows (48 min) and macOS (20 min). It could share that cost with kernel.md open issue 13's `TopOpeBRepBuild` patch if both are wanted.
- Rejected: plain `double` everywhere (the holes and crashes measured above); `-ffp-contract=off` alone (the 53-bit variant still loses triangles and crashes); exact expansion arithmetic (Shewchuk's), correct but slower and a larger rewrite, since Delabella's normal and dot products need about 210 bits for double inputs; Delabella's own exact integer configuration (its header comment: 14-bit coordinates, a grid far coarser than the mesh); Watson for every face (11 to 12 s against the 1.5 s budget); per-platform expected files or a wider tolerance (ADR 0038, and a hole would ship).

**Notices** (delivery.md 2.9 item 6), for the gate: (i) OCCT's bundled DELABELLA entry renamed `DELABELLA, in OCCT's mesher and in its copy in partsmith-occt-sys`, with the same license, path and text (chosen and applied in `ui/scripts/notices/occt-7.9.3/bundled.json`, so no generator code changes: the copy keeps that file's notice word for word, and the one MIT text with its copyright covers both); (ii) an entry of its own for the copy, which needs a new kind of entry in `notices.mjs`, whose bundled list holds only code inside OCCT's tree.

## Consequences

- Kernel.md 3.7 item 2, 3.9 items 1 and 7, 3.11, 3.12 item 5, section 5, tests 137 and 138 and open issues 8 and 14; delivery.md 2.8, 2.9 item 6, open issue 1 (d) and section 8; the crate's `AGENTS.md`.
- Speed (release, medians of 3 runs alternating with OCCT's copy on one 4-core container, 2026-10-27): the engine's sphere 0.97 s against 0.89 s and `PLATE` 0.85 s against 0.79 s natively, within the 1.5 s budget; under Node 2.44 s against 3.52 s and 1.17 s against 2.16 s, within the web's 4.5 s, since OCCT's `long double` there is software arithmetic. The part (16 ms) and `element_display` of a hole wall (2 ms, a cylinder, which keeps Watson) did not change.
- The examples' expected results did not change on Linux: `cargo test -p partsmith-cli --test integration examples::` passed with the files of 2a202ac (kernel.md open issue 8).
- Checked on Linux: test 137 gives the same triangles natively and under WebAssembly; built with Clang and `CXXFLAGS=-mfma` (fused instructions available, contraction left to `build.rs`), in debug and release, every tessellation and determinism test passed, 137 with the same triangles; with `CXXFLAGS="-mfma -ffp-contract=on"`, which `cc` places after `build.rs`'s flags, test 137 failed with one diagonal flipped, so a build environment that turns contraction back on is not supported (kernel.md 3.12 item 5). Clang at `-O2 -mfma` emits 60 fused instructions in the copy without the flag and none with it. `partsmith export` to OBJ of the 12 examples of the first run's findings and predictions (`bench/fifty-features`, the four cones, both pipe-tees, `move_body/move-then-fillet` and the four revolve examples) gave the same bytes with the shim built by GCC and by Clang with `-mfma`, OCCT being the same GCC build in both.
- Delabella is maintained in this repository. An OCCT upgrade (ADR 0003) compares the new `delabella.cpp` and `delabella.pxx` with the copy and this list.
- OCCT's own copy stays linked, since `BRepMesh_Context`'s constructor references OCCT's Delabella factory, but it never triangulates.
- Node positions can still differ across platforms in the last bits (OCCT's curve and surface evaluation, its Watson and node insertion, the platform's libm, Apple Clang's fused operations). Kernel.md open issue 14 holds the decision rule: once test 137 passes on macOS, a mesh-dependent result that still leaves the tolerance there comes from its nodes, and the answers are OCCT built with `-ffp-contract=off` on macOS (every OCCT cache builds again) or print checks that do not depend on the diagonals of a degenerate triangulation.
- The next platforms run must show tests 137 and 138 passing on `windows-2025` and `macos-15`, and the examples runner passing there (with print.md 3.7 item 7): no open edges in `bench/fifty-features` (`29 warnings`), 4 warnings for the pointed cones, the frustum values within the tolerance, and on Windows no access violation in the revolve examples and no open edges in `move_body/move-then-fillet`.

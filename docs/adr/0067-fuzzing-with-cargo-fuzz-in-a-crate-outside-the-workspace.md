# 0067: Fuzzing with cargo-fuzz in a crate outside the workspace

Status: Accepted (owner's rule of 2026-11-05). It builds the M2 plan's choice 23, option (a): cargo-fuzz with libFuzzer, in a job of its own in `nightly.yml`, on a nightly toolchain pinned by date. Each choice below is settled by the owner's rule: the most open-source approach, then the safest, then the industry standard, then this work's recommendation. Its new dependencies and its change to the license policy go to human review at the M2 gate (m2-plan.md gate 19, AGENTS.md Process): `libfuzzer-sys` 0.4.13 with `arbitrary` 1.5.0 and `jobserver` 0.1.35, the tool cargo-fuzz 0.13.2, and an exception for NCSA scoped to libfuzzer-sys. All of them are dev-only. No build Partsmith distributes holds any of them. It changes no file format, protocol schema, naming algorithm or host capability. delivery.md sections 2.15 and 3.8 specify it.

## Context

- **What the design asks.** Technical design section 16 lists `cargo fuzz` on the file parser, the `.scad` interpreter and the protocol decoder. The M2 plan's item 8 adds the STEP reader and the font reader. Risk 13 names the reason: M2 reads font and STEP files from documents other people share. Gate 15 asks for a fuzz job of its own in `nightly.yml` with no skip rule, 10 minutes per target each night, a nightly toolchain pinned by date in delivery.md 2.2's tool table, committed corpora, a regression test for every finding, and 14 consecutive nights with no crash, panic or hang before the gate. It also asks for an ADR under the owner's rule for a crash inside OCCT that partsmith-occt-sys cannot turn into an error.
- **The readers.** `partsmith_model::load_bytes` reads a `.ptsm` file's bytes (crates/partsmith-model/src/file/mod.rs). `partsmith_protocol::decode_request_frame` decodes each frame a host sends to the engine (crates/partsmith-engine/src/dispatch.rs). `partsmith_occt_sys::read_step` hands a file's bytes to OCCT's `STEPCAFControl_Reader`, `ReadStream` and then `Transfer` (crates/partsmith-occt-sys/cpp/exchange.cpp). The shim turns C++ exceptions into `KernelError`. It installs no signal handler (kernel.md section 3.9 item 7). A fault inside OCCT ends a native process.

Its default build is a release build with debug assertions, AddressSanitizer, libFuzzer's coverage instrumentation of the Rust code and `--cfg fuzzing`. Sanitizers need a nightly compiler. cargo-fuzz passes `-artifact_prefix=<fuzz folder>/artifacts/<target>/` itself. Its default ignore file names `corpus`.

## Decision

1. **The crate.** `fuzz/` holds one crate, `partsmith-fuzz`, outside the workspace, in the layout of `cargo fuzz init --fuzzing-workspace=true`: its own `[workspace]` with `members = ["."]` and its own lock file, made from `Cargo.lock`. The root `Cargo.toml` does not change.
2. **The toolchain.** `fuzz/rust-toolchain.toml` pins `nightly-2026-05-22`, the last nightly of Rust 1.97, the version the root pins. A change of the root's version moves the pin in the same change.
3. **The targets.** `ptsm_load`, `protocol_frame` and `step_read` in wave 1, `font_read` in wave 3, the `.scad` interpreter's in M4. Each target calls its reader on the input. `ptsm_load` and `protocol_frame` also check the round trips the architecture promises.
4. **The license check.** cargo-deny checks `fuzz/Cargo.lock` with the same `deny.toml`, in a second step of the `deny` job. `deny.toml` gains `exceptions = [{ allow = ["NCSA"], crate = "libfuzzer-sys" }]`. The allow list does not change. The notices and the dependency source archives do not change: they read the workspace, and no distributed build holds a fuzz binary.
5. **The job.** `nightly.yml` gains `fuzz`, one matrix row per target, 10 minutes each with `-max_total_time=600`, no skip rule and a timeout of 60 minutes per row. A row that finds a failing input uploads it as `fuzz-artifacts-<target>`, kept 7 days.
6. **The corpora.** Seeds are committed under `fuzz/corpus/<target>/`, each named by its SHA-1. `examples/` is read in place every night. The grown corpus stays in the Actions cache. The job never commits.
7. **Findings.** Each finding gets an acceptance test in its crate's spec that reads the input from the corpus, and the input is committed with the test and the fix (delivery.md 3.8). The first finding is fixed by choice 10 below.

## Alternatives considered

The plan settled the tool (choice 23). Its options: (a) cargo-fuzz with libFuzzer; (b) afl.rs; (c) more proptest only. It picked (a): the tool technical design section 16 names and the Rust community's standard. This record does not reopen it.

The choices below are each Accepted (owner's rule of 2026-11-05).

1. *Where the crate lives.* (i) `fuzz/` at the root, outside the workspace, with its own lock file; (ii) a member of the workspace, such as `crates/partsmith-fuzz`; (iii) a `fuzz/` folder in each crate that owns a reader, as `cargo fuzz init` writes by default. All three are equally open. The rule takes (i), the safest. `Cargo.lock` stays as it is. The notices and the dependency source archives stay as they are too. libfuzzer-sys never enters a lock that a distributed build reads. `cargo test --workspace` and `cargo clippy --workspace` build nothing that links libFuzzer. It is also the industry standard: cargo-fuzz's own layout with `--fuzzing-workspace=true`. Under (ii), `Cargo.lock` and the archives would hold libfuzzer-sys, and its NCSA license would enter the policy of the shipped builds. (iii) needs three crates, three lock files and three caches for the same job. The cost of (i) is a second lock file that must follow the first, which test 144 checks.
2. *The toolchain.* (i) `nightly-2026-05-22`, the last nightly whose `rustc --version` starts with `rustc 1.97.0-nightly`; (ii) the newest nightly on the day of writing; (iii) `nightly` with no date; (iv) the stable 1.97.0 with `RUSTC_BOOTSTRAP=1`. The rule takes (i), the safest: of every nightly it is the compiler closest to the stable release that builds the product. It is the last nightly of the line that became 1.97.0. (ii) fuzzes with a compiler more than five months newer than the product's. (iii) changes every night, and a night's failure could be the compiler's. (iv) is the escape hatch the Rust project tells users not to rely on, a workaround AGENTS.md principle 1 rules out. The plan asks for a pin by date in 2.2's tool table. (i) is that pin.
3. *The license of libfuzzer-sys.* (i) an exception in `deny.toml` that allows NCSA for libfuzzer-sys alone; (ii) NCSA added to the allow list; (iii) a second `deny.toml` for the fuzz crate, with NCSA allowed; (iv) a `[[licenses.clarify]]` entry that declares libfuzzer-sys `MIT OR Apache-2.0`; (v) no license check of the fuzz crate. NCSA is OSI-approved and permissive. Each option is open. The rule takes (i), the safest. The policy of every other crate stays as it is. A crate under NCSA in a shipped build still fails. The npm license check, which reads the allow list (delivery.md 2.10), stays as it is. It is also the industry standard: cargo-deny documents `exceptions` for one crate's license. (ii) widens the policy for the shipped builds and the npm packages with no need. (iii) keeps two policies in step by hand. (iv) states a license the crate does not have. (v) leaves the fuzz lock without its advisory, ban and source checks too.
4. *The corpora.* (i) committed seeds, `examples/` read in place, and the grown corpus kept in the Actions cache; (ii) a job that commits the grown corpus to `main` each night; (iii) committed seeds alone, with nothing kept between nights; (iv) no committed corpus. The rule takes (i), the safest. No workflow writes to the repository: `nightly.yml` keeps `contents: read`. The repository does not grow by megabytes each night. The fuzzing still builds on the inputs of earlier nights. It is also close to the industry standard: projects commit seeds, and OSS-Fuzz keeps the grown corpora in storage of its own. (ii) needs `contents: write` and a push to `main` that no review sees. (iii) starts from the seeds every night. (iv) fails gate 15's checked-in corpora. Every seed is a copy of a file of this repository or bytes delivery.md 2.15 spells out, under the repository's license.
5. *One row per target.* (i) a matrix with one row per target, side by side; (ii) one job that fuzzes the targets one after another. The rule takes (i), the safest: a finding in one target does not stop the others (`fail-fast: false`), each target is a check of its own, and each row has its own timeout. A row takes about 20 minutes of wall time. (ii) would take about 40, and its first failure would end the others' runs. Each row of (i) builds the crate's dependencies again, which the Rust cache keeps small.
6. *Leaks.* (i) leak detection off for `step_read` alone, `-detect_leaks=0` for libFuzzer's check after each input and `ASAN_OPTIONS=detect_leaks=0` for LeakSanitizer's check at exit, and on for the targets of Rust code; (ii) LeakSanitizer suppressions for OCCT's leaks, with `fast_unwind_on_malloc=0`; (iii) leak detection off for every target; (iv) a patch to OCCT for its leaks. The rule takes (i), the safest that runs. A crash, a read or write outside memory the reader owns, a timeout and a memory limit still fail `step_read`. A leak in Rust code fails the two other rows. (ii) was measured: with the first leak suppressed, the next run stopped on a second one, on a valid file. The suppressions name OCCT's functions and change with each OCCT release. The slow unwinder slows a reader that already runs about 19 inputs per second. (iii) gives up leak detection where a leak is Partsmith's bug. (iv) changes the OCCT build and its source archive for leaks of a few bytes per read. kernel.md records the two leaks for a report to OCCT.
7. *The limits for one input and the process.* (i) OSS-Fuzz's, `-timeout=25` and `-rss_limit_mb=2560`; (ii) libFuzzer's defaults, 1,200 s and 2,048 MB; (iii) tighter limits, such as 5 s. The rule takes (i), the industry standard. Under (ii) a hang would never be reported: 1,200 s is longer than the 600 s run. (iii) would report as hangs the large STEP files that OCCT reads in seconds.
8. *Checks on every change.* (i) `cargo fmt` and `cargo clippy` of the fuzz crate in CI's `rust` job, on the stable toolchain, and the license check in `deny`; (ii) no check until the nightly run builds the crate; (iii) `cargo fuzz build` of every target in CI, on the nightly toolchain. The rule takes (i), the safest at the least cost. A change to a reader's interface that breaks a target fails its own pull request, not the next night. It took 21 s on the 4-core development container, where sccache served the C++ objects. CI has no sccache. There a check from an empty `fuzz/target` compiles libFuzzer's C++ and the shim's C++ again on every run. A cold check of `partsmith-occt-sys` alone, without sccache, took 38 s on that container. Test 151 measures the step on the runner. (ii) breaks `main`'s nights silently. (iii) adds the nightly toolchain and about four minutes to every CI run, for what clippy already compiles.
9. *What the ADR for an OCCT crash weighs.* When a finding crashes inside OCCT and no check in the shim can refuse the input first, the step that meets it writes an ADR under the owner's rule. The options: (i) the ADR weighs at least a patch to OCCT applied by `scripts/build-occt.sh` and offered upstream, a signal handler (`OSD::SetSignal`, which kernel.md 3.9 item 7 rules out today), the reader in a process of its own on the native hosts, and a newer OCCT release; (ii) the ADR is left open. The rule takes (i), the safest: the routes known today are weighed every time, and the patch keeps the OCCT source archive exact (delivery.md 2.13). Until that ADR's fix lands, the row keeps failing. No row is skipped to pass the gate.
10. *The fix of the first finding.* (i) `read_step` refuses a file whose complete check list holds a fail, `ModelCheckList(Standard_True)`: the load check and OCCT's semantic check of every entity. It refuses with `ReadFailed` and `The file is not a valid STEP file.`, after the check for nothing to transfer and before any transfer; (ii) it refuses only the fails of kinds `Incorrect Syntax` and `Unresolved Reference`; (iii) a patch to OCCT's `StepToGeom` that checks for a null direction; (iv) the transfer runs anyway, and the import keeps what transfers; (v) it refuses a file whose load check holds a fail, `ModelCheckList(Standard_False)`, the syntactic messages alone (`IFSelect_WorkSession.hxx`: "<complete> = False : only syntactic (check file form)"). All five are equally open. The rule takes (i), the safest. Each load fail is a parameter or a reference that OCCT could not read, and a transfer over it works on nulls or wrong types. A semantic fail names a rule of the STEP schema that an entity breaks. `libTKDESTEP.a` holds such texts as `ERROR: non 2-manifold topology`, `ERROR: EdgeCurve not referenced` and `ERROR: No.of KnotMultiplicities not equal No.of Knots`. (v) refuses finding 1 too: its load check holds 29 fails. Under (v) a file with semantic fails alone still reaches the transfer, which no test or fuzz run has shown safe on such data. (i) refuses it first. The complete check costs more: 24 ms against the load check's 11 ms on a 1.59 MB export whose `ReadStream` took 130 ms, and under 1.3 ms on each file under 110 KB (Probe). The check comes after the check for nothing to transfer. The empty file of kernel.md test 83 then keeps its `EmptyResult`: both lists hold its one `DATA NOT AVAILABLE FOR CHECK`. Under (ii) the fails of other kinds, such as `Entity has illegal type`, still reach the transfer, a route to the same null reads. (iii) guards one call site of many and patches OCCT. (iv) is a partial import with its own spec and messages. The cost of (i): a file from another program that holds a fail and transfers today stops importing. That includes a file with semantic fails alone, which (v) would still import. No STEP file of the repository and none of the four exports holds a fail. The kernel spec's step specifies the change (kernel.md section 3.8.1 read item 4). Before the change lands, its implementer measures both lists on the STEP texts of kernel.md's tests and on the STEP files that the examples runner's test 5 imports back. If a file that the repository imports holds semantic fails alone, (i) and (v) are weighed again under the owner's rule.
11. *`.github/workflows/AGENTS.md`.* The file is the owner's. (i) delivery.md 2.15 settles the sentences that name the job, applied with it, as wave H's were; (ii) the file stays as it is until the owner edits it. The rule takes (i), the safest: every agent reads that file before it changes a workflow, and a job it does not describe would be changed blind. The change touches only the sentences 2.15 names (test 150).

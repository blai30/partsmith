# 0043: The engine's web-column budgets are measured by hand in Chromium, through the app's bridge

Status: Accepted. No capability, schema, license or dependency changes: the benchmark uses Playwright, Vite and the bridge that `ui` already has, and no workflow runs it.

## Context

- **A column with no benchmark.** engine.md section 5 gives every engine budget a desktop and a web value, and technical design section 14 sets the web values in Chrome on the reference machine. `crates/partsmith-engine/benches/budgets.rs` measures the desktop column through `Session::call`; nothing measured the web column, though section 5 named "a Playwright benchmark against the WebAssembly build" (gap list ENG-2).
- **What the module offers.** The web core exports `ps_alloc`, `ps_free` and `ps_call` alone (ADR 0010), is built for a worker (`-sENVIRONMENT=worker`), and runs one session per instance, created by its `main` with display on, random ids and the wasm32 `cache_budget` of 512 MiB. The UI's performance tests (ui.md 6.7) already run by hand with `PARTSMITH_PERF=1`, and P-12 already serves a test page with a module worker from a Vite dev server.
- **Measured on 2026-10-27** in this repository's container with a prototype of the driver, against the web core built from that day's tree:
  - Chromium 141 headless: the page and its module worker are cross-origin isolated under the Vite dev server (`vite.config.ts` sets the headers on every response), so `performance.now()` steps by 5 µs. A literal `import('/core/partsmith_core.mjs')` fails, since Vite refuses to import a script from `public/`; the import under `import.meta.env.BASE_URL` that `core.worker.ts` uses works. Playwright's `Worker.evaluate` reaches the worker's global scope.
  - Seven instances of one compiled module, one per sample, opened the reference part cold in 3,934, 2,748, 2,339, 2,263, 2,228, 2,194 and 2,372 ms: the first ran before V8 had optimized the module's code, and the later ones shared that code. Two instances answer `new_document` with document 1 each, so each has a session of its own.
  - The 300 boxes of the desktop memory row opened in 791 ms and left 29,097,984 bytes of wasm memory, 16 MiB of it the module's initial memory. `engine_info` through the app's `callCore` took 0.055 to 0.13 ms.
  - Under Node 22, the same module took 3.0 to 3.7 s for `analyze_print` of the 250 mm resin sphere, against a web budget of 900 ms.

## Decision

1. **A test page drives the shipped module in Chromium.** `ui/e2e/engine-budgets.spec.ts` runs its tests in order in one worker (`test.describe.configure({ mode: 'default' })`, as `perf.spec.ts` does, despite the configuration's `fullyParallel: true`) and opens `ui/e2e/pages/engine.html` once per worker for the rows; its module worker, `engine-worker.ts`, compiles `partsmith_core.wasm` once and makes a new instance of it wherever the desktop bench makes a new `Driver`, and one untimed open of the reference part before the rows warms the module up, so they run on code V8 has optimized. Each call is timed around `callCore` of `ui/src/core/bridge.ts`, the path the app's core worker takes: the two copies are timed with `ps_call`, and encoding and decoding are not, as the desktop bench times `Session::call` alone.
2. **The rows are the desktop bench's, ported to TypeScript** in `ui/e2e/support/engine-budgets.ts` under the same names, except the memory row (`wasm memory` for `resident memory`), with the same documents, edits, samples and checks, and kept in step by hand: a change to a row of `budgets.rs` changes its web row in the same change. One Playwright test per row, its median the 4th smallest of 7 samples (`percentile` at 0.5, which is `median` for 7), reported as a `perf` annotation before it is held to its budget, as ui.md 6.7's tests report theirs. The four grid rows each open the grid in an instance of their own, so each row runs alone.
3. **Only by hand.** The rows are tagged `@perf` and run only with `PARTSMITH_PERF=1`, on the reference machine before a release until the fixed hardware runner exists (delivery.md 1.2); CI never runs them, so a slow runner fails no budget. A run elsewhere records its numbers in engine.md open issue 19. Two tests of the driver (engine.md tests 156 and 157) run without `@perf` on every e2e run, on pages of their own, and test 156 also checks that `budgets.rs` still names each timed row, so the driver cannot rot unnoticed; the rows' own requests and checks run only by hand, as the desktop bench's do. delivery.md test 67 checks that no workflow sets `PARTSMITH_PERF`.
4. **Memory is the instance's wasm memory**, `HEAPU8.length` after the 300-box document opens, held below 4 GiB, the module's maximum; the session's `cache_budget` is the module's own 512 MiB.
5. **`bare_numbers` has no web row.** Only `Session::count_bare_numbers` times the count alone, and the module cannot reach it; engine.md open issue 20 keeps the options.

## Options considered

- **Where it runs:** (a) a Playwright page whose worker drives the shipped module in Chromium (chosen: the build and the browser the web budgets are set for); (b) the engine's budgets bench built for `wasm32-unknown-emscripten` and run under Node, which keeps one copy of the rows but times another binary (the bench profile instead of `wasm-release`, `Session::call` without the bridge's copies), in Node instead of Chrome, and needs a budget per target in every row; (c) the desktop bench writes its request frames and the browser replays them, one copy of the rows again, but the requests that depend on a response (the fix of `apply_fix`, the edges of the loss and ghost rows, mesh ids) are right only while both builds answer alike, and the desktop bench gains a recording mode; (d) a Node script like `parity.mjs`, with no browser and the same module, again not where the budgets are set.
- **Reporting:** (a) one Playwright test per row with `perf` annotations (chosen: `-g` selects rows as the desktop bench's words do, a failed row stops no other, and the annotations are the UI's own); (b) one test that ports `Report` and prints its table, which repeats what Playwright's report already does and needs a selection of its own.
- **Instances:** (a) one compiled module, a new instance per new `Driver` (chosen: a new session with empty caches, as natively, on code that is already optimized); (b) a new worker for each, which compiles the module again every time and starts each row on unoptimized code (the first cold open above took 3.9 s, the later ones 2.2 to 2.7 s).
- **Warm-up:** (a) one untimed open of the reference part in a new instance, ended before the first row (chosen: every row, a row selected alone with `-g` and the first row after a failed one included, starts on code V8 has optimized, as `partsmith-wasm`'s bench warms up with `WARM_UP_RUNS`); (b) none, where a row's first samples depend on what ran before it on the page.
- **`bare_numbers`:** (a) no web row, with open issue 20 (chosen); (b) an `apply_edits` as an upper bound, which open issue 17 dropped natively because it says nothing about the count; (c) a fourth export or a test-only command, which changes ADR 0010 or the protocol schema.

## Consequences

- engine.md section 5 (the desktop and web columns), tests 155 to 157, open issues 19 and 20; ui.md 6.3 and 6.7; delivery.md 1.2 and test 67 (in `ui/scripts/workflows.test.mjs`). The change adds `ui/e2e/engine-budgets.spec.ts`, `ui/e2e/support/engine-budgets.ts`, `ui/e2e/support/perf.ts` (the annotation helper, moved out of `perf.spec.ts`), `ui/e2e/pages/engine.html` and `engine-worker.ts`, and updates `ui/e2e/README.md` (with the JSON reporter command that records a local run's annotations), `ui/AGENTS.md`, `crates/partsmith-engine/AGENTS.md` and the doc comment of `benches/budgets.rs`, which name the web bench and the rule that keeps the two in step. `playwright.config.ts` gains no project.
- Two copies of each row's setup, one in Rust and one in TypeScript, which only review keeps in step beyond the row names test 156 checks; a row that drifts measures something else without failing.
- Every e2e run opens the engine page three times for tests 156 and 157, compiling the module twice, a few seconds; the rows themselves cost CI nothing.
- Row 1 holds 29 MB, far from `cache_budget`, so it cannot check how far the caches stay within 512 MiB (gap list ENG-3).

# 0042: The web core is compared with a native session over the corpus, the sketch suite and the engine's panic containment run on WebAssembly, and display buffers may differ

Status: Accepted. No capability, schema, license or dependency changes: the tests use the crates' existing dependencies, and the new CI steps go into the existing `kernel-wasm` and `core-wasm` jobs.

## Context

- **Promises nothing checked.** engine.md 3.18 promised that native and WebAssembly builds give the same recipes, ids, statuses and messages and geometry within 1e-9, recompute.md 3.9 equal reports "on every platform", sketch.md 3.12 sketch results within 1e-9 across targets, and protocol.md 2.10 an `internal_error` for a panic in the web core instead of a trap. No test compared the two builds or panicked on WebAssembly (gap list ENG-1, ENG-4 and SK-1). The web app is the build most users open.
- **Measured on 2026-10-27** in this repository's container, with the web core built from that day's tree and the native engine through `partsmith._core` (release, display on, random ids, as the module's session):
  - 253 documents (the 8 engine fixtures and the 245 examples), each opened, measured body by body, analyzed with `as_modeled` and closed: 1,056 requests. Every response header matched, strings and integers exactly and every other number within `max(1e-9 * |native|, 1e-9)` (the largest gaps: 6.2e-11 on a center of mass near 0, 2e-11 relative on an area), except the `triangles` ranges of 7 print findings in 3 documents. Every buffer had the same byte length, but the model meshes of 99 bodies differed: 36 held the same triangles in another order and 63 other triangles (cylinders keep OCCT's Watson algorithm, kernel.md 3.7 item 2, and nodes move in their last bits, kernel.md 3.11). The native side took 35.8 s in release, the module 15.7 s under Node; `partsmith rebuild --checks` of every example one after the other takes 42 s with the debug binary.
  - The same day, with test 154 as written (`list_elements` of each body added, 1,353 requests): the whole test took 57 s in a debug build with Node 22 and matched except 4 numbers of `list_elements` in 3 documents, coordinates near zero of fillet faces 1.2e-9 to 1.6e-9 apart (`chamfer/pipe-tee`, `fillet/pipe-tee` and `fillet/top-loop`, engine.md open issue 18); element names, references and fingerprint texts were equal. Element geometry is therefore held to delivery.md 2.8's tolerance, as print reports.
  - Sketch, the generated benchmarks of sketch.md 5.2 and 5.3: the chain solve and the grid profile are bitwise equal on both targets, the 100 chain drag frames agree within 2e-13 mm, and in frames 5 to 16 the arc `e-0-ar` comes back with start angle 5π/3 natively and its stored -π/3 under WebAssembly. sketch.md 3.7.6 returns an entity exactly as given when none of its parameters changed bitwise, and a rounding moved them on one target only.
  - `cargo test -p partsmith-sketch --target wasm32-unknown-emscripten`: 649 of the 650 tests pass (47 s with the build); test 97 fails because it spawns a thread and the target is built without threads.
  - `cargo test -p partsmith-engine --lib --target wasm32-unknown-emscripten dispatch::`: the 11 dispatch tests pass, the panic tests among them, so `catch_unwind` works with native WebAssembly exceptions (39 s with the dependencies built).
  - CI run 40509563233 (2026-10-27): `kernel-wasm` 2.0 min, `core-wasm` 6.2 min (its `web_module::` step 51 s), and `rust` 31.2 min, the longest path to `deploy`.

## Decision

1. **One parity test runs the web core against a native session** (engine.md test 154, in `crates/partsmith-wasm/tests/web_parity.rs` with `tests/node/parity.mjs`): `open_document`, `measure` and `list_elements` of each body, `analyze_print` and `close_document` for every engine fixture and example. Strings, booleans, `null` and integers are equal, so element names and references too (recompute.md test 74's output names); other numbers agree within `max(1e-9 * |native|, 1e-9)`; an arc's angles modulo 2π; the `print_health` report and the geometry of `list_elements` descriptors within delivery.md 2.8's tolerance, the report without its findings' `triangles`; buffer tables by count and element type only. The promise and the test cover x86_64 Linux and WebAssembly; Windows and macOS stay held to delivery.md 2.8's tolerance by the platforms workflow.
2. **The Rust test drives everything.** It builds each request, sends it through the module's own `call` natively (a fresh session on the test's thread with the options `main` gives the module's, `Session::call` inside), and writes the frames to a file; the Node script only passes them through `ps_call` and writes the answers back. The comparison stays in one place, next to the native session, and the script stays as small as the two that exist.
3. **The parity test is ignored by default** and CI runs it with `-- --ignored` right after `scripts/build-wasm.sh` in `core-wasm`. A module built from another tree fails it on any change of behavior, so it cannot run whenever a module happens to be in `ui/public/core/`, as the `web_module::` round trips do. When asked for, it fails instead of skipping if it cannot run.
4. **No test-only id mode.** The compared commands draw no ids (only `import_step` and `apply_fix` do), so the native session takes the module's own options, random ids included; a command that drew one would differ and fail the test, which is when an id mode would be worth adding.
5. **Panic containment on WebAssembly is the engine's dispatch tests run on `wasm32-unknown-emscripten`** in `kernel-wasm`, plus a check in `crates/partsmith-wasm/tests/build_script.rs` that the module's profile, `wasm-release`, keeps `panic = "unwind"` (protocol.md test 84). The tests link with the target's arguments of `.cargo/config.toml`, which the module repeats, so they unwind as the module does; the module's own extra arguments (an ES module factory for a worker, the runtime kept alive, the exports) do not touch exceptions.
6. **The sketch suite runs on `wasm32-unknown-emscripten`** in `kernel-wasm`. Test 97 compares its spawned thread only where threads exist. A new test 255 holds the chain drag (frames 50 and 100) and the chain with every radius 6 to native values written into the test as literals within 1e-9. Arcs agree across targets modulo 2π (sketch.md 3.12). No assertion is relaxed: every bitwise one passes there.
7. **Display buffers may differ between native and WebAssembly** (engine.md 3.18 and open issue 18), and a recipe the engine writes from solved geometry holds the same values within the tolerances, not the same text. Keys of recompute can differ across builds too (recompute.md 3.9), since they hold the bits of converted values.

## Options considered

- **Reference:** (a) a native session in the same test (chosen); (b) checked-in expected frames, 18 MB of responses rewritten on every change of behavior; (c) only the examples' expected files, which the module cannot produce without a CLI and which round to 1e-6.
- **Ids:** (a) none needed (chosen); (b) a test-only module with `SequentialIds`, a second module build of about 4 minutes or an argument parsed by the shipped `main`; (c) placeholders for new ids, as `SideBySide::send_generating` does, needed only once a compared command draws ids.
- **Buffers:** (a) count and element types (chosen, kernel.md 3.11); (b) byte lengths too, true for every mesh today, but a node count is a decision of the mesher on continuous values that the last bits can flip; (c) contents within an `f32` tolerance, false today for 99 meshes.
- **Print:** (a) included, within delivery.md 2.8's tolerance (chosen: it is what kernel.md 3.11 promises across platforms, and the web is where most prints are checked); (b) left out, as the gap list's item named only opening and measuring; (c) within 1e-9, true today but not promised.
- **Panics:** (a) the dispatch tests in the dev profile and a check of the module's profile (chosen); (b) the same tests in the `wasm-release` profile, a fat-LTO build of the engine's unit tests for minutes per run; (c) a panic trigger in a second module build, which needs a fourth export (ADR 0010) or a test-only command in the protocol schema.
- **Sketch baseline:** (a) literals in the test (chosen); (b) a JSON fixture with a bless mode, more code for the same check; (c) the drag frames through the engine's parity test with `drag_sketch`, which would need the sketch benchmark generator in `partsmith-wasm`.
- **Arcs returned as given on one target:** (a) compare angles modulo 2π (chosen); (b) judge "changed" in sketch.md 3.7.6 with a tolerance, a change of the solver left to sketch.md open issue 5.

## Consequences

- engine.md 3.15, 3.18, test 154 and open issue 18; recompute.md 3.9 and test 74; protocol.md 2.10 and test 84; sketch.md 3.12, tests 97 and 255 and open issue 5; delivery.md 1.1, 2.4, 3.7 and tests 2, 7 and 66. The implementation updates the AGENTS.md of `partsmith-wasm`, `partsmith-sketch` and `partsmith-engine` and `.github/workflows/AGENTS.md` with the new commands, and `crates/partsmith-recompute/AGENTS.md`, which maps every recompute.md test to a file, with the line "test 74 is engine.md test 154, in `partsmith-wasm`".
- CI: `core-wasm` grows by the parity test, about a minute of native debug work and under half a minute under Node by the measurements above; `kernel-wasm` by the sketch suite (under a minute) and the engine's WebAssembly test build (a few minutes cold, less with its Rust cache, which grows by that build). Both stay far inside their 60 minutes and shorter than `rust`, so the time to `deploy` does not change.
- Whatever only WebAssembly gets wrong in a fixture or an example (a status, a message, a measurement, a print finding) now fails CI with the document, the request and the JSON Pointer. A change of behavior shows on both sides at once, so the test needs no update when expected results change.
- Mesh differences between the builds stay allowed and are recorded, not tested; exported mesh files differ in bytes across builds, so a golden export file is pinned on one target (gap list ENG-6).

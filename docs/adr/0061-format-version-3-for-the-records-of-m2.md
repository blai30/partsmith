# 0061: Format version 3 for the records of M2

Status: Accepted (owner's rule of 2026-11-05): the M2 plan's choice 1, option (a), and the choices below. It changes the file format (file-format.md sections 3.2, 3.5, 3.9 and 3.10, model.md sections 2 and 3, engine.md sections 3.2 and 3.20). It goes to human review at the M2 gate (AGENTS.md Process, m2-plan.md gate 19). No protocol schema, license, dependency or capability change: `engine_info` reports the number 3 in the field it already has.

## Context

- **M1 writes version 2.** `FORMAT_VERSION` is 2 and `OLDEST_FORMAT_VERSION` is 1 in `crates/partsmith-model/src/file/mod.rs`. `MIGRATIONS` in `src/file/migrate.rs` holds one step, `migrate_from_1`, which returns the document unchanged ([ADR 0025](0025-file-format-version-2.md)). A build refuses a newer file with `NewerFormatVersion` before it deserializes anything: "This file uses format version 3, which is newer than this version of Partsmith supports (up to 2). Update Partsmith to open it."
- **M2 brings records an M1 build would misread or drop.** Conic, spline, text and projected sketch entities (the sketch contracts step of wave 1), the printer profile a document stores ([ADR 0062](0062-custom-printer-profiles-stored-in-documents-and-kept-by-every-host.md)), new feature types and new params of existing types. `Document`, `Parameter` and `Body` deny unknown fields (`crates/partsmith-model/src/document.rs`). An M1 build would refuse a document with a `printer_profile` key with an `Invalid` error that does not say to update.
- **The plan picked one version.** The M2 plan's choice 1 took option (a): one bump to version 3 for every M2 record shape, declared in wave 1, with a migration from 2 that changes only the version, frozen at the gate. It rejected a bump per track and optional fields with no bump.
- **`main` is in production.** The Cloudflare Pages deploy publishes `main` (delivery.md section 3.3). From the merge of wave 1 on, the web app writes version 3 into users' files, months before the gate reviews it.
- **An unknown feature type is already safe.** file-format.md section 3.2 keeps feature params as they are. The engine loads a record of an unknown type and gives it status `error` with features.md's `UnknownType` message ("This document has a feature of type 'wedge', which this version of Partsmith does not have. Update Partsmith, or delete the feature."). It builds the rest and saves the record unchanged (engine.md section 3.2).
- **The checked-in documents.** The repository holds 353 `.ptsm` files at d47b0d9, all at version 2: the examples, the model and engine fixtures and the e2e fixtures under `ui/e2e/fixtures/`. Tests that compare a save with a fixture's text need the fixture at the current version (engine.md test 7, file-format.md tests over E1 to E11).

## Decision

1. **Version 3.** `FORMAT_VERSION` becomes 3. `OLDEST_FORMAT_VERSION` stays 1. `MIGRATIONS` gains `migrate_from_2`, which returns the document unchanged. The chain sets the version (file-format.md section 3.9). A version 1 text passes both steps. `migrate` reports `Some(2)` for a version 2 text. The JSON Schema's `format_version` is `const: 3` (file-format.md section 3.10).
2. **The step from 2 reads nothing.** Every version 2 document means the same at version 3. Version 3 adds only keys, records and values that a version 2 document cannot hold, each with the version 2 meaning when absent. Opening a version 2 document and saving it without edits changes only its `format_version` line (file-format.md test 59).
3. **Version 3 grows until the gate, by addition only** (choice 2). Each M2 spec that adds a record lists it in the version 3 row of file-format.md section 3.9, in the same change. Each addition is an optional key omitted when absent, a new record type or a new value of a tagged enum. A key, record or value that a version 3 build has written keeps its shape and meaning until the gate. The gate freezes version 3 with every record in its row.
4. **No tag between the bump and the gate** (choice 3). The release checklist's item 3 checks that the tagged commit writes a frozen version: version 2, or version 3 from the M2 gate commit on. The first tag, M1's, comes from a commit that writes version 2, such as a3f4573 on `main`.
5. **What needs a version after the gate** (choice 1). A new feature type alone does not. A new key in an existing type's params, a new value of an enum an existing record holds, a new sketch entity or constraint type, a new key of `Document`, `Parameter` or `Body`, and a rule that refuses a stored printer profile an earlier build accepted each do (file-format.md section 3.9).
6. **The checked-in documents move to version 3** (choice 4). The commit that bumps `FORMAT_VERSION` rewrites the `format_version` line of every checked-in document from 2 to 3, and nothing else in them. Only the texts that test the migration are at version 2: engine.md tests 171 and 175 set version 2 in the text they open, and ui.md's new fixture `printer-v2.ptsm` is written at version 2.

## Options considered

The plan settled the bump itself. The spec met four choices the plan leaves open. The owner's rule settles each: the most open-source approach, the safest, the industry standard and the recommendation of this work. All options here are equally open, plain JSON with no account.

1. *Whether a new feature type alone needs a new version.* Options: (i) every new record type bumps the version; (ii) a new feature type alone needs none, and every other addition does. The rule takes (ii), the safest for users. Under (ii) an older build opens the file, shows every feature it knows, marks the new one with a message that says to update, and keeps the record on save. Under (i) it refuses the whole file. Neither misreads anything. glTF takes the same line: a reader skips an extension it does not know, unless the file marks the extension required.
2. *How version 3 grows before the gate.* Options: (a) by addition only, with what was written fixed until the gate; (b) free changes until the gate, with files written before the gate left unsupported; (c) a preview number (such as a separate version for the months before the gate) renumbered at the gate. The rule takes (a), the safest. Users of the web app write version 3 from wave 1 on. Under (a) every one of those files opens in every later build with the same meaning. Under (b) a later change could make one of them open with another meaning, or not at all. Under (c) every preview file needs its own migration, and the version the gate reviews is not the one users hold. A record the gate rejects after the web app wrote it stays readable. Its change waits for version 4 and a migration step.
3. *Tags before the gate.* Options: (i) no tag on a commit that writes version 3 before the gate; (ii) tags allowed, with version 3 marked unreviewed in the release notes. The rule takes (i), the safest. A desktop or CLI release lasts on users' machines, where the web deploy is replaced on every merge. A release that wrote an unreviewed version would spread files that the gate review could not change without a version 4. delivery.md section 3.6 and `.github/workflows/AGENTS.md` gain the check (by handoff).
4. *The checked-in documents.* Options: (i) rewrite their version line when the bump lands; (ii) keep them at version 2 and let every load migrate them. The rule takes (i), the industry standard for fixtures that pin canonical text. Under (ii) every test that compares a save with its fixture fails, since a save writes version 3. Every opened example would also show the `migrated` notification (ui.md section 4.3). The migration tests keep version 2 texts of their own.

## Consequences

- An M1 build refuses every version 3 file with `NewerFormatVersion` and the message above. It never opens one. It never drops a stored profile or a record it cannot read when it saves.
- An M2 build opens every M1 file. The UI shows the `migrated` notification for each one ("{file} was updated from format version 2. Saving writes the current format.", ui.md section 4.3). Saving it writes version 3.
- partsmith-model gains `migrate_from_2` and the constant 3. file-format.md's tests 23, 39, 46, 48 and 58 change their numbers. Tests 59 to 69 are new. engine.md test 148 and its fixtures in section 3.20 move to version 3, and test 171 is new.
- The bump commit rewrites the version line of every `.ptsm` file tracked at that commit: the 353 of d47b0d9 and every file wave 1 adds before the bump, the corpus models under `corpus/` among them. It also adds a copy of each rewritten document under `crates/` and `ui/e2e/fixtures/` to `fuzz/corpus/ptsm_load/` (delivery.md section 2.15, test 146). The commit that adds `custom-printer.ptsm` and `printer-v2.ptsm` adds their copies too. Example results and Python twins keep their values: no record changes meaning. `docs/format/ptsm.schema.json` is regenerated with `const: 3` and the stored printer profile of ADR 0062.
- Each later M2 spec that adds a record lists it in file-format.md section 3.9's version 3 row. A spec that would change an already written record waits for version 4.
- The release checklist, `.github/workflows/AGENTS.md` and architecture.md's `Document` struct need the version, by handoff from this step.
- This changes the file format. It goes to human review at the M2 gate with the records of version 3.

# 0044: `cache_budget` is split in halves between the two caches, a body that cannot be shown is a warning of its feature, and the golden 3MF files are pinned on CI's Linux build

Status: Accepted. No capability, schema, license or dependency changes: the split and the message are engine code, the golden files are test fixtures, and test 160 compares raw bytes, so it needs no new dev-dependency.

## Context

- **The budget bound twice the budget** (gap list ENG-3). `Session::new` gave the whole `cache_budget` to the tessellation cache as bytes and the whole of it again to the recompute cache as a limit of `cache_budget / 256 KiB` results (4096 at the default 1 GiB, 2048 at wasm32's 512 MiB), so the two caches together could hold about twice the budget, while engine.md section 3.17 said the total stayed within it. Recompute counts results, not bytes (recompute.md section 3.7), so no split can make the recompute half exact.
- **Two messages that broke the error guidelines** (gap list ENG-5). A body whose display mesh could not be built gave `display_failed` with `Partsmith could not display body "{name}" ({detail}). Please report this.`, which no spec described, with the kernel's text in the sentence and the body's name in double quotes, as an `error` after the feature's own messages, so a feature that built, and whose dependents build on its body, read as failed, and hosts that show a feature's first message beside its status (ui.md's status strip) showed "Error:" before a warning. Not every such failure is a bug: kernel.md section 3.5 keeps a STEP solid that is still invalid after repair, and operations carry its invalid parts forward. `duplicate_element_name` named the body by its id, and could never be reported: every naming map is built and read with unique names (naming.md section 3.3 step 7 and section 2.6), and the element set the table builds rejects a duplicate (section 2.7), which already makes the display fail.
- **No byte-for-byte golden 3MF** (gap list ENG-6). Technical design section 17 lists 3MF exports compared byte for byte among the test oracles, and io.md section 3.9 says such files must be regenerated when the zip or deflate crates change, but no such file existed: engine tests 87 and 88 check a 3MF's title and that two exports agree, and io's tests compare decompressed parts. Mesh bytes depend on the build, not only on the target: mesh nodes come from OCCT's evaluation, which the compiler and the C library's libm can move in their last bits (kernel.md section 3.11 and its open issue 14), 99 bodies' model meshes differed between the native and the WebAssembly build on 2026-10-27 (engine.md open issue 18), and `two-bodies.ptsm`'s cylinder caps have cocircular nodes, where a last-bit change flips a diagonal.

## Decision

1. **Halves.** `Session::new` gives the tessellation cache `cache_budget / 2` bytes and the recompute cache the other half as a limit of results at the 256 KiB per result the engine already assumed: 2048 results at 1 GiB, 1024 at 512 MiB. The split is `cache_shares(cache_budget) -> CacheShares { display_bytes, recompute_results }`, a private function of `session.rs` beside `ESTIMATED_RESULT_BYTES` (engine.md section 3.17). The recompute half stays an estimate, recorded in engine.md open issue 21 with the two ways to a bound in bytes. Engine test 158 checks the split and that each cache gets its share.
2. **A body that cannot be shown is a warning of its feature, with the technical text in the detail.** The feature that produced the body state gets, first among its messages, a `warning` with code `display_failed`, the message `Body '{name}' cannot be shown, and Partsmith could not tell why. Report this with the details.`, `detail` `body {id}: {text}` (as `InvalidParams` puts `{feature type} {feature id}: ` before its parser's text), with `{text}` the failure's technical text (`KernelError::detail()`, `FeatureError::detail()` or the engine's own sentence, never a `Display` text), and no other field; its status becomes `warning` when it would be `ok`. When these messages change without a recompute (after `set_tessellation`), `recomputed` is sent again with the latest statuses (engine.md sections 3.4 and 3.8, test 159).
3. **No duplicate name check in the engine.** The check, its message and its paragraph go; naming's own checks stay the only ones.
4. **Two golden files pinned on CI's Linux build.** `crates/partsmith-engine/tests/fixtures/box.3mf` and `two-bodies.3mf` hold the bytes of the 3MF exports of `box.ptsm` and `two-bodies.ptsm` in CI's `rust` job: `ubuntu-24.04`, with OCCT built by `scripts/build-occt.sh` with that image's compiler and C library (GCC 13.3 and glibc 2.39 on 2026-10-27, which the reference container matches). They are blessed only in that build or one that matches it, and goldens blessed outside CI count only once the next CI run passes test 160 with them. Engine test 160 compares them on x86_64 Linux with the GNU C library and is ignored on every other target (`#[cfg_attr(not(all(target_arch = "x86_64", target_os = "linux", target_env = "gnu")), ignore = "...")]`). engine.md section 3.20 lists the five changes after which a regenerated golden is expected (the zip crate, its deflate backend or level; an OCCT bump or a change of the kernel's tessellation or build flags; a change of the compiler or C library that builds or runs OCCT, such as a new runner image once CI's OCCT cache is rebuilt; a change of how the kernel or features.md build the fixtures' box and cylinder; an intended change of the package's content or of its inputs), and any other change of the bytes is a defect. The failure for a differing golden tells a contributor on another Linux build that the build itself can make the difference.
5. **Regeneration through the examples' bless.** `PARTSMITH_BLESS=1 cargo test -p partsmith-engine --test integration export_and_import::t160`, and only with that filter, writes a missing or differing golden, and a set `PARTSMITH_BLESS` under `CI` fails with the examples' message (delivery.md section 2.8, engine test 161). The engine's tests carry their own copy of the examples runner's few-line `bless_mode`, since two crates' tests share code only through a crate, which would be a new dev-only crate (ADR 0027).

## Options considered

- **The budget:** (a) state the approximation, a bound of about twice the budget, in section 3.17, section 2 and an open issue, with no code; but a host picks `cache_budget` as a memory bound, as the web core's 512 MiB within 4 GiB is; (b) halves (chosen): a few lines in `session.rs`, a bound of about the budget, and half as many cached results at a given budget, which no budget row nears (its largest document holds 300 results); (c) another ratio, such as three quarters for meshes, which no measurement supports; (d) one byte budget shared by both caches, which needs recompute to size its results (open issue 21, option (a)).
- **The display failure:** (a) a `warning` first among the feature's messages, the status raised to `warning` (chosen): the feature built, so it is "done, but not entirely as asked" (errors.md), and the message a host shows beside the status is this one; (b) an `error` after the feature's own messages, with status `error`, which makes a feature that built read as failed while its dependents build on it, and puts a warning first under an error status; (c) the words of a bug ("Partsmith hit a bug while displaying body ..."), which an invalid STEP solid the import kept would make untrue (errors.md: a user's input is never presented as a bug).
- **The duplicate check:** (a) delete it (chosen); (b) keep it as a `debug_assert`, which repeats naming's check, sorts every body's names for every status in debug builds, and cannot fire.
- **The pin:** (a) CI's x86_64 Linux build (chosen); (b) the target alone, `x86_64-unknown-linux-gnu`, which a contributor's other compiler or C library, or a new runner image after an OCCT cache miss, can break with no change in the repository; (c) a golden per target, three sets of bytes for one rule, which only the weekly platforms workflow could bless and CI could not check; (d) decompressed parts on every target, which io's tests already compare and which would not pin the compression.
- **Regeneration:** (a) the examples' `PARTSMITH_BLESS` with its refusal in CI (chosen), one variable for every expected output of the repository; (b) a variable of its own, one more to learn, which would keep a bless of the whole workspace from rewriting the goldens, a case the filter rule covers instead; (c) writing the files by hand with `partsmith export`, which no test ties to the fixtures.

## Consequences

- engine.md sections 2, 3.4, 3.7, 3.8, 3.13, 3.17 and 3.20, tests 158 to 161 and open issues 18, 19 and 21; io.md section 3.9; delivery.md section 2.8, its README list and its error table. The code change is in `session.rs` (`cache_shares`, `Session::new` and the doc comment of `ESTIMATED_RESULT_BYTES`), `options.rs` (the doc comment of `cache_budget`), `events.rs` (the message, its detail, and `recomputed` when the messages change without a recompute) and `status.rs` (the message first with status `warning`, the duplicate check removed); the tests add the two fixtures, tests 160 and 161 in `tests/export_and_import.rs` and the bless mode in `tests/common`; the engine's AGENTS.md and the README name the regeneration command, its filter and the pinned build.
- The recompute cache keeps 2048 results instead of 4096 at the default budget, and 1024 instead of 2048 in the web core, so a long session can build again a result that the old limit would still have held. No budget row comes near either limit; the budgets bench, run before and after the change, shows whether any row is slower.
- A change of `zip`, its deflate backend, OCCT, the tessellation or CI's toolchain now fails engine test 160 in CI until the goldens are regenerated, which is the point: the change shows its effect on exported bytes in review.
- Windows, macOS and other targets never check the golden bytes; test 88 still checks there that an export repeats its bytes. An x86_64 Linux build other than CI's checks them and can fail for its build alone; its failure says so.

## Partsmith design direction

Applying [frontend-design.md](frontend-design.md) to a CAD tool used for hours at a time:

- **One interface for everyone:** there is no beginner mode, expert mode, simple view or skill setting. Newcomers and experienced users see the same screens, and those screens carry the full power of the app. FreeCAD and Fusion overwhelm newcomers through density, jargon and modal detours, not through capability, so Partsmith makes power approachable by how it is presented: a small number of clearly labeled tools, sensible defaults that produce a good result immediately, plain words, live previews, undo for everything, errors that explain and offer a fix, and hints that appear in context and get out of the way. The same surfaces serve speed: shortcuts, the command palette, expressions in every numeric field, precise typed entry and direct manipulation work everywhere, with no wizards or confirmations in the path. Every control earns its place on screen; a capability is never removed or hidden behind a separate mode to make the app look simpler.
- **References that survive edits:** a model must keep working when an earlier step changes. FreeCAD's numbered names (Edge002, Face009) break silently when anything upstream changes, and users lose hours finding out why; Partsmith never stores such numbers. Every reference is a semantic name plus a geometric fingerprint, resolved by meaning after each edit, and a reference that truly cannot be resolved says so in plain words: which element was lost, which change removed it, and how to pick its replacement in one click. Reference stability is tested with the edits that break other CAD tools, not assumed.
- **Errors that help:** prevent errors where the app can (good defaults, live previews, limits checked before the kernel runs), and when one happens anyway, explain it so a newcomer understands and an expert gets the detail: what happened, why (including which earlier change caused it), and what to do next, with a one-click fix when one exists ("Fillet too large: max 2.4 mm. Use 2.4 mm?"). Never show raw kernel text, error codes or internal ids as the message; keep the technical detail one step away for reports.
- **Tone:** a precision instrument. Graphite and zinc surfaces, generous spacing, restrained motion. The model in the viewport is the hero, and the chrome recedes through quiet color, compact size and regular weight, never through darkness: islands sit a step lighter than the viewport in both themes.
- **Islands, not docked panels:** the 3D view fills the window, and the chrome floats over it as rounded islands with a gap from the window's edges and from each other, never as panels docked behind hairline borders. The visual language is shadcn/ui's, kept flat: `rounded-xl` cards, `rounded-lg` menus, popovers and one-line chips, `rounded-md` controls, and no outlines. Depth is a tonal step (an island lighter than the viewport, a menu, a popover or an island floating over the free area's cards lighter again in the dark theme, a segmented control's thumb raised over its tinted track) plus one faint shadow, a step stronger for what comes and goes; buttons are filled (the primary accent, the rest tonal) or ghost; lines inside an island appear only where groups cannot be told apart otherwise, such as menu separators or the edge of a list while it scrolls under a header; secondary text is muted and focus rings are clear. In forced-colors mode the system draws each island's edge from a transparent border and each selected or pressed state from a transparent outline ([ADR 0032](../adr/0032-flat-islands-without-outlines.md)), and inputs keep a visible boundary of at least 3:1. Framing, the view cube and every overlay use the area the islands leave free, the model shows through the gaps, and nothing is picked through an island ([ADR 0030](../adr/0030-islands-over-a-full-window-viewport-and-rgb-axes.md)). Island and type rules name the type roles (interface, numbers and code), never a font family.
- **Accent:** one signal orange for selection, focus and primary actions. It stays distinct from sketch blue (under-constrained geometry) and red (conflicts and errors).
- **Axes:** X red, Y green, Z blue wherever an axis or a coordinate is shown (the view cube, origin axes and planes, coordinate fields and readouts), in hues of their own that stay distinct from the accent, error red and sketch blue, also under red-green color blindness. An axis color always comes with its letter, except the origin planes (tinted by their normal, named by their plane label) and the view cube's edges (named by its face labels), so color is never the only signal.
- **Type:** Geist for interface text, units and numbers, with its serifed capital I (`ss05`) set once at the root, tabular figures (`tabular-nums`) wherever digits line up (fields, readouts, measurements, tables, dimension labels, the timeline's and the status bar's counts and timings) and proportional figures in sentences, counts in prose and button labels, always with the plain zero. JetBrains Mono for code only: parameter names and expressions shown as code, and technical text; an inspector field stays in Geist even while it holds an expression. Titles are Geist at semibold, with no display face. Both fonts are self-hosted and named only in the theme variables and font faces of `ui/src/index.css`, so components use the inherited interface face, `font-mono` and `tabular-nums` and never name a family ([ADR 0031](../adr/0031-self-hosted-geist-and-jetbrains-mono-for-code.md), ui.md 2.16.7).
- **Themes:** light and dark from the same role-to-color mapping, toggled with the `dark` class on the root element (`@custom-variant dark` in `ui/src/index.css`). The mapping from roles (surface, text, accent, sketch states, axes, analysis colors) to Tailwind palette steps is documented in `docs/spec/ui.md` and single-sourced in code, which [tailwind-css.md](tailwind-css.md) allows for documented design-system mappings.
- **Stylesheet:** `ui/src/index.css` holds only the Tailwind import, the `@font-face` rules of the two self-hosted fonts, the font theme variables (`--font-sans`, `--font-mono` and their feature settings) and the dark variant (ui.md 2.16.1). Everything else is Tailwind utility classes. Positions computed from 3D geometry at runtime (floating inspector, dimension labels) are applied imperatively through refs, never as static styles.

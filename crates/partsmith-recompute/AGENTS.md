# partsmith-recompute

Runs a document's timeline: validation, dependency graph, parameter and expression evaluation, content-hash cache keys, the shared result cache with LRU eviction, rollback and stop points, failure, panic and cancellation isolation, and per-feature reports.

Spec (the definition of done): `docs/spec/recompute.md`. Acceptance tests in `tests/` come from recompute.md section 6, features.md section 6.4 (`tests/body_semantics.rs`) and naming.md tests 81 to 90 (`tests/naming_conformance.rs`); test 37 (the section 5 budgets) is the benchmark `benches/budgets.rs`; tests 41 to 68 and 71 to 73 (the statuses and the loss diagnosis) are `tests/diagnosis.rs`, with the message lint over every explanation clause of section 3.10, test 69 is the corpus (`tests/reference_stability_{1,2,3}.rs`, below), test 70 the newcomer error corpus (`tests/newcomer_errors.rs`, below), the writer chain tests of section 3.5 are in `tests/timeline.rs`, and file-format.md test 57 (a version 1 document rebuilds as before format version 2) is `tests/format_version.rs`. The per-feature document tests `tests/feature_<type>.rs`, their release-only build-time budgets `tests/budgets.rs` (a module per feature, named like its file) and their helpers `tests/feature_support` (`mod.rs`, with the records, documents and motion checks of the frames on the model, ADR 0023, in `frames.rs`, and the records a feature's document tests share with its budgets in `fillet.rs`, `hole.rs`, `import.rs`, `linear_pattern.rs` and `shell.rs`; `import.rs` also holds `box_step_asset`, the STEP box that other document tests import) belong to the built-in feature pipelines (features.md section 6.1). Do not weaken them.

## Public interface (crate root)

- `Recompute` (`new`, `with_cache_limit`, `registry`, `graph`, `plan`, `run`, `cache_len`, `clear_cache`), `DEFAULT_CACHE_ENTRIES`, and `Input { document, context, stop_at, assets }`. `Recompute` is `Send + Sync`; `graph` and `plan` take `&self` and never change the result cache.
- Graph: `Graph` (`nodes`, `node`, `dependents`, `affected_by`, `independent`), `Node`, `NodeState`, `Edge`, `EdgeKind`, `Change`.
- Plan: `Plan`, `PlanStep`, `Action`.
- Keys: `CacheKey` (32 bytes, `Display` is 64 lowercase hex characters).
- Report: `Report`, `FeatureReport`, `Status`, `Timing`, `BodyReport`, `ParameterReport`, `Message` (`severity`, `code`, `pointer`, `text`, `suggestion`, `repairs`, `fixes`, `detail`, `root`, `reason`). A feature whose only messages are info notices has status `Ok`.
- Loss diagnosis: `LossReason` (`Unknown`, `NotInDocument`, `Suppressed`, `ComesLater`, `RolledBack`, `UpstreamFailed`, `OtherBody`, `Removed`, `EntityDeleted`, `PointGone`, `CopyGone`, `NotInFile`, `Followed`) and `Removal` (`CutAway`, `Covered`, `Rounded`, `Beveled`, `Hollowed`, `PieceGone`, `NoLongerMade`, `NoLongerMeet`).
- Re-exported from `partsmith-features`: `CancelToken`, `FeatureOutput`, `BodyState`, `FeatureError`, `FeatureWarning`, `Repair`, `Fix`, `Severity` (`Info`, `Warning`, `Error`).

## Internals

- `validation.rs`: `Validations` memoizes `validate_and_canonicalize` plus `dependencies`, the compact key params and the names expressions use, per record content (the BLAKE3 hash of id, type and params in stored order), so documents that share ids (`SequentialIds`) keep their own outcomes. Each `graph`, `plan` or `run` is one pass; after it the memo is pruned to the cache limit by last use, never dropping what the pass used.
- `timeline.rs`: `Timeline::prepare` gives every record its state (stop point, then rollback, then suppression, then validity), computes providers, edges, parameters and context names, and builds the `Graph`. Each step's `StepKind` holds its validation (`Valid`) once: an active step always, a suppressed or rolled-back one when it validates, so `Step::valid` gives the loss diagnosis what every record writes. `check_links` holds the pre-build checks. A stop point that names no record falls back to the rollback marker (section 3.1 step 3), and its `unknown_stop` text then says the run stopped at the marker (section 4's second text). Neither text names the missing feature, which has no label (`Message::unknown_stop`, `Message::unknown_stop_before_rollback`).
- `graph.rs`: inactive nodes provide no bodies, so `affected_by` of a feature change is queried on the graph in which that feature is active (after unsuppressing or adding it, before suppressing or removing it).
- `evaluate.rs`: values and the key of one active step, from the keys of earlier steps. `key.rs`: the key preimage (`KeyInput`) and the compact canonical params text.
- `plan.rs` and `run.rs` walk the steps in order with the same key computation and checks; `cache.rs` holds outcomes (`Built` output with its body states, made with `BodyState::from_update` so they keep the topology and volume the feature measured, or the error), each with the loss findings memoized for it (`diagnosis::Findings`, evicted with it), and evicts by last-use run, then key. `run.rs` leaves messages empty; `Recompute::run` renders them after the loop.
- `chains.rs`: `Bodies`, every body's current state, provider and writer chain (section 3.5). A build gets its declared bodies' chains as `BuildInputs::history` (taken out and put back, so nothing is copied; a body its dependencies name twice is taken once and a record joins a chain once, so a plugin's duplicate links cannot misalign a chain); `state_before` gives any body's state just before any record, with its provider.
- `diagnosis/` (section 3.10): `mod.rs` holds `LossReason`, `Removal` and `render_messages`, which explains each error, warning and notice with an `Explainer` per feature (roots of `upstream_failed` chains, `because` of empty bodies, `lost_face` and `turned_over` with their root for `no_effect`, `hole_misses_body` and `separate_solid` (computed in every run, never memoized), the reasons and `after` of losses, those a `plane_fallback` carries included, `by` of follows) and renders it with the run's outputs as `DocumentNames`. `view.rs` is the finished run as the diagnosis reads it (`RunView`, `RecordFact`); `memo.rs` the memoized `Findings` with the `Observations` they hold under and the `Probe` that records them (record facts, which say whether a record is at or after the rollback marker, the rollback marker, provider keys of undeclared bodies, rule 3's lookups of `by` and the order of the document's bodies; the states of the bodies the feature declares are read unobserved, through `declared_state_before`, since its key covers them); `reason.rs` rules 1 to 9, ambiguous `after` and follows, reading names only (naming maps and `BodyState::name_set`), so no element infos are computed; `explain.rs` the `Explainer` and the reason clauses and fixes it renders at report time; `face_name.rs` face names as the diagnosis reads them (`maker_of` and copy groups), on partsmith-naming's `ElementName::face_name` view.
- `pass_lru.rs`: `PassLru`, the map behind the cache and the validation memo. It records the pass (run, plan or graph) that last used each entry and, beyond a limit, evicts the entries used longest ago, the smaller key first on ties, never one the current pass used.
- `test_support.rs` (tests only): small test features (`test_datum`, `test_writer`, `test_reader`, `test_asset`, `test_panic`) and their `registry`, their records (`datum`, `datum_on`, `writer`, and `record` from any JSON), document helpers (`document`, `document_with`, `input`, `prepared`, `prepared_until`), the ids, names, notices, warnings and datum outputs tests write (`id`, `name`, `region_split`, `unknown_params`, `datum_at`) and `with_view`, the diagnosis's view of a run of three datums; timelines are prepared over one shared registry.
- `tests/common` holds the `Harness`, the spec's test features (with `test_history`, which checks the writer chain `BuildContext::body_history` gives it and places its datum at the sum of the body's volumes before each writer) and the plan and graph readers, and re-exports the tolerances, measurement helpers, report readers and test ids of `tests/feature_support` (`feature_report`, `body_report`, `final_state`, `state_before`, `id`; `Run` methods use the same readers), so every test measures and reads reports the same way. `benches/budgets.rs` includes it with `#[path]`, beside `tests/feature_support`, which `common` takes from its parent.
- `tests/diagnosis.rs` runs corpus scenarios through `tests/stability_common` (the record builders and shared setups of `records.rs`, documents, runs and edits, fixes, the STEP plates of the import scenarios, and the picks below), a module of the test target `integration` (not of `budgets`) that the corpus shares. Picks follow the corpus's "Picked references" rule: `run_picked` runs a setup, re-picks every reference (`Reference::from_element`), region (`Region::reference()`), face sketch plane (`fallback_frame: body`) and edge or face axis (`direction`) in the state the setup builds, and runs the picked document; `with_picks` carries those picks into an edited document wherever the edit kept the stored query or region key; `stored` reads the pick a record stores for a query. Each of its scenarios is a function named after its corpus scenario (`r16` is R16 after its edit), or after what it builds when the corpus has none, so its last test, `every_explanation_clause_passes_the_message_lint`, renders every clause of section 3.10's rendering table again (one scenario per `LossReason` and `Removal` variant and per variant part that changes the words, counted by an exhaustive match) and checks each against `lint_failures` of `partsmith-message-lint` (ADR 0027), a dev-dependency like the lint of every document test's messages (`feature_support::assert_messages_pass_lint`).
- `tests/newcomer_errors.rs` (test 70) runs the newcomer error corpus (docs/design/newcomer-error-corpus.md, NC01 to NC12) from the document alone through `tests/stability_common`, as `tests/diagnosis.rs` does: picked setups, edits that keep the picks, and each message's code, text, fixes and root, linted. NC01's finding is rendered with the sketch crate's `MessageContext` as hosts render it, and NC09 runs the documents `Document::units_edits` leaves with and without Keep sizes; cause lines and applied fixes are the engine's twin, `crates/partsmith-engine/tests/newcomer_errors.rs`.
- `tests/reference_stability_{1,2,3}.rs` (test 69) are the reference stability corpus (docs/design/reference-stability-corpus.md, R01 to R66), 124 tests, one per scenario variant and size, each named after its scenario (`r26_deleting_and_recreating_the_base_extrude`), modules of `integration` like every other test file; the record builders and shared setups (`tests/stability_common/records.rs`), documents, runs, edits, fixes, picks (`picks.rs`), readers, resolver diagnostics (`diagnose`) and collected checks (`Checks`, with `placement`, `sketch_placement` and `datum_placement`, and `ExactMessage`, in `checks.rs`) they share live once in `tests/stability_common` (which re-exports `asset_name`, `axis_distance`, `id`, `saved` and `try_element` from `tests/feature_support`), reached as `crate::stability_common` by the second and last thirds, `tests/diagnosis.rs` and `tests/newcomer_errors.rs`. The first third's own helpers are in `tests/stability_support_1/mod.rs`, which re-exports it: its own `Expectations` and `EXACT_POSITION_TOLERANCE`, the corpus's 1e-6 mm. Every setup runs picked (`run_picked`, through `run` or the first third's `setup`), every edit keeps the picks (`with_picks`, through `edit`, `edit_document`, `run_edited` or `run_then_edit`, the same-session edit of a setup), and checks that resolve a reference resolve its stored pick. Message checks compare the structural message the specs render (recompute.md test 69); cause lines ("deleted", the changed setting) are the engine twins'.

## Commands

```sh
export OCCT_ROOT=/opt/occt/7.9.3/native
cargo test -p partsmith-recompute
cargo test -p partsmith-recompute --test integration feature_box::   # one file of tests/ other than budgets.rs, a module of tests/integration.rs (the feature budgets run with --test budgets)
cargo test -p partsmith-recompute --test integration reference_stability_1::   # one third of the reference stability corpus (and _2::, _3::)
# the release-only feature budgets (features.md section 6.1); a filter such as feature_box:: runs one feature's
cargo test -p partsmith-recompute --release --test budgets
cargo clippy -p partsmith-recompute --all-targets -- -D warnings
cargo fmt -p partsmith-recompute
# timing budgets (recompute.md section 5, test 37), all or by words of their names
cargo bench -p partsmith-recompute --bench budgets
cargo bench -p partsmith-recompute --bench budgets -- plan cancel
```

Every test runs by default against `Registry::with_builtins()` (all 20 types are registered). The only ignored tests are the release-only feature budgets of `tests/budgets.rs`, a test target of its own (`[[test]] budgets`), so that no median is timed beside the tests of `integration`, where `feature_shell::t012_performance` missed its 250 ms with more test threads than cores, and `median_duration` of `tests/feature_support` times one median at a time, since in their own target the budgets still slowed each other at 8 test threads on 4 cores (ADR 0035). Each sits in a module named after the file of the feature it times, so its test id is `feature_<type>::<name>`. Every budget but `feature_hole::t033_ten_holes_in_a_200_face_body_within_80_ms`, which fails until its budget is decided (features.md open issue 5), holds in a release build on an otherwise idle machine at any thread count.
